# 动态 Agent 会话与成员借调

## 一、产品定义

Magic 中参与工作的 Agent 核心都是完整 Agent。无论由用户、CEO、PM、项目制作人、组长还是技术总监创建，新 Agent 都可以拥有独立会话、上下文、记忆、任务历史和正常 Agent 工具系统。

“临时 Agent”“会话成员”“项目成员”“借调成员”不是能力等级，而是成员关系：它们决定 Agent 当前服务谁、可以看什么、能做什么、向谁汇报、对什么任务负责，以及工作结束后是否继续保留。

一句白话规则：

> 每次派发都可以招募一个真正能工作的 Agent；角色由任务决定，项目关系决定它服务谁，权限决定它能看到和做到什么。

## 二、固定团队与动态招募

工程启动时可以提供 PM、前端、后端、测试等默认角色模板，帮助用户快速开始。模板只提供角色说明、工具建议和初始配置，不是必须固定存在的组织结构。

工程可以：

- 只有一个 PM；
- 使用一组默认模板成员；
- 在任务出现后动态创建新成员；
- 让 PM、组长或技术总监建立自己的下属会话；
- 保留高频协作者为项目成员；
- 在能力不足时，经明确授权借调其他项目成员（后续扩展能力）；
- 阶段结束后停用或解除成员关系。

## 三、任务角色由派发者决定

CEO、PM、组长或其他获授权派发者根据当前任务决定 Agent 的任务角色。例如：

- 调研竞品时创建“竞品调研专家”；
- 规划技术方案时创建“架构专家”；
- 检查视觉效果时创建“美术评判”；
- 上线前创建“发布经理”；
- 复杂测试中由测试负责人创建“安全审计 Agent”。

任务角色可以在下一项任务中改变。角色变化不自动改变 Agent 身份、项目归属或权限，也不需要把所有可能角色预先建成固定岗位。

## 四、完整能力与有效权限

所有 Agent 使用正常的 Agent 核心能力，包括理解目标、计划、工具调用、文件操作、验证、派发、汇报和持续对话。实际能力受当前有效授权约束：

```text
Agent 核心能力
  + 当前任务角色
  + 成员关系
  + 上下文可见范围
  + 工具与资源权限
  + 预算和副作用规则
= 本次可执行能力
```

因此，“完整 Agent”不等于“拥有所有项目和账户权限”。CEO 可以决定派发什么角色和任务，但不能越过用户授权与 Magic 策略层扩大权限。

## 五、创建来源与汇报关系

| 创建者 | 默认归属 | 默认汇报对象 | 可继续派发 |
|---|---|---|---|
| 用户 | 当前会话或指定工程 | 用户或指定 PM | 按用户授权 |
| 会话主 Agent / CEO | 当前任务或会话团队 | 当前会话主 Agent | 在任务与预算范围内 |
| PM / 项目制作人 | 当前工程 | PM 或项目治理关系 | 在工程授权范围内 |
| 组长 / 技术总监 | 当前负责的小组或任务 | 创建者，上级可见汇总 | 在被授予的委派深度内 |
| 项目成员 | 当前成员任务或小组 | 当前成员或任务责任人 | 受任务、权限和预算限制 |

创建者、任务责任人、实际执行者和结果接收者可以不同。创建下属 Agent 不会自动把上级任务责任转移给下属。

## 六、会话与上下文读取

每个 Agent 有自己的独立会话和记忆，但协作不能靠人工复制所有内容。Magic 应支持有范围的跨会话读取：

- 用户可以查看自己有权访问的工程会话；
- PM 可以查看本工程任务状态、成员汇报、产物和监督范围内的会话记录；
- 派发者可以查看自己创建的下属会话、任务过程和结果；
- 下属 Agent 可以读取任务说明、上级提供的上下文、项目共享事实和授权资料；
- 同项目成员可以读取与依赖任务有关的结果、公开汇报和授权会话；
- 需要完整原始会话时，应检查项目、隐私和权限范围。

“可以读取”不等于把所有会话全文默认塞入每个 Agent 的上下文。系统应优先提供任务相关摘要、事实、产物和按需读取入口，避免无限上下文、循环引用和无关信息污染。

默认不得读取：其他工程私有会话、未授权私有记忆、凭证、隐藏推理、与任务无关的敏感内容，以及已被撤销访问权的资料。

## 七、成员关系生命周期

```text
创建完整 Agent 会话
  → 参与当前任务
  → 完成后解除关系
     或保留为会话成员
     或挂接为项目成员
     或在后续扩展中建立跨工程借调关系
  → 停用 / 归档 / 解除借调
```

关系变化必须记录：

- Agent 身份与来源；
- 创建者和派发者；
- 当前任务角色；
- 服务的会话、项目或小组；
- 可见上下文与工具权限；
- 当前任务责任人和汇报对象；
- 预算、期限和结束条件；
- 关系变更历史。

## 八、跨工程借调（后续扩展）

产品方向允许项目 A 的成员未来被项目 B 借调，但首版默认禁止跨工程直接调用。借调不是把项目 A 的完整工作现场复制给项目 B。

借调时：

1. 保留原 Agent 身份和来源工程关系；
2. 在目标工程建立临时成员关系和独立工作会话；
3. 明确目标任务、责任人、汇报对象、时间和预算；
4. 只开放目标工程需要的上下文、文件和工具；
5. 检查来源工程已有任务和时间冲突；
6. 借调结束后解除目标关系，并保留可审计的任务与产物记录。

来源工程私有记忆不会自动进入目标工程，目标工程内容也不会自动写回来源工程。可复用经验必须经过确认，转换成无敏感信息的摘要、模板或明确共享事实。

## 九、首版范围

首版采用：

- 用户、CEO、PM 和获授权成员创建完整 Agent 会话；
- 派发者按任务动态定义角色；
- Agent 拥有独立上下文、任务历史和正常工具入口；
- 父级读取自己派发的下属会话，PM 查看工程监督信息；
- 会话成员挂接为项目成员；
- 任务账本记录派发、执行、交付、责任和依赖。

首版限制：

- 不支持无限层级自动建队；
- 不默认把所有会话全文注入所有 Agent；
- 不允许借调自动共享两个工程的私有记忆和权限；
- 不允许创建下属 Agent 自动扩大预算或外部副作用权限；
- 不把同一个底层运行或同一工作会话同时冒充多个工程任务；
- 不因角色名称自动授予责任、权限或长期成员关系。
- 首版不开放跨工程直接调用或跨工程借调；该能力进入后续扩展时必须单独完成权限、预算、冲突和隔离验证。

## 十、验收场景

1. CEO 为调研任务创建完整调研专家，会使用正常搜索、文件和验证工具，并向 CEO 汇报。
2. 技术总监创建架构与测试两个下属会话，能够读取它们的任务过程和结果，父任务责任仍由技术总监承担。
3. 新 Agent 完成一次任务后解除关系，运行和产物保留，但不会被误显示为长期项目成员。
4. 高频协作者被挂接为项目成员，身份连续，项目权限与可见范围明确。
5. 后续扩展中，项目 B 借调项目 A 的专家时，目标工程使用隔离会话，双方私有内容不会互相泄露。
6. 后续扩展中，借调成员与来源工程任务发生时间冲突时，PM 收到冲突并重新安排，不静默双重承诺。
7. Agent 读取依赖会话时只获得授权内容，不出现循环加载、无限上下文或重复执行。

## 十一、技术待核查

- OpenCode 是否能稳定创建与用户会话等价的完整子会话；
- 父子会话、同级会话和跨项目会话的读取接口与权限粒度；
- 会话身份、Agent 身份、项目成员关系与底层 Session 的映射；
- 子会话的停止、恢复、归档、重开和长期保留；
- 多层派发的并发、预算、取消和结果回收；
- 借调时工作区、文件、模型、工具、MCP 和外部网络的隔离；
- 上下文按需读取、摘要、版本、引用和循环依赖检测；
- 一个 Agent 身份跨多个隔离会话时的记忆与成本归属。
