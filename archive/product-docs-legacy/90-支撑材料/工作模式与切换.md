# 工作模式与切换

## 一、目的

本文定义两种会话工作方式与一种长期组织形态之间的关系：代理模式和 CEO 模式决定会话主 Agent 如何组织当前工作，工程模式决定长期项目如何建立专属组织。本文不规定底层执行引擎，而规定用户如何选择、各种形态如何嵌入，以及变化后什么必须连续。

本文是代理、CEO 与工程之间的组合规则。代理模式和 CEO 模式文档分别说明各自的工作体验；工程组织文档说明 PM 与成员的长期关系；发生交叉时，本文负责解释作用域、切换和连续性。

## 二、两层产品模型

Magic 不把三个模式设计成互斥的三级开关，而是提供两个可以组合的维度：

1. **会话工作方式**：当前工作主要由会话主 Agent 直接负责，还是由它以 CEO 职责显式组织团队。
2. **组织范围**：当前工作位于普通工作空间，或位于拥有项目专属 Agent 组织的工程中。

代理模式与 CEO 模式共享同一个会话主 Agent，也共享当前会话已形成的会话成员。是否调用子 Agent 不是两者的分界线：代理模式也可以派发和复用会话成员；CEO 模式的差异在于团队分工、依赖、进度、汇报和协作治理成为主要工作结构。

计划推进是独立的任务级能力，不属于代理/CEO 工作方式或普通/工程组织形态。任何任务都可以直接完成，也可以由主 Agent 按计划推进；长任务可以自动展示步骤和进度，但不因此自动进入 CEO 或建立工程。

工程模式内部仍可采用代理或 CEO 工作方式。没有启用工程模式的用户，也可以通过多个普通会话自行组织长期工作。

## 三、会话中的 Agent 关系

### 会话主 Agent

每个普通会话拥有一个持续面对用户、理解目标并对交付负责的会话主 Agent。代理与 CEO 之间变化时，不替换这个主 Agent：

- 代理模式下，主 Agent 以直接执行为主，可以调用其他 Agent 辅助局部工作
- CEO 模式下，主 Agent 承担 CEO 职责，以团队组织、协调和综合交付为主

### 会话成员

代理模式或 CEO 模式创建的核心子 Agent，统一称为会话成员。会话成员拥有当前会话内可恢复的身份、职责、独立上下文、任务历史和汇报关系。

会话成员可以：

- 在当前会话的多个任务中被主 Agent 反复调用
- 在代理辅助与 CEO 团队协作之间改变参与方式
- 完成任务后进入空闲状态，并在后续任务中被重新唤醒
- 与后续新增成员共同参与下一次协作

会话成员默认不能被同一工作空间中的其他会话直接调用。重新打开原会话时，原成员及其关系仍可继续；新会话只能使用已经写入工作空间的文件、产物和正式结论，不能继承原会话成员的身份与私有上下文。

“成员持续存在”表示身份和上下文可恢复，不要求底层进程永久运行。

## 四、选择入口

### 用户主动选择

用户可以在新会话开始前直接选择代理模式或 CEO 模式，也可以在对话中为下一轮工作选择方式。该选择不改写已经开始的运行进程。未表达偏好时可以预选代理模式，但选择器必须可见、可改，不能要求用户先经历代理模式才能使用 CEO。

用户可以在设置中指定默认工作方式。账户默认决定没有其他偏好时的新会话初始选择；工作空间或工程可以覆盖该默认值。对话创建后保持自身默认工作方式，修改上级默认值不追溯改变已有对话。

### 单次调用 CEO

用户可以在代理对话中，为下一项任务调用一次 CEO 协作，而不改变该对话的默认工作方式。当前会话主 Agent 继续面对用户，但本轮承担 CEO 职责，负责派发临时成员、协调结果、遵守准则、处理审批边界、审计过程和最终确认。CEO 完成交付后，用户可以在下一轮回到代理方式，也可以再次明确选择 CEO。

### 系统提出建议

系统可以从任务规模、持续周期、协作需求和用户表达中识别更合适的工作方式或组织方式，并以不打断当前工作的方式提出建议。

建议不是自动切换，也不是错误提示。用户可以接受、忽略，或通过设置关闭此类主动建议。关闭后不再主动建议改变工作方式或启用工程组织，但代理、CEO 和工程的手动入口始终保留。用户明确选择 CEO 或代理时，不需要再次确认。

“工作方式建议”是持久功能设置，默认开启。提示中的“不再主动建议”应提供即时撤销；第一版先提供一个总开关，后续再依据反馈决定是否拆分 CEO 与工程建议。

## 五、代理与 CEO 的判断边界

代理和 CEO 的区别不是参与 Agent 的数量，而是当前工作的组织复杂度与产品呈现方式。

适合保持代理模式：

- 主 Agent 仍然是主要执行者和整合者
- 子任务范围清楚，成员返回结果后即可由主 Agent 吸收
- 成员之间没有持续的复杂依赖
- 用户不需要以团队视角观察和干预工作

适合使用 CEO 模式：

- 多条工作线需要持续并行和协调
- 成员之间存在依赖、交叉评审或反复协商
- 主 Agent 的主要工作转为分派、追踪、调整和验收
- 团队结构、进度、阻塞和汇报需要显式呈现

系统不能因为调用了子 Agent 或达到某个成员数量就自动切换到 CEO 模式。

## 六、组合关系

```text
普通工作空间
  ├── 代理模式：主 Agent 直接负责，可调用会话成员辅助
  ├── CEO 模式：主 Agent 显式组织会话成员协作
  ├── 会话成员可在本会话的多个任务中持续复用
  └── 用户也可用多个会话自行组织长期工作

工程模式
  ├── 项目专属 PM 负责规划、派发、汇总和治理
  ├── 项目成员是可以跨本工程任务和会话工作的长期 Agent
  ├── PM 与成员都可以采用代理或 CEO 工作方式
  ├── 成员可以拥有多个独立任务会话
  └── 项目成员默认不能跨工程调用
```

从 CEO 改回代理，不是解散会话成员或删除已完成工作，而是改变后续工作的组织方式。成员身份、结果、对话记录和工程状态继续保留。

## 七、自动建议的触发信号

### 建议 CEO 模式

- 用户明确要求多个角度、多人分工或相互审查
- 多条工作线需要并行且存在协调关系
- 任务需要辩论、交叉验证或不同专业视角
- 主 Agent 已经持续承担大量拆解、追踪、汇总和复核
- 用户明确表达“不想自己拆任务”

### 建议工程模式

- 用户反复围绕同一长期项目工作
- 用户开始稳定使用角色、职责或协作关系
- 同一组会话成员或同一套分工被反复使用
- 项目需要跨会话积累成员记忆、规范和任务队列
- 用户明确表达“长期建设”“持续维护”“建立团队”等意图

### 不应单独触发建议

- 一次任务字数很多、工具调用多、失败或耗时较长
- 系统内部进行了任务拆解或调用了若干子 Agent
- 用户打开了多个文件

工程模式的建议必须说明它会建立长期项目关系，例如：

> 这项工作可能会持续推进。要建立一个由项目 PM 管理、成员可长期复用的工程吗？

不应使用“升级”“高级模式”“专业模式”等暗示等级的词。

## 八、改变工作方式时的连续性

每一轮工作开始时，系统应形成当前状态的可继续表达，包括：

- 用户原始目标、约束和待决策事项
- 已完成与未完成的工作
- 已产生的文件、产物和验证结果
- 当前工作空间位置
- 可复用的上下文摘要
- 当前会话成员及其职责、历史任务和状态

新一轮工作继续由同一个会话主 Agent 面对用户并承担交付责任。已有会话成员不因方式变化而自动删除、复制或失去上下文；工作方式变化本身不等于运行中移交。

## 九、作用范围

工作方式采用“默认值继承、就近选择覆盖”的规则：

```text
当前任务的临时选择
  > 当前对话的默认工作方式
  > 当前工作空间或工程的默认工作方式
  > 账户默认工作方式
  > 系统预选代理模式
```

- 普通改变默认只影响当前对话的后续工作，不影响同工作空间的其他对话
- 工作空间或工程的默认值只影响之后新建的对话，不追溯修改已有对话
- 单次任务可以临时覆盖对话默认值，完成后恢复原方式
- 已经开始的任务运行不在进程中改变执行组织；新一轮工作可以明确选择另一种方式

## 十、变化边界

### 代理到 CEO

这不是运行中的进程切换。已经开始的代理运行保持原有模式和底层事实；用户随后提出“用 CEO”时，该要求只作用于后续被接收的新一轮工作。若新输入在旧运行期间进入队列，旧运行不被改写，待新输入获得执行时再按 CEO 方式启动。排队输入、待审批工具、文件修改和已经发生的外部副作用仍需按底层运行规则记录。

### CEO 到代理

后续新一轮工作交回同一个会话主 Agent 的代理职责。已有会话成员可以按当前会话规则继续复用，但不会自动转化为工程长期成员；CEO 记录、已有结果和审计信息继续保留。

### 普通工作到工程

必须经过用户明确确认，至少确认：

- 工程名称和目标
- 是否创建项目专属 PM 与长期成员
- 初始团队是推荐还是用户指定
- 哪些上下文进入工程共享空间
- 哪些内容只保留在原会话
- 哪些会话成员转为项目专属长期成员

工程不能通过一次模糊提示静默创建。会话成员转为工程成员后，其归属、可用范围、记忆和权限发生变化，必须让用户看见并确认。

当前会话主 Agent 可以在转换后承接该工程的项目 PM 职责，当前会话成为 PM 主会话，从已有目标、调研和产物继续规划工程。用户也可以选择保留原会话为来源会话，另外创建项目 PM；产品不能为了进入工程强迫用户重新解释目标。

### 工程内的工作方式变化

工程中的 PM 与项目成员都可以直接执行，也可以为复杂任务组织 CEO 协作。某个成员的独立记忆不会因为一次协作自动公开给所有参与者；信息共享仍遵守工程范围与权限。

一个工程可以包含多个由不同成员负责的协作团队。项目 PM 掌握全局任务和跨团队依赖，但不要求所有工作都由 PM 亲自执行。

工程阶段或整个项目完成后，用户可以完成或归档工程组织。项目成员、任务记录、共享信息和产物按工程规则保留，当前 PM 主 Agent 可以退出项目管理职责，继续以代理方式与用户处理后续工作。退出工程不等于删除工程。

### 用户自行组织长期工作

用户可以只依靠多个普通会话、文件和自己的工作习惯组织长期项目。产品可以提供整理或转入工程的入口，但不应反复催促，也不应降低这条路径的基础能力。

## 十一、失败与回退

如果变化所需的上下文、权限或执行状态无法安全迁移：

- 当前方式继续保持可用
- 系统说明无法迁移的具体部分
- 不伪造成功，不删除原有任务或结果
- 允许用户稍后重试或手动开始新的工作范围

## 十二、决策状态

### 已确认

- 用户可以在代理对话中只对一次任务调用 CEO，不改变对话默认方式
- CEO 选择发生在新一轮工作开始时，不把已经进行中的代理运行切换成 CEO 运行
- 代理和 CEO 共享同一个会话主 Agent 及同一组会话上下文；CEO 可按需派发临时成员
- 代理模式允许自主派发和复用会话成员，调用子 Agent 不等于进入 CEO 模式
- 会话成员可以跨本会话多个任务复用，但默认不能被其他会话调用
- 普通工作方式改变默认只影响当前对话；任务可以临时覆盖，工作空间或工程只提供新对话默认值
- 用户可以设置默认工作方式，并关闭主动建议而不失去手动入口
- 已有会话成员只有经用户确认，才能转为工程长期成员
- 一个工程可以包含多个职责或任务范围不同的协作团队
- 当前会话主 Agent 可以承接项目 PM 职责，当前会话直接成为 PM 主会话
- 工程完成或归档后，用户可以回到代理工作，工程组织和成果不会因此消失
- 首次主动建议可以告知用户；用户关闭后不再重复主动建议，代理、CEO 和工程的手动入口始终保留

### 待产品裁定

- 会话成员的自动保留期限、数量上限和归档策略
- 用户是否可以重命名、替换或手动固定会话成员职责

### 待技术核查

- OpenCode 当前版本对会话、运行、排队、停止、暂停和恢复的真实能力
- 底座是否能提供有序、幂等、可补发的状态事件，以及执行中工具和副作用的可恢复信息
