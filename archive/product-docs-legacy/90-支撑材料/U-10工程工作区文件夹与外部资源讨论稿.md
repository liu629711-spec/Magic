# U-10 工程、工作区、文件夹与外部资源讨论稿

> 本文记录 U-10 的正式产品规则。它先把容易混淆的对象拆开，再说明首版范围、用户表达和待技术核查项。

## 一、先用一句话区分

- **工作区**：用户工作的总边界，里面可以有多个工程、会话、文件和资源。
- **工程**：为了一个长期目标建立的项目组织，有自己的 PM、成员、任务、事实、产物和规则。
- **文件夹**：真实文件系统中的目录，是资源，不是工程组织。
- **外部资源**：不一定存在于本地目录中的 Git 仓库、URL、数据库、云文档、API 或其他可连接对象。

白话例子：

> “我的产品研发”是一个工程；`D:\\Magic` 是一个文件夹；“Magic 产品工作区”可以同时容纳 Magic 工程、另一个实验工程和共享资料；GitHub 仓库和线上接口是外部资源。它们可以关联，但不能因为名字相近就当成同一个对象。

## 二、候选对象关系

```text
账户
└── 工作区
    ├── 多个工程
    ├── 多个文件夹与本地资源
    ├── 多个外部资源连接
    └── 普通会话与工程会话

工程
├── 目标、PM、成员、任务、事实和产物
├── 一个默认主资源 + 多个附加资源关联（首版建议）
└── 资源类型和读写范围按关联关系治理
```

工作区是资源和会话的总边界，工程是目标和组织的责任边界。一个工作区可以包含多个工程；建立工程不等于新建文件夹，也不要求用户搬迁已有会话。

## 三、正式规则与首版范围

### 3.1 工作区可以包含多个工程

建议允许一个工作区包含多个工程。这样用户可以在同一个工作环境中同时做“Magic 主项目”“客户 A 项目”和“个人实验”，但每个工程仍然拥有独立的：

- PM 和成员关系；
- 任务、责任和计划；
- 项目事实和产物登记；
- 默认工作偏好、权限和预算；
- 会话、记忆和共享信息边界。

共享工作区不等于工程之间自动共享 Agent、完整会话、私有记忆、权限或任务。

### 3.2 工程支持多资源，主资源只是默认入口

一个真实项目可能天然包含前端仓库、后端仓库、文档仓库、设计资料和部署服务。因此产品模型不应把工程限制为只能绑定一个资源。

首版建议采用“一个默认主资源 + 多个附加资源”的用户体验：主资源用于打开工程时的默认入口，附加资源可以是其他代码仓库、文档目录或外部服务。主资源是界面默认值，不是工程只能拥有一个资源的产品上限。

Agent 开始具体任务时，系统必须明确本次任务的目标资源、读写范围、当前责任人和冲突处理方式。这样用户可以自然地拥有多个仓库，同时 Agent 不会猜测应该修改哪里。

### 3.3 同一资源的重叠写入范围首版只允许一个责任主体

建议首版采用：

- 一个文件夹可以被多个工程看见，但同一重叠写入范围在同一时刻只有一个责任主体；
- 其他工程如需引用，默认只读；
- 需要第二个工程写入时，必须复制、建立独立工作树，或由用户明确处理资源所有权；
- Magic 不因为两个工程都关联了同一个路径，就自动合并任务、Agent、权限或责任。

这里的“单一写入责任”不是说整个工程永远只能有一个 Agent 工作，而是说同一资源的同一重叠写入范围，在同一时刻必须有一个明确的写入责任主体。不同资源或不重叠路径可以并行执行。

产品上应表现为“这项任务正在修改哪个资源和范围”，而不是要求用户理解底层锁或工作树术语。

白话例子：

> 项目 A 正在修改 `src`，项目 B 可以读取 A 的稳定结果或某个版本，但不能悄悄在同一目录同时改文件。否则 A 和 B 都说“代码是我改的”，最终没人能解释结果。

### 3.4 外部资源是独立对象

Git 仓库、URL、数据库、云盘、设计平台、部署平台和 API 等都作为独立资源登记，再通过关系关联到工作区、工程、任务或运行实例。

外部资源至少要能说明：

- 资源身份和连接方式；
- 来源和所属范围；
- 关联的工程或任务；
- 可读、可写、可发布等动作权限；
- 凭据引用，不把原始凭据直接放进会话上下文；
- 版本、同步状态和最近一次可验证访问；
- 成本、副作用和撤销方式。

“工程关联 GitHub 仓库”不等于 Agent 自动获得整个 GitHub 账号的权限；“工程看到一个 URL”也不等于 URL 内容已经被确认成项目事实。

## 四、资源变化时的产品行为

### 4.1 文件移动或重命名

文件夹的产品身份不能只依赖路径字符串。移动或重命名后，Magic 应保留资源身份并更新路径；关联工程、任务和 Agent 需要收到影响通知。

如果路径已经不存在，相关任务进入等待或阻塞，并告诉用户缺少什么、哪个任务受到影响、如何继续，不直接把任务判定为失败。

### 4.2 文件删除

删除是资源副作用，不等于删除工程、任务、产物或历史。删除前按 U-09 和 U-12 的权限、风险和确认规则处理；删除后保留操作来源、时间、责任人和受影响任务。

### 4.3 多 Agent 或多工程同时修改

同一可写资源发生并发修改时，Magic 必须记录变更来源并阻止静默覆盖。可选处理方式包括：

- 先暂停冲突写入，要求责任人处理；
- 生成独立变更集或工作树后再合并；
- 允许用户选择保留、合并或回退。

底层工具是否支持工作树、补丁、锁和冲突证据，属于技术核查，不在本文中假设已经具备。

### 4.4 外部资源失联或版本变化

外部资源不可访问、凭据过期、远端版本变化或同步失败时，运行事实仍然保留，任务不能被静默标成完成。责任人需要看到资源状态、最后一次成功访问和受影响范围，并决定重试、等待、改用本地版本或调整目标。

## 五、与 Agent 和权限的关系

工程成员默认只获得本工程任务所需的资源访问权。工作区里存在其他工程或文件，不代表当前 Agent 可以读取。

访问判断至少同时考虑：

```text
Agent 身份与成员关系
  + 当前任务授权
  + 工程和工作区边界
  + 资源动作与范围
  + 有效期限、预算和副作用等级
  = 本次实际可执行范围
```

一个前端 Agent 可以写主工程的前端目录、读接口文档，但不能因为它属于同一工作区就读取客户项目的私有凭据；一个 PM 可以看到工程任务和资源状态，但不自动拥有部署生产环境的权限。

## 六、用户已确认的裁定

U-10 已由用户确认采用以下规则：

1. 一个工作区允许包含多个工程。
2. 一个工程允许关联多个文件夹或外部资源；主资源只是默认入口，不是资源数量上限，也不代表其他资源只能只读。
3. 多个工程可以引用同一文件夹或外部资源，但首版跨工程默认只读；写入必须建立明确的任务、范围和责任关系。
4. 多个工程引用同一外部资源时，权限、版本、成本和副作用关系分别建立。
5. 文件移动、删除和外部资源失联不自动结束任务，进入等待或阻塞并通知责任人。
6. 多 Agent 同时修改代码资源时，使用独立修改空间和 Git 变更；首版不自动替用户完成不可逆合并。
7. 产品允许没有本地文件夹、只连接外部资源或只做研究的工程；首版可先从本地代码资源闭环实现。
8. 任务完成、修改可进入主版本、合并成功和最终验收必须分别记录。

## 七、首版不做

- 多工作区实时协作权限；
- 多工程同时写入同一目录且自动仲裁；
- 任意跨工程资源读取；
- 自动复制、合并或迁移完整 Agent 记忆与会话；
- 把文件夹路径直接当作工程 ID；
- 把外部资源连接成功直接当作任务完成；
- 在没有冲突证据时自动覆盖其他 Agent 的文件变更。

## 八、待技术核查

- 工作区、工程和本地文件夹的稳定 ID 与生命周期如何绑定；
- 一个工程是否能安全关联多个路径、Git 仓库或外部连接；
- 路径移动、删除、断连和重连是否有稳定事件；
- 并发写入、变更集、工作树、补丁和冲突检测能力；
- OpenCode 工具层能否按工程、任务和 Agent 限制路径与外部资源；
- 外部资源凭据的安全引用、过期、撤销和审计；
- 资源版本、同步状态和成本能否回收到 Magic 任务账本；
- 多工程共享资源时，责任、预算和副作用能否独立归属。
