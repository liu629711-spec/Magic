# 工程模式蓝图

> 本文是方向蓝图，不是完整 PRD，也不是技术实现设计。工程模式的规模很大，当前只冻结它为什么存在、解决什么问题、必须具备哪些边界，以及后续应按什么顺序对齐。

本文用于保留工程模式的探索空间和产品价值假设，不作为首版完整功能清单。涉及 PM、成员、成员任务会话和用户直达的当前设计，阅读《工程组织与会话体系》；涉及首版范围和门槛，阅读《Magic 最终产品裁定与技术会议输入》。

## 一、产品定义

工程模式是围绕一个长期项目建立项目专属 PM、长期成员、成员会话和治理关系的组织方式。

它支持的不只是一个会话中的 Multi-Agent 并行，而是跨本工程多个会话持续存在的组织能力：成员可以复用，记忆可以积累，协作关系可以演进，任务可以长期推进，结果可以被反复评审和交付。

每个工程默认拥有自己的 PM 与成员实例。不同工程可以复用相同角色模板，但不默认共享成员身份、项目记忆、会话和汇报关系。

## 二、它解决的问题

工程模式适用于以下类型的问题：

- 工作会持续数天、数周或更久
- 工程需要多个稳定分工
- 同一批协作关系会被反复使用
- Agent 需要积累各自的工作记忆
- 工程需要任务队列、状态、评审和回顾
- 用户希望把“建设一支团队”本身作为工作对象
- 用户希望主要与 PM 沟通，由 PM 自动创建成员任务会话并持续跟踪

它不适合仅仅因为一次任务很复杂就被自动创建。

## 三、可能的组织形态

工程模式通常由项目专属 PM 负责管理，并可以按项目需要包含但不限于：

- 工程负责人或 CEO
- 产品经理
- 项目经理
- 前端 Agent
- 后端 Agent
- 测试 Agent
- 代码审查 Agent
- 产品质量评判 Agent
- 视觉或美术评判 Agent
- 文档与研究 Agent
- 各专业方向的组长
- 组长管理的组员团队

这些名称是代表性工种，不代表第一版必须预置固定角色。相同工种在不同工程中默认创建为不同成员；首版需要先验证“项目专属的稳定职责是否有价值”，再决定角色创建和模板机制。

## 四、工程模式的核心能力方向

### 1. 团队建立

用户可以从空工程开始，也可以从当前会话及其会话团队转入。当前会话主 Agent 可以承接项目 PM 职责，使当前会话成为 PM 主会话；系统也可以基于工程目标推荐新的项目专属 PM、初始计划和初始成员。无论采用哪条路径，用户都必须知道并确认长期关系的建立。

工程不要求一次建立完整团队。它可以只有 PM，也可以先建立少量核心成员，再随项目阶段增加、调整、停用或固化成员。

一个工程可以包含多个由不同成员负责的 CEO 协作团队，分别负责不同职责、阶段或任务范围。多个团队不是彼此隔离的工程副本，而是在同一工程边界内共享经过治理的事实和产物；项目 PM 负责掌握全局任务与跨团队依赖。

### 2. 稳定职责

每个项目成员应有明确的项目归属、职责、边界、输入、输出、工具权限和协作对象。职责可以调整，但调整应留下可理解的记录。

角色模板可以跨工程复用，但模板在不同工程中创建出的成员是不同 Agent 实例。复制配置不能默认复制旧项目的私有记忆。

### 3. 独立记忆

每个项目成员可以积累与自身职责相关的长期项目记忆，但独立记忆不能天然等于事实。产品需要区分个人工作经验、工程共享事实、成员任务会话上下文和用户决策。

### 4. 共享关键信息

Agent 之间需要共享工程目标、约束、接口、决定、风险和交付状态等关键信息。共享应有范围和来源，不能把所有上下文无差别塞给所有 Agent。

### 5. 层级派发

组长可以管理自己的小团队，并向上汇报。层级派发必须有边界、可观察、可停止、可回收，不能因为理论上支持无限递归就让系统失去控制。

项目成员也可以在自己的任务会话中直接执行、调用临时 Agent，或采用 CEO 工作方式建立会话级团队。这些会话成员不会自动成为工程正式成员。

### 6. 圆桌会议

多个 Agent 可以围绕目标、方案、风险或验收结果进行结构化讨论。圆桌会议需要有议题、证据、发言顺序、冲突记录和结论，不应只是多个 Agent 同时输出长文本。

### 7. 工程交付

工程模式的交付必须回到统一工作区和产物体系。团队组织再复杂，用户最终仍需要知道完成了什么、产出了什么、哪些部分没有完成。

### 8. PM 主入口与成员直达

用户主要在 PM 会话中提出项目目标、查看整体进度和参与关键决策。PM 自动为成员创建任务会话、派发和收取汇报，用户无需手动维持所有会话。

用户仍可以进入任何成员会话直接补充要求或下发任务。直接指令需要同步给 PM 和项目任务系统，由 PM 处理对整体计划的影响。

## 五、关键边界

- 工程模式不是自动升级的结果
- Agent 的稳定职责不等于不可更改的职业身份
- 独立记忆不等于完全隔离，也不等于可以任意共享
- 层级越深不代表智能越强
- Agent 数量越多不代表结果越可靠
- 圆桌会议不应成为所有任务的固定仪式
- 用户始终保留最终目标、范围和关键决策权
- 工程模式不能掩盖失败、冲突或交付缺口
- 多个 CEO 团队可以共存，但不能在缺少范围和协调关系时对同一任务重复发号施令
- 不同工程默认不共享 PM、项目成员和成员私有记忆
- Agent 身份不等于会话；一个项目成员可以拥有多个任务会话
- 工作空间相同不代表工程组织相同，也不授予跨工程调用成员的权利
- 进入工程不要求丢弃原会话，退出或归档工程也不删除项目组织与成果

## 六、建议的设计顺序

1. 先定义工程实体、项目专属组织和生命周期
2. 再定义 PM 主会话、成员身份与成员任务会话
3. 再定义项目成员的职责、记忆、权限和版本变化
4. 再定义任务分派、汇报、用户直达和停止机制
5. 再定义独立记忆与工程共享信息的边界
6. 再定义组长、组员和会话级自主调度规则
7. 再定义圆桌会议与冲突收敛
8. 最后定义角色模板、自动建队、跨工程协作和规模治理

不能先从“预置多少种 Agent”开始，因为角色数量不是工程模式成立的理由。

## 七、首版验证问题

- 用户是否真的需要长期 Agent，而不是持续使用 CEO 模式
- 哪些职责最适合稳定复用
- 独立记忆能否提升连续工作的质量
- 共享信息如何避免遗漏和污染
- 组长派发是否比 CEO 统一派发更自然
- 圆桌会议在什么场景下比单 Agent 审查更有价值
- 用户愿意管理哪些组织信息，哪些应该由系统维护
- 一个工程的合理 Agent 规模和层级上限是什么
- 用户通过 PM 管理项目，是否确实比手动维护多个会话更省力
- PM 自动创建成员会话后，用户能否清楚理解项目正在发生什么
- 项目专属成员是否比跨项目通用 Agent 更能提升连续性和责任清晰度

## 八、明确不提前承诺的内容

- 固定的 PM、前端、后端、测试等预制团队
- 自动为每个工程生成完整组织
- 默认让同一个长期 Agent 同时服务多个工程
- 默认复制其他工程的成员私有记忆
- 无限层级和无限数量的 Agent
- 每个 Agent 拥有永久不变的个人记忆
- 所有 Agent 默认共享所有文件和对话
- 没有证据的自动投票或自动裁决
- 将工程模式包装成“更高级”的产品等级
