# 工程组织与会话体系

> 本文整理已经对齐的工程组织方向，不是完整 PRD。具体权限、自动化程度、界面和异常处理仍需后续专题设计。

本文是工程组织专题的当前详细基线，负责说明 PM、项目成员、成员任务会话、用户直达和圆桌的产品关系。《工程模式蓝图》保留更远期的组织想象和验证问题，不与本文争夺首版范围；涉及全局对象和生命周期时，以系统底图为准。

## 一、工程模式的本质

工程模式不是一个普通会话调用更多子 Agent，也不是 Plan / Execute 一类只影响当前任务的短期状态。

工程模式是在项目开始或发展过程中，建立一套长期存在、可调整、可观察的项目专属 Agent 组织。工程启动时可以采用默认角色模板，也可以只有 PM；后续用户、PM、组长或获授权成员都可以按真实需要创建新的完整 Agent 会话并纳入项目。用户主要通过项目 PM 沟通，PM 代替用户进行规划、派发、协调、追踪和汇总；用户仍可以进入任何成员会话直接工作。

## 二、标准组织结构

```text
工程
├── 项目专属 PM
│   ├── PM 主会话
│   ├── 项目规划与任务派发
│   ├── 依赖、风险和进度管理
│   └── 向用户汇总与请求决策
├── 项目专属成员
│   ├── 完整 Agent 身份、独立会话和项目成员关系
│   ├── 动态任务角色、独立记忆和多个任务
│   └── 必要时创建下属 Agent 会话或组织 CEO 协作
├── 圆桌会议
└── 项目共享层
    ├── 目标、规范和关键决策
    ├── 计划、任务和依赖
    ├── 文件、产物和验证结果
    └── 经过治理的共享信息
```

PM 是用户的主要项目入口，但不是唯一入口。工程成员是长期身份，会话是成员处理不同任务的工作空间，两者不能等同。

## 三、每个工程拥有自己的团队

工程是 Agent 组织、记忆、权限和汇报关系的默认隔离边界。

```text
项目 A
├── PM-A
├── 前端 Agent-A
└── 测试 Agent-A

项目 B
├── PM-B
├── 前端 Agent-B
└── 测试 Agent-B
```

两个项目可以使用相同角色模板，但 `前端 Agent-A` 与 `前端 Agent-B` 是不同成员。它们分别积累本项目记忆，接受本项目 PM 派发，并遵守本项目权限。

默认原则：

- PM 只向本工程成员派发任务
- 项目成员只读取本工程授权的信息
- 相同角色名称不代表同一个 Agent
- 新工程可以复用模板或复制成员配置，但不能默认复制其他项目的私有记忆
- 跨工程调用同一成员必须是用户知情并明确授权的特殊协作

## 四、PM 的工作方式

### 4.1 PM 唯一性与交接

一个工程同一时间只有一名当前 PM。唯一的是工程级最终协调责任，不是唯一 Agent 身份、唯一会话或唯一能提出建议的人。

工程可以拥有 PM 助手、代理 PM、观察者和临时主持人。它们可以整理信息、分析风险、监控任务或在明确期限和范围内代行工作，但默认不能与当前 PM 同时发出互相冲突的正式计划、派发或工程决定。

PM 可以拥有多个会话，但多个会话不能产生多个同时有效的当前 PM。PM 失联时，工程进入“待 PM 接管”，由用户或获授权主体显式接管，不能静默生成第二个当前 PM，也不能重复派发已有任务。

PM 交接必须记录原 PM、新 PM、生效时间、原因、当前计划版本、未完成任务及责任人、运行中任务、待审批事项、资源修改/合并状态、未解决风险、预算、未决决定和新 PM 的接管确认。

交接完成后，新 PM 接管工程级计划、协调、汇总和后续派发；已有任务仍由原任务责任人负责，除非另行显式移交。PM 交接不自动取消、重做、批准、合并或回退已有工作。交接窗口内，新的非紧急派发可以等待，已经开始且授权有效的低风险工作可以继续。

PM 理解项目目标后，可以提出项目阶段、任务依赖、初始成员和自治程度建议。用户确认长期组织边界后，PM 可以：

- 为已有成员分派任务
- 为成员创建独立任务会话
- 跟踪任务、阻塞、依赖和产物
- 接收成员汇报并更新项目计划
- 组织圆桌会议和跨成员评审
- 建议增加、调整、停用或固化成员
- 在 PM 会话中向用户提供全局进度和决策入口

用户不需要逐一进入成员会话派活，但可以随时进入成员会话补充要求、纠正方向或直接下发任务。

用户直接下发的工程任务应同步进入 PM 和项目任务系统。PM 主会话是持续监督入口，用户可以在 PM 正在监督其他成员时直接插入新需求；新消息先登记，再由 PM 判断是补充说明、目标变更、普通新任务还是紧急任务。若与原计划冲突，以用户最新明确指令为准，但不静默取消旧任务，PM 负责识别影响并重新规划，而不是让成员在两套命令中自行猜测。普通需求可在授权范围内自动排队和派发，只有目标、范围、预算、权限、期限或资源冲突才需要 PM 或用户介入。

## 五、成员与会话

每个项目成员可以拥有多个独立任务会话：

```text
前端 Agent-A
├── 登录页面实现
├── 编辑器性能优化
└── 移动端问题修复
```

成员长期保留的是项目身份、职责、权限、独立记忆和历史成果。任务会话可以创建、完成、归档或重新打开，避免把所有工作无限堆积在一个上下文中。

PM 可以通过项目能力在自己的会话中查看：

- 成员当前状态和工作负载
- 正在进行、受阻和等待验收的任务
- 任务之间的依赖和冲突
- 每个成员的阶段汇报与交付物
- 需要用户决策或授权的事项

## 六、成员的自主调度

项目成员可以在自身任务内采用代理或 CEO 工作方式。无论由谁创建，参与工作的 Agent 核心都是完整 Agent，会使用正常的上下文、推理、工具和执行系统；权限、归属、可见范围和责任来源根据成员关系与任务授权不同：

- 直接完成主要工作
- 创建完整 Agent 会话辅助局部任务
- 建立属于该成员当前任务或小组的可复用会话团队
- 在复杂协作中承担 CEO 职责
- 将结果和风险上报 PM

成员创建的 Agent 不会仅因完整能力而自动成为工程长期成员。“临时成员”“项目成员”和“借调成员”描述的是组织关系与生命周期，不是 Agent 能力等级。某个新 Agent 可以只完成一次任务，也可以由 PM 或用户保留为项目成员；任务角色由派发者按当前工作决定，不要求固定成永久岗位。

## 七、团队不需要一次建满

工程可以从只有 PM 的轻组织开始，也可以根据清晰的项目规划建立一组初始成员：

```text
只有 PM
→ PM 加少量核心成员
→ 按项目阶段增加成员
→ 临时调用专业能力
→ 将高频能力固化为长期成员
→ 阶段结束后停用部分成员
```

工程模式的价值不是角色数量，而是需要长期存在的职责、记忆和协作关系不会随一次调用结束而消失。

## 八、动态招募、挂接与借调

普通会话发展为长期项目时，用户可以创建工程，并选择把已有完整 Agent 会话挂接为项目成员。工程运行中，用户、PM、项目制作人、组长或技术总监也可以按授权创建新成员，例如调研专家、架构专家、视觉评审或发布经理；这些名称是当前职责，不是固定成员目录。

当前会话主 Agent 可以承接新工程的项目 PM 职责，使当前会话直接成为 PM 主会话。这样，前期代理执行或 CEO 调研形成的目标、结论和用户关系可以连续进入项目规划，不要求用户换到空白会话重新开始。用户也可以选择保留原会话为来源，另外创建 PM 主会话。

挂接不是复制一个名字，也不是把弱化子 Agent 升级成完整 Agent，而是为已有完整 Agent 建立新的工程成员关系。确认内容至少包括：

- 新的项目职责和汇报关系
- 哪些历史上下文或经验迁入项目记忆
- 哪些原会话私有内容不进入工程
- 项目文件和工具权限
- 原会话是否继续保留该成员的历史身份

未被选择的会话成员继续属于原会话，不因创建工程而静默成为长期成员。

产品方向允许项目缺少某类能力时从其他项目借调成员，但首版默认禁止跨工程直接调用和隐式借调。未来开放借调时，必须保留来源成员身份，并为目标工程建立独立成员关系、任务、责任、预算和隔离工作会话；来源工程私有记忆、权限和未公开内容不自动进入目标工程。借调结束后，目标工程关系可以解除，双方只保留各自有权保留的任务记录、产物、事实或确认摘要。

## 九、工程完成与退出

工程模式不是永久锁定。项目阶段完成或整个项目结束后，用户可以：

- 标记阶段完成并保留当前团队继续后续建设
- 完成或归档工程，冻结 PM 与成员的主动工作
- 重新打开已归档工程，恢复原项目组织
- 退出项目管理视角，由当前主 Agent 回到代理方式处理其他工作

工程退出或归档不会删除项目文件、产物、决策、任务记录和成员历史，也不会把项目成员降级成普通会话成员。是否长期保留成员的可恢复状态和运行成本，需要在工程生命周期专题中继续定义。

## 十、圆桌会议

用户主要通过 PM 进入圆桌，也可以由 PM 或获授权成员为具体议题召集相关成员。圆桌应包含：

- 明确议题与目标
- 参与者及其职责
- 证据、分歧和风险
- 形成的项目决定
- 决定产生的后续任务及负责人

圆桌结论进入项目共享决策，由 PM 负责转化为计划和派发。圆桌不是每项任务的必经流程。

## 十一、已确认原则

- 工程不是一个普通会话的放大版，而是项目级长期组织
- 每个工程默认拥有独立 PM 和独立项目成员关系，但团队可以按需动态增长
- 固定角色只是工程启动模板；用户、PM 和获授权成员可以随时创建完整 Agent 会话并赋予当前任务角色
- 所有 Agent 核心都使用正常 Agent 能力，临时、长期和借调只改变权限、归属、可见范围、责任及保留方式
- 角色模板可以复用；跨工程借调必须显式建立隔离的任务、上下文、权限和汇报关系
- PM 代替用户完成日常规划和派发，用户仍可直接进入成员会话
- 项目成员可以拥有多个独立任务会话
- 项目成员可以自行调用临时 Agent 或组织 CEO 协作
- 工程可以只有 PM 或少量成员，不要求一次创建完整团队
- 同一工程同一时间只有一名当前 PM；助手和代理可以协作，但不与当前 PM 同时拥有冲突的正式协调权
- PM 交接必须显式记录；交接不自动改变成员任务责任、运行、审批、资源变更或历史
- 动态 Agent 会话挂接为项目成员或跨工程借调必须遵守显式授权与项目隔离
- 当前会话主 Agent 可以成为项目 PM，当前会话可以连续成为 PM 主会话
- 工程完成后可以归档组织并回到代理工作，项目成果和组织历史继续保留

## 十二、后续专题

- PM 的自治等级和哪些组织变化必须审批
- 项目创建时的规划、推荐团队和确认流程
- PM 面板与成员会话的导航和状态表达
- 任务、依赖、冲突、汇报和验收机制
- 用户直接派发与 PM 计划冲突时的详细规则
- 成员独立记忆与项目共享事实的写入治理
- 跨工程专家邀请和模板复制机制
- 圆桌会议的发起、记录、收敛与执行闭环
- 工程完成、归档、恢复和成员资源回收策略
