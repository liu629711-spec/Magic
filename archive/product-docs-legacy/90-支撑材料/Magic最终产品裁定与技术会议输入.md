# Magic 最终产品裁定与技术会议输入

> 本文是 Magic 当前阶段进入技术会议的主入口。它统一记录四方已经确认的产品不变量、首版验证建议、必须由用户继续裁定的问题、必须由技术实机核查的问题，以及本次技术会议必须形成的输出。它不是完整技术方案，也不授权技术团队替产品决定长期身份、责任、记忆、权限和模式语义。

## 一、会议状态与最终判断

### 1.1 四方会议是否完成

已完成以下闭环：

1. Nash、Tesla 阅读 AgentCore 旧产品资料和 Magic 当前产品资料，完成第一阶段三方复核。
2. 主产品经理、Nash、Tesla 共同判断需要一名新的第四位成员，但不需要再增加泛产品审阅角色。
3. 第四位成员以“OpenCode 底座、产品系统边界与运行时契约审阅员”身份独立阅读两套资料并提交报告。
4. Nash、Tesla 阅读第四位报告，分别提出修正、遗漏和正式文档分级建议。
5. 主产品经理整合四方结论，形成本文件和《Magic 产品系统边界与生命周期底图》。

### 1.2 为什么需要第四位成员

前三方已经能够判断 Magic 是否解决真实用户问题、模式关系是否自然、工程首版是否过度扩张，但不足以仅凭产品文档判断 OpenCode 当前版本的真实能力，也不能把 AgentCore 的运行时对象直接映射成 Magic 用户对象。

第四位成员补足的是产品与底座之间的系统边界，而不是增加一轮重复意见。四方共同认为当前不需要第五位常驻产品成员。下一位应当进入会议的人不是新的产品审阅者，而是能够对当前 OpenCode 版本进行实机验证并对系统方案负责的技术负责人。

### 1.3 当前阶段裁定

Magic 的产品方向成立，可以进入产品契约与技术可行性共同收敛阶段。

当前可以召开：

- OpenCode 能力盘点与实机核查会议；
- Magic 产品对象、责任和状态契约会议；
- 首版工程闭环的技术拆解与风险评估会议。

当前不应直接召开最终开发排期冻结会，也不能据此直接冻结数据库、接口、完整状态机和权限模型。原因不是方向不明确，而是 P0 产品契约和底座事实还需要在会议中完成确认。

### 1.4 四方最终签署

最终成稿完成后，Nash、Tesla 与系统边界审阅员分别进行了签署式复核：

| 参与者 | 最终意见 | 关注范围 |
|---|---|---|
| 主产品经理 | 同意提交技术会议 | 产品方向、最终裁定与文档完整性 |
| Nash | 无阻塞项，同意提交 | 旧产品证据、自然体验与管理负担 |
| Tesla | 无阻塞项，同意提交 | 责任闭环、状态分离、共享事实与首版验证 |
| 系统边界审阅员 | 两项门槛歧义修正后无阻塞项，同意提交 | OpenCode 核查、运行时映射、生命周期与 Go / No-Go 门槛 |

四方签署表示当前文档足以支持产品契约收敛、OpenCode 实机核查和首版技术风险评审，不表示待用户裁定项、底座能力、数据库、接口、完整状态机、权限模型或开发排期已经冻结。

## 二、结论分级规则

本文使用四种结论级别，技术团队不得混用：

| 级别 | 含义 | 技术会议中的处理方式 |
|---|---|---|
| **产品不变量** | 长期不可违反的产品语义和责任原则 | 技术方案必须满足，不能因实现方便改变 |
| **首版建议** | 为验证价值而提出的范围和默认方案 | 可以根据底座事实调整实现，但不得被解释为永久上限 |
| **待用户裁定** | 涉及长期身份、责任、默认行为、权限、记忆或成本的产品选择 | 技术可以说明代价和方案，不能代替用户决定 |
| **待技术核查** | 依赖当前 OpenCode 版本或现有代码的客观事实 | 必须给出版本、复现方式、证据、限制和结论 |

证据来源应同时标注为：AgentCore 已实现、AgentCore 试运行观察、Magic 已确认、产品建议、技术实机结果或尚无证据。

## 三、产品不变量

以下内容由四方共同确认，作为后续设计和技术方案的上游约束：

1. Magic 采用两个可组合维度：会话工作方式为代理方式或 CEO 方式；长期组织形态为非工程工作或工程组织。
2. 代理方式与 CEO 方式平等。代理方式不是低级模式，CEO 方式也不是复杂任务的自动升级结果。
3. 工程是长期组织形态，不是第三种能力等级，不是大型聊天、文件夹或工作区的别名。
4. 用户可以主动选择初始工作方式、对单次任务临时使用 CEO、修改会话后续默认方式，或继续使用非工程会话自行组织长期工作。
5. Agent 数量、耗时、文件数量、文本长度、失败、重试和任务复杂度不能单独触发 CEO 或建立工程。
6. 工程内部仍可以采用代理方式或 CEO 方式；普通代理和工程成员都可以按需调用辅助 Agent。
7. 临时执行 Agent、会话成员、项目成员、会话主 Agent、PM、长期 Agent 身份和运行实例必须分离。
8. 一个工程的成员默认只属于该工程；相同角色模板不代表相同 Agent 身份、记忆、权限或汇报关系。
9. 工作区、文件夹、工程、会话和任务是不同对象。共享文件不等于共享身份、完整上下文、私有记忆、权限或组织关系。
10. Agent 协作不以共享完整上下文为基础。每个 Agent 默认保持会话、记忆和权限隔离，通过任务上下文、结构化任务结果、文件或产物引用、项目决定和受控证据访问协作。共享事实仍是独立、可追溯、可争议、可撤销的对象，不能等同于文件、聊天摘要、私有记忆或完整会话。
11. 每个进入正式账本、可以执行的任务任一时刻必须有且只有一名当前责任人；责任可以显式转移，不能由运行实例状态隐式改变。草拟工作项在正式派发前由创建者或 PM 承担临时维护责任，不得在无人负责时开始执行。
12. 每个任务必须形成一个统一、可解释的最终状态。任务状态和运行实例状态必须分离。
13. 失败、部分完成、等待、停止和取消不能包装成成功；断连也不能被解释为完成或取消。
14. 长期身份、工程建立、权限扩大、跨边界共享和持久化项目事实必须可见、可审计、可撤销，并按风险获得确认。
15. 取消运行不等于撤销已经发生的文件写入、命令、付费或外部副作用。
16. OpenCode 和 AgentCore 的底层对象不得直接暴露或伪装为 Magic 用户对象。
17. 产品不能承诺执行中的任意“无损切换”。应尽量保持目标、上下文、产物和责任连续；无法无损时必须说明影响，并提供继续、暂停、重新规划或回退。
18. 计划推进是所有任务都可使用的任务级能力，不是代理、CEO 或工程之外的第三种组织模式。较长任务可以由主 Agent 自动生成并持续展示计划、当前步骤、下一步和阻塞；计划展示不等于每一步都需要用户审批。
19. 工作默认、权限授权、成本预算和高风险确认分开治理。就近选择可以覆盖默认偏好，但不能突破上级权限边界；角色名称不自动带来更高权限；授权、预算和副作用都必须有来源、范围、时效和审计记录。

## 四、首版工程验证建议

### 4.1 要验证的完整闭环

```text
用户建立工程
→ 确认一名 PM
→ 配置少量项目成员
→ PM 建立成员任务与任务会话
→ 成员执行、产生状态和产物
→ PM 回收进度、事实与结果
→ 用户查看真实进度或直达成员
→ PM 获知对工程产生的影响并重新协调
→ 任务形成唯一、可解释、可恢复的最终结果
```

### 4.2 首版建议范围

以下均为验证约束，不是永久产品规则：

- 单用户、多 Agent、单工程闭环；
- 一个主工作区和一个主目录；
- 一名 PM；
- 2 至 4 名项目成员；
- 每项任务一名当前责任人；
- PM 可以创建成员任务会话并收回结构化汇报；
- 候选事实可以由用户或获授权的 PM 提升为项目事实；
- 用户可以查看工程任务、成员状态、产物和阻塞；
- 用户在工程内直达成员产生的新任务统一进入工程任务账本；其中影响工程目标、资源、文件、预算或交付的变化还必须通知 PM 并触发计划影响判断；
- 支持等待、停止、失败、部分完成、取消、归档和重开；
- 断连重连、重复事件和运行重试后，Magic 产品状态最终收敛一致。

### 4.3 首版明确不做

- 多层 PM 和无限嵌套团队；
- 跨工程成员直接调用；
- 自动建立完整团队；
- 长期自治扩张和永久在线 Agent 进程；
- 全量私有记忆自动共享；
- 自动裁决相互冲突的项目事实；
- 完整圆桌会议系统；
- 复杂权限继承和多组织治理；
- 成员市场和跨项目永久职业身份；
- 执行中的任意无损代理与 CEO 重编排；
- 以同账号多端跟播代替真正的多人协作权限模型。

### 4.4 首版成功标准

首版成功不是“多个 Agent 同时说话”，而是以下结果同时成立：

- 用户比 AgentCore 对照场景更少手动拆解、派发和重复解释；
- 用户无需持续观看完整协作过程，也能知道谁负责、做到哪里、结果在哪里、是否需要自己介入；
- PM 和成员确实可以跨任务复用，而不是被包装成一次性子调用；
- 失败、部分完成、等待和停止可以被准确呈现并正确恢复；
- 任务、事实、产物和外部副作用都有来源，最终结果只有一个责任闭环；
- 用户完成首轮真实工程后，愿意再次复用 PM 或项目成员。

## 五、产品侧建议方案

以下是四方认为最值得带进会议验证的方案。其中任务责任、任务计划推进、模式作用域、U-09 默认授权与成本治理和 U-10 工程资源规则已经由用户确认采用；其余方案在用户正式确认前仍按“待用户裁定”管理。

### 5.1 已确认的任务责任规则

- 草拟工作项在正式派发前由创建者或 PM 承担临时维护责任，只能编辑、补充或等待派发；正式派发后才能进入执行状态，并必须明确唯一当前责任人。
- 普通代理任务由会话主 Agent 担任当前责任人。
- 当前任务显式使用 CEO 时，仍由承担 CEO 职责的会话主 Agent 对用户统一交付。
- 工程成员任务由被分派的项目成员担任当前责任人；PM 对计划、依赖、项目级汇总和风险负责，不自动承担每个成员任务的执行责任。
- 成员或主 Agent 派发的正式子任务，在开始执行前必须明确子任务当前责任人；下级运行失败不会自动转移上级任务责任。
- 当前责任人可以显式移交。移交必须记录原责任人、新责任人、原因、时间、已有结果和未完成事项。

### 5.2 产品权威状态

- Magic 任务账本是 Magic 产品任务的权威记录，负责保存任务目标、任务关系、责任关系、进度和最终收口状态。
- OpenCode 和 AgentCore 负责产生运行事实，例如运行开始、运行结束、工具结果、测试结果、异常、中断和恢复；这些事实不能被 Magic 改写或伪装。
- Magic 不替 OpenCode 判定底层运行成败，而是由当前责任人依据底层事实、依赖、交付和验收信息，组织多个运行结果并形成产品任务状态。
- 在普通代理中，产品任务状态可以直接映射或接近一次 OpenCode 运行状态；在 CEO 或工程模式中，一个产品任务可能包含多个 OpenCode/AgentCore 运行，运行结束不等于父任务整体完成。
- 一个任务可以拥有多次运行尝试；重试通常产生新的运行实例，但不产生另一个互相冲突的产品任务结论。

### 5.3 任务计划推进

- 计划推进属于任务级能力，代理、CEO 和工程任务都可以使用；它不创建长期 Agent 组织，也不自动建立工程。
- 对包含多个阶段、多个交付物、持续验证、等待依赖或跨多个回合的任务，主 Agent 可以自动生成轻量计划，并持续展示当前步骤、已完成内容、下一步和阻塞原因。
- 低风险、可逆且在已授权范围内的步骤可以自动连续执行；目标、范围、权限、预算、审批、外部发布、删除、付费或其他明显副作用发生变化时，必须请求用户或获授权责任人介入。
- 计划步骤不是正式子任务。只有需要独立责任人、独立交付或验收、单独等待/重试/暂停、跨成员依赖或单独追踪时，才升级为正式子任务，并遵守 U-02。
- 一个计划步骤可以对应多个运行实例，一个运行实例也可以连续完成多个计划步骤；计划步骤、MagicTask、TaskAttempt 和 OpenCode Run 不强行一一对应。
- 计划可以动态调整，但新增正式子任务、改变目标/范围/验收标准、改变依赖或责任关系时，必须形成计划版本或变更记录；已完成步骤不得静默改写。

### 5.4 模式作用域

建议采用以下覆盖顺序：

```text
当前任务临时选择
  > 当前会话默认工作方式
  > 当前工程或工作区对新会话的默认值
  > 账户默认值
  > 系统预选代理方式
```

“本次使用 CEO”和“以后默认使用 CEO”必须是两个不同操作。修改默认值不追溯改变已经执行或正在执行的任务，除非用户明确选择移交当前任务。

### 5.5 新一轮工作选择 CEO 或代理

- CEO/代理选择发生在一轮新工作被接收时，不把已经开始的底层运行进程改造成另一种模式。
- 当前代理 Agent 仍是同一个会话主 Agent；当用户要求“用 CEO 完成这件事”时，该 Agent 在本轮承担 CEO 编排职责，负责理解目标、制定分工、派发临时成员、遵守准则、处理审批边界、汇总结果和向用户最终确认。
- CEO 不是更高权限，也不是自动拥有工程 PM 身份。需要用户或 Magic 策略层批准的动作，仍然必须按权限规则处理。
- 当前运行已经开始后，即使用户补充了“切换 CEO”，也只影响后续被接收的新一轮工作；旧运行继续保持原有运行事实。若输入被排队，模式属于该新输入，不追溯修改旧运行。
- 新一轮工作默认沿用同一 `MagicSession` 的目标上下文、已确认结果、有效计划和可复用会话成员，但每次底层执行仍创建独立运行记录；已完成内容不因角色变化自动重做。
- 用户要求回到代理模式时，后续新一轮工作由同一会话主 Agent 以代理职责直接完成，不需要删除 CEO 记录，也不需要重新解释已经确认的目标。
- 首次出现系统主动建议 CEO 时可以做一次非阻塞说明；用户关闭后不重复主动提示。用户明确说“使用 CEO”或“回到代理”时，不再弹出确认式提示，但当前回合必须有轻量、可识别的工作方式标记。
- 不同用户目标应建立不同 Magic 任务；用户明确表示“继续刚才的目标”时，才在同一任务下继续。工作方式变化本身不自动新建任务，也不自动改变会话默认值。

### 5.6 用户直达工程成员

- 用户在工程范围内直接给成员的新工作，统一进入工程任务账本，而不是成为 PM 看不见的私下任务。
- 用户最新的明确指令优先，但不静默取消 PM 已派发的其他任务。
- 如果新指令与当前任务、文件、预算或交付冲突，成员应暂停冲突部分并请求用户选择；PM同步知情并重排计划。
- 默认由接受任务的成员承担任务交付责任；需要项目级综合交付时，由 PM 汇总但不改写成员真实状态。
- PM 主会话是工程的持续监督入口。用户可以直接在 PM 当前会话中插入新需求；PM 接收新消息不会丢失原计划或停止对其他任务的监督。
- 新消息先进入任务账本，再由 PM 判断是原任务补充、原目标变更、普通新任务还是紧急任务。普通需求可在授权范围内自动排队和派发；紧急需求可以调整优先级，但必须记录受影响任务、责任人和计划变化。
- PM 不需要审批用户的每一个普通需求，只在目标、范围、预算、权限、期限或资源冲突时请求介入。PM 的监督会话可以继续存在，但底层处理应按独立回合、任务和运行实例记录。

### 5.7 动态 Agent 会话、成员关系与借调

- Magic 中参与工作的 Agent 核心都是完整 Agent，会使用正常的上下文、推理、工具和执行系统；临时成员、会话成员、项目成员和借调成员不是能力等级，而是不同的归属、权限、可见范围、责任来源和保留方式。
- CEO、PM、项目制作人、组长、技术总监或获授权成员可以按任务创建新的完整 Agent 会话，并为当前工作分配调研专家、架构专家、实现负责人、测试评审等任务角色。角色由派发者按任务决定，不要求永久固定。
- 工程启动时的默认角色只是团队模板。工程可以从只有 PM 开始，也可以动态增加、调整、停用或保留成员，不要求一开始建满固定岗位。
- 新 Agent 会话拥有独立上下文、记忆、任务历史和完整工具入口；实际文件、工具、模型、预算和外部资源权限由当前任务与成员关系约束。
- Agent 默认通过任务上下文包获得开工所需的最小信息，并通过结构化任务结果接收下级工作回报。它可以在授权范围内读取相关任务结果、成员汇报、项目决定、文件产物和验证证据；这不等于可以读取父会话、兄弟会话或下属会话的完整内容。私有记忆、无关会话和其他工程内容仍保持隔离。
- 一个完整 Agent 会话可以完成一次任务后解除关系，也可以被保留为会话成员、挂接为项目成员，或经明确授权借调到其他工程。关系变化不复制或弱化 Agent 核心能力，但必须记录来源、目标、职责、权限、上下文范围、责任、成本和结束条件。
- 跨工程借调保留来源 Agent 身份，但目标工程必须使用隔离的成员关系、任务和工作会话。来源工程私有记忆与权限不自动开放，目标工程内容也不自动回写来源工程。

### 5.8 任务结果回传、受控信息访问与项目知识沉淀

- 子 Agent 完成或停止工作后，必须向任务指定接收者回传结构化结果。结果至少说明：为哪个任务工作、当前状态、完成了什么、产物在哪里、依据什么验证、还缺什么、存在什么风险或阻塞，以及建议的下一步。
- 结果回传是定向协作通道。父 Agent、当前责任人和被授权的项目成员默认接收任务结果；结果回传不自动授予对方读取完整会话、私有记忆或全部工具权限的权利。
- Agent 开工时只获得完成当前任务所需的最小任务上下文，包括目标、验收标准、相关资源、已确认决定、必要项目规则和当前权限。子 Agent 不自动获得父会话、兄弟会话或其他项目的完整 transcript。
- 文件、diff、测试报告、运行日志和外部资源属于产物或证据。它们必须保留来源、关联任务和适用范围；文件已存在、运行已结束或 Agent 声称完成，均不单独代表任务完成。
- Agent 需要任务范围之外的信息时，必须通过受控请求获得。任务结果、已发布项目决定和任务相关产物可以按策略自动允许；私有会话、跨项目资料、凭据、明显敏感内容或高风险资源必须拒绝或升级给 PM、责任人或用户。
- 共享事实、Agent 判断、用户陈述、项目决定和底层执行事实必须分开记录。Agent 结果可以成为事实或决定的来源，但不会自动把判断升级为事实，也不会自动把子任务完成升级为父任务完成。
- 对目标、范围和取舍，用户最新且明确、且有权作出的项目决定优先于既有决定，但必须形成变更记录，不能静默覆盖历史。对代码状态、测试结果和文件内容，必须以可复现证据核验，不能由口头陈述静默覆盖。
- 事实或决定发生变化时，保留已经发生的运行、产物和历史依据；只重新评估依赖该信息的任务，不默认暂停整个工程，也不自动回滚已经发生的副作用。

详细对象边界、访问规则、结果回传流程和验收场景见《任务结果回传与受控信息访问》。

### 5.9 工程资源、修改空间与合并

U-10 已由用户确认采用。工程资源规则如下：

- 一个工作区可以包含多个工程；一个工程可以关联多个本地或外部资源。
- 工程可以设置一个默认工作位置。默认工作位置只是打开工程和资源未明确时的入口，不是工程的资源数量上限，也不等于唯一写入位置或唯一事实来源。
- 每个具体任务开始前必须明确目标资源、执行目标、读写动作、写入范围、基线或版本和当前责任人。不同资源、不重叠路径和相互隔离的修改空间可以并行。
- 同一资源的同一重叠写入范围，在同一版本基线和同一时间只能有一个主动变更责任主体。多个工程可以引用同一资源，但跨工程写入首版默认禁止，除非建立明确授权和独立任务关系。
- 对代码、文本和配置等可版本化资源，并行重叠修改优先使用独立修改空间和 Git 变更。底层可以采用 branch、worktree、checkout、补丁或副本；产品界面统一表达为“独立修改空间”，不要求用户理解底层术语。
- 分支或修改空间的创建者、任务责任人、执行 Agent、合并责任人和最终验收人可以不同，必须分别记录。任务责任人对任务结果负责，合并责任人对进入目标主版本的变更负责，最终验收人对是否满足用户目标负责。
- 资源变更必须独立记录“执行中、待检查、可进入主版本或正式资源、存在冲突、已进入主版本或正式资源、已放弃”等状态。任务完成不等于变更可合并，变更已合并也不等于整体任务验收完成。
- 合并前必须保留变更内容、来源、基线、检查结果、冲突信息和责任人。存在冲突、基线过期、测试失败、高风险文件或外部副作用时，首版不得自动合并；低风险自动合并能力必须以项目策略和技术核查为前提。
- Git 分支不作为数据库、生产 API、云文档、设计文件或其他外部资源的通用冲突机制。非 Git 资源使用快照、版本、锁、草稿、测试环境、审批或补偿方案；删除分支或放弃修改不代表已经发生的外部副作用被撤销。
- 资源移动、删除、失联、同步失败和远端版本变化保留运行事实，不自动把任务改判为成功或失败；任务进入等待、阻塞或待决策状态，并通知当前责任人。

详细对象、用户表达、资源类型边界和首版核查项见《U-10 工程工作区文件夹与外部资源讨论稿》；三方讨论与用户裁定记录见《会议记录-U-10-工作区工程资源三方讨论》。

### 5.10 权限、成本与副作用

- 低风险、可逆、处于明确范围内的动作可以按用户设置预授权。
- 权限扩大、跨范围访问、明显成本增加、外部发布、付费、删除、部署和其他难以撤销的副作用需要显式确认。
- PM 和项目成员只能在被授予的范围内行动；工程角色不能自动继承账户全部权限。
- 底座工具审批负责最低层拦截，Magic 策略层负责主体、范围、预算、继承和审计。

### 5.11 默认授权与成本治理

U-09 已由用户确认采用。Magic 将“怎么工作”和“允许做什么”分开处理：

- 工作偏好按以下顺序继承：当前任务明确选择 > 当前会话默认 > 当前工程或工作区默认 > 账户默认 > 系统默认。它只决定后续工作如何开始，不追溯改写已经执行的任务。
- 权限不是简单的就近覆盖，而是受上级硬边界约束。`deny` 表示禁止，`ask` 表示等待有权主体批准，`allow` 只有在授权主体有权授予时才有效。下级可以缩小权限，不能突破上级禁止。
- 权限至少记录主体、资源、动作、范围、时效、授权来源、预算上限和副作用等级。Agent 角色、PM 身份或 CEO 职责本身不自动授予更高权限。
- Agent 向下派发时，只能传递自己拥有且允许转授权的权限、预算和派发深度；默认不传递原始凭据，也不因创建下属 Agent 自动增加预算或外部副作用权限。
- 预算同时记录上限、已预留、实际消耗、成本归属和剩余额度。子 Agent 派发前应先完成预算预留，超出上限时停止派发或请求授权。
- 权限撤销影响后续工具调用、新 Agent 创建和新的信息访问，不改写已经发生的运行、文件写入、费用和外部副作用；历史授权与使用记录继续保留。
- 首版默认禁止跨工程直接调用。未来若开放跨工程借调，必须建立一次性目标关系、隔离上下文、独立任务、独立预算和明确责任，不得把两个工程的权限或私有记忆自动合并。
- 用户界面不展示复杂继承矩阵，只说明“这次能做什么、预计花多少、哪里被拦住、需要谁决定”。

### 5.12 PM 唯一性与交接

U-11 已由用户确认采用：

- 一个工程同一时间只有一名当前 PM。这里的“唯一”指工程级最终协调权唯一，不限制工程拥有 PM 助手、代理 PM、观察者或临时主持人。
- PM 助手可以分析、整理、监控和提出建议，但默认不能同时拥有工程级最终派发、计划裁定或统一汇总权。代理 PM 只有在明确授权的范围和期限内代行职责。
- 当前 PM 是工程责任关系，不等同于某一个永久进程、单个 OpenCode Session 或某一次运行。PM 可以拥有多个工作会话，多个会话也不能因此形成多个同时有效的当前 PM。
- PM 交接必须显式建立交接记录，至少包括原 PM、新 PM、生效时间、原因、计划版本、未完成任务及责任人、运行中任务、待审批事项、资源修改/合并状态、未解决风险、预算和未决决定。
- 交接完成后，新 PM 接管工程级计划、协调、汇总和后续派发；已有成员任务仍由原任务责任人负责，除非另行显式移交。PM 交接不自动取消、重做、批准或合并已有工作。
- 交接窗口内不能让两个 PM 对工程同时发出互相冲突的正式指令。新的非紧急派发可以等待；已经开始且授权有效的低风险任务可以按原规则继续。
- 原 PM 失联、进程退出或会话不可用时，工程可以进入“待 PM 接管”状态。系统可以提醒用户或获授权主体接管，但不得静默制造第二个当前 PM 并重复派发。
- 交接只改变后续工程协调责任，不改写历史消息、运行事实、任务结果、资源变更、审批记录和已发生副作用。

详细交接清单和异常案例见《U-11 PM 唯一性与交接规则》。

### 5.13 权限模式与审批

U-12 已由用户确认采用。Magic 对用户提供三档简洁权限入口：

- **请求批准**：遇到需要确认的动作时暂停并询问。
- **当前范围内自动处理**：在当前任务、会话或工程已授权范围内自动工作，遇到高风险动作时询问。
- **完全访问当前工程**：解除当前工程的文件和网络访问限制，但系统禁止项、高风险确认、预算边界和账户边界仍然有效。

三档入口不替代内部权限模型。Magic 必须分别记录资源访问边界、审批策略、动作风险、预算范围、环境范围、授权有效期和授权来源。用户选择“帮我批准”或类似自动处理时，默认作用于当前任务；扩展到当前会话或工程必须明确显示范围，不能静默变成账户永久权限。

低风险且可逆的读取、计划、独立修改空间、分支/工作树创建、本地测试和本地提交可以按授权自动执行。合并主版本、远程推送、共享资源修改和超预算动作按项目策略处理，必要时请求责任人确认。删除重要资源、生产部署、生产数据库/API 写入、付费、对外发布和无法可靠审计的动作必须确认或首版禁止。

模型建议、Magic 是否允许、底层是否实际执行、外部副作用是否已经发生必须分开记录。运行中遇到高风险动作时，保存当前结果和运行事实，进入等待确认；批准后继续，拒绝后保留历史，不重复执行已发生的动作。

详细用户表达、模式范围和审计要求见《U-12 权限模式与审批规则》。

以下问题不能由技术团队自行替用户选择。用户已经完成 U-01 至 U-12 的产品裁定；技术团队仍需针对每项首版能力给出方案、代价、证据和风险，不得用技术实现反向改写产品语义。

| 编号 | 待裁定问题 | 四方推荐起点 | 不裁定的风险 |
|---|---|---|---|
| U-01 | 任务、子任务、任务会话、回合和运行实例的正式定义 | 采用分层，并为团队画布预留成员、任务、派发、执行、交付、责任和依赖关系 | 状态、接口和 UI 各自发明概念 |
| U-02 | 不同工作形态下谁是当前责任人 | 采用唯一当前责任人，允许显式移交 | 失败或直达成员时无人收口 |
| U-03 | Magic 任务账本与底层执行事实的关系 | 任务账本是产品任务关系和收口状态的权威记录；OpenCode/AgentCore 提供不可改写的运行事实 | 重连、重试或多 Agent 协作后出现多个任务结论 |
| U-04 | 单次 CEO 与默认 CEO 的作用范围 | 采用当前任务覆盖会话默认的规则 | 用户不知道一次选择会影响多久 |
| U-05 | 新一轮工作选择 CEO，旧运行如何保持连续 | 用户在新一轮工作开始时选择 CEO；当前代理运行不被改写，主 Agent 以 CEO 职责派发临时成员；首次建议可关闭，明确选择不重复提示 | 把角色选择误做进程切换、重复执行、提示骚扰或责任漂移 |
| U-06 | 用户和 PM 会话中插入需求时的优先级与权责 | 用户可在持续运行的 PM 会话中直接插入需求；先入账再分类，普通需求可排队派发，紧急需求可调整优先级但不静默取消旧任务 | 私下任务、队列混乱、监督中断或文件冲突 |
| U-07 | 动态 Agent 会话、项目成员与跨工程借调边界 | 所有参与者均为完整 Agent；任务角色动态分配，固定角色仅为启动模板；成员关系可挂接、保留或借调，但权限、上下文、责任和项目边界分别治理 | 把临时误解成弱能力、把角色固化成团队、跨项目泄露记忆或责任失真 |
| U-08 | 任务结果回传、受控信息访问与项目知识沉淀 | Agent 默认会话隔离，通过最小任务上下文、结构化结果、产物引用和受控证据访问协作；事实和决定保留来源、范围、争议与替代记录 | 结果无法回到主任务、文件和会话边界混淆、错误结论扩散或用户被迫管理共享上下文 |
| U-09 | 默认值、授权和成本如何跨账户、工作区、工程、会话、任务继承 | 工作偏好按层级继承并允许当前任务覆盖；权限受上级硬边界约束；预算可预留、归集和拦截；撤销不改写历史 | 默认设置意外扩大执行权限、子 Agent 越权派发或成本失控 |
| U-10 | 工程、工作区、文件夹和外部资源的基数关系 | 已确认：工作区可含多个工程；工程可关联多个资源；主资源/默认工作位置只是默认入口；代码资源重叠修改使用独立修改空间和 Git 变更，由授权责任人检查并合并；跨工程写入首版默认禁止 | 文件移动、多资源关联、并发写入、合并责任和多工程引用后失真 |
| U-11 | PM 是否必须唯一及如何交接 | 已确认：同一工程同一时间只有一名当前 PM；允许助手/代理协作；交接显式记录并保留任务、运行、审批、资源变更和历史责任 | 多 PM 指令冲突、重复派发、任务责任漂移或交接丢状态 |
| U-12 | 哪些成本和外部副作用必须逐次确认 | 已确认：提供“请求批准、当前范围内自动处理、完全访问当前工程”三档入口；访问边界、审批策略、预算、风险和有效期分开治理；高风险和系统禁止项独立生效 | 自动化造成不可接受损失、提示疲劳、预算失控或副作用无法追踪 |

## 七、OpenCode 实机能力核查矩阵

当前产品资料没有提供 OpenCode 的锁定版本、稳定接口、状态枚举和可复现证据。因此下表全部是待技术核查，而不是对 OpenCode 能力不足的判断。

| 能力域 | Magic 需要的能力 | 核查问题 | 会议必须提交的证据 |
|---|---|---|---|
| 版本与扩展点 | 可锁定、可升级、扩展点稳定 | 当前采用哪个 commit/tag；插件、事件和内部 API 哪些稳定 | 版本号、依赖清单、升级策略 |
| 会话 | 创建、继续、历史、分支、归档、重开 | 会话与运行如何关联；重启后保留什么 | 最小复现、持久化位置、限制 |
| 子 Agent | 创建、独立上下文、结果回收、取消 | 是否存在稳定 API；是否支持复用，复用的究竟是什么 | 接口、生命周期实验、并发限制 |
| 并发与排队 | 多成员运行、插话、排队、指定接收者 | 真实并发模型是什么；队列作用域和顺序如何定义 | 压测或场景实验、队列语义 |
| 暂停与恢复 | 等待审批、跨进程恢复、重启恢复 | 是真正恢复原运行，还是重新发起 | 断进程实验、检查点内容 |
| 停止与取消 | 停止模型、工具和任务尝试 | 中断粒度如何；已发生副作用如何呈现 | 取消场景、残留状态、补偿边界 |
| 工具与审批 | 工具调用、审批钩子、结果和审计 | 是否可按主体、资源、动作、时效拦截 | 钩子接口、审计样例、失败行为 |
| 工作区与文件 | 路径隔离、变更集、冲突和产物登记 | 并发写同文件如何处理；是否支持补丁或工作树 | 冲突实验、差异与回退能力 |
| 历史与持久化 | 对话、运行、工具、成本和副作用记录 | 保留、删除、迁移、版本兼容如何处理 | 数据结构、恢复实验、保留策略 |
| 事件与状态 | 有序、幂等、重连补发、最终收敛 | 事件 ID、顺序、重复、丢失和最终状态枚举 | 事件样本、重连实验、状态表 |
| 成本 | 模型与工具成本归集、预算拦截 | 能否按任务、成员、工程归集和限制 | 计量字段、误差、阻断点 |
| 安全隔离 | 成员权限、目录范围、外部网络和命令边界 | 能否支持工程和成员级策略 | 权限实验、越权失败证据 |

每项核查结论只能使用：**原生满足、适配后满足、Magic 需补建、当前不支持、仍未知**。不得仅写“应该可以”。

## 八、AgentCore 继承与重建边界

| 分类 | 内容 | Magic 处理方式 |
|---|---|---|
| 可继承的产品经验 | AgentCore 已实现并在既有试运行范围内验证可用的直答与委派并存、插话、排队、停止、真实交付和诚实终态经验 | 作为全模式共同原则和体验基础，不外推为大规模市场验证 |
| 可参考的运行机制 | DAG、Journal、事件 fold、SSE、同人续派、工具审批、挂起恢复 | 映射到 Magic 契约后复用或重建，不直接暴露 |
| Magic 必须拥有的契约 | 工程、PM、Agent 身份、会话成员、项目成员、任务账本、共享事实、产物登记、工程权限、成本策略 | 由 Magic 定义语义、权威状态和责任边界 |
| 不应直接迁移 | `Run`、`RunSession`、transcript 等同任务或成员；文件夹等同工程；CEO 等同复杂任务；同账号多端等同多人协作；永久进程等同长期 Agent | 明确禁止形成用户心智或数据模型捷径 |

“Magic 必须重新建立”表示必须建立自己的产品语义和责任层，不表示所有底层执行能力都要从零开发。AgentCore 文档中的蓝图不等于代码能力，现有代码中的对象也不等于已经形成稳定产品契约。

## 九、产品对象与底座对象映射原则

| Magic 产品对象 | 权威归属建议 | 底座关系 |
|---|---|---|
| 工程 | Magic | 底座没有证据证明存在等价对象 |
| PM、会话成员、项目成员 | Magic 身份与成员关系 | 可绑定多次底座运行，不等同某个进程或 Run |
| 会话 | Magic 记录并绑定 OpenCode 会话 | 是否一对一待实机验证 |
| 任务 | Magic 任务账本 | 可拥有一个或多个 OpenCode 运行实例 |
| 回合 | Magic 会话输入记录 | 可以映射底座消息或一次请求，但不承担任务责任 |
| 运行实例 | OpenCode 运行证据加 Magic 映射 | 负责实际执行，不承担长期身份 |
| 共享事实 | Magic 版本化事实账本 | 可引用底座消息、文件和运行结果作为来源 |
| 产物 | Magic 登记记录加真实文件或外部资源 | 底座写文件只是产物形成过程的一部分 |
| 权限与审批 | Magic 策略账本加底座执行拦截 | 两层都必须保留审计信息 |

详细生命周期见《Magic 产品系统边界与生命周期底图》。

## 十、技术团队不得自行推断的事项

- 不得因 OpenCode 内部已有 session、agent、task 或 run 名称，就认定它们等同于 Magic 产品对象。
- 不得因底座支持子 Agent，就认定支持会话成员、项目成员及其长期记忆。
- 不得因可以恢复聊天历史，就认定可以恢复任务、工具副作用、审批和工程状态。
- 不得因多个 Agent 可以运行，就自动进入 CEO 方式或建立工程。
- 不得为了复用实现，把代理方式设计成简化版 CEO。
- 不得把首版一名 PM、2 至 4 名成员或单目录写成永久限制。
- 不得让运行状态隐式修改当前责任人或产品最终状态。
- 不得静默扩大权限、跨工程共享记忆或把会话成员升级为项目成员；首版不得把跨工程借调描述成已经支持。
- 不得把文件已写入、模型已输出或运行已结束直接等同于任务成功。
- 不得对外承诺尚未通过实机验证的 OpenCode 能力。

## 十二、开发冻结与后续扩展门槛

本节包含两个时间不同、目的不同的门槛：前两项是开始首版开发前的冻结条件，最后一项是首版完成后决定是否扩大产品范围的验证条件。后者不是首版开发的前置条件。

### 12.1 开发冻结前置门槛

#### 产品门槛

U-01 至 U-12 中影响首版的项目已经由用户裁定，并同步回对应专题文档。

#### 技术门槛

OpenCode 实机能力矩阵完成，并且每项首版关键能力都拥有被会议接受的可执行路径：

- **原生满足**：附当前版本、接口、复现证据、限制和验收标准；
- **适配后满足**：附适配方案、责任边界、工作量、风险和验收标准；
- **Magic 需补建**：附技术方案、工作量、风险、依赖和验证计划，经评审确认可进入首版；
- **当前不支持**：必须选择调整首版范围、采用替代方案或将开发冻结标记为 No-Go；
- **仍未知**：不得进入开发冻结。

“能力事实已经查明”不等于“首版路径已经可行”。技术门槛以 Go / No-Go 判定表中所有首版关键路径均不再处于阻塞或未知状态为通过标准。

产品门槛和技术门槛同时通过后，才适合冻结首版技术方案与排期。

### 12.2 首版扩展门槛

#### 用户验证门槛

首版通过真实工程场景验证，证明它确实减少手动派发、重复解释和无意义确认，同时没有牺牲责任清晰、真实状态、可恢复性和用户控制权。

用户验证门槛不作为首版开始开发的前置条件，而用于决定是否扩大工程组织、圆桌、多层团队和跨工程能力。技术可行不能自动等同于产品价值成立。

## 十三、四方最终裁定

> **Magic 应继承 AgentCore 已实现并在既有试运行范围内验证可用的协作经验，利用 OpenCode 作为强执行底座，但由 Magic 自己定义用户能够理解和信任的任务、身份、责任、事实、权限与工程组织。代理方式先让工作自然发生，CEO 方式让协作按需展开，工程让被用户确认的长期组织持续存在。产品的先进性不来自 Agent 数量，而来自用户无需管理复杂编排，系统仍能保持真实、连续、可控和可追责。**

## 十四、首次四方技术对齐会议结果

### 14.1 会议结论状态

2026-08-29，主产品经理与以下四位技术总监完成三轮正式对齐：

- Magic AI 核心总监；
- Magic AgentCore 项目架构技术总监；
- Magic OpenCode 项目架构技术总监；
- Magic OpenCode 项目前端技术总监。

四位总监均对 F-01 至 F-10 完成签署，最终状态为“有条件一致”。没有人否定 Magic 的产品方向，也没有人同意在底座证据不足时冻结首版技术方案。

### 14.2 四方共同接受的技术产品基线

1. Magic 产品方向 Go；首版开发冻结是独立门槛，只有影响首版对象、责任、状态收敛、权限、副作用、选定底座契约或恢复语义的未知才阻塞冻结。
2. Magic 必须独立持有 `AgentIdentity`、`SessionMember`、`ProjectMember`、`PM`、`MagicSession`、`MagicTask`、`TaskAttempt`、`Turn`、`Artifact`、`Fact`、`Permission` 和 `SideEffect` 等产品语义。OpenCode 与 AgentCore 对象只能作为绑定或运行证据。
3. 首版采用候选关系：`MagicSession 1-N MagicTask`、`MagicTask 1-N Turn`、`MagicTask 1-N TaskAttempt`、`TaskAttempt 1-1 RootExecutionBinding`，每个 Attempt 暂限制绑定一个 canonical OpenCode Session；该关系仍需底座实机验证。
4. 代理/CEO 与非工程/工程组织是两个组合维度；任务计划推进是第三个独立的任务级维度。当前任务选择、会话默认、工程默认、身份和成员关系必须分开存储。代理/CEO 选择发生在新一轮工作开始时，不在已经开始的运行进程中切换；不承诺任意时刻无损重编排。
5. 正式任务和正式子任务任一时刻只有一名 Magic 当前责任人。CAPTAIN 负责 Attempt 内编排，PM 负责工程计划与汇总，项目成员负责被分派任务。临时 Agent 仍是完整 Agent，但不会仅因执行一次任务自动获得长期成员关系或长期责任。
6. Task、Attempt/Run、Connection/Sync、Approval、Artifact、Fact 和 Responsibility 必须分层。底座 `idle`、`ended`、Run 完成、工具成功、文件存在或 SSE 断开均不能单独推导 Magic Task 成功。
7. transcript、memory、NoteWall、文件、产物和共享事实必须分层。所有参与工作的 Agent 都是完整 Agent；临时、会话、项目和借调描述成员关系而非能力等级。角色按任务动态分配，关系变化不自动迁移完整历史、私有记忆或权限。
8. 前端默认展示目标、责任人、任务状态、介入事项、产物和验收状态；底层事件、工具日志、Session/Run ID 和复杂协作细节默认折叠，但失败、等待、同步缺口和已发生副作用不得隐藏。
9. 首版按已承诺的端到端场景验收，不按 Agent 数量、页面数量或测试文件存在验收。完整圆桌、多层 PM、跨工程、多用户多端、永久 Agent 和任意无损切换延后。
10. 任务计划推进可以在代理、CEO 和工程任务中使用；计划步骤用于展示和推进，不自动等同正式子任务、Agent 或 OpenCode Run。

### 14.3 唯一首版技术阻塞

F-10 是四方共同确认的唯一组合技术阻塞：锁定 OpenCode runtime、commit/tag、protocol/client contract 后，必须以可重复的端到端证据验证 Magic TaskAttempt 在断连、进程重启、重复或乱序事件、重试、停止、审批和已发生外部副作用组合场景下最终收敛。

验收必须能够回答：留下了什么、谁负责、是否重复执行、产物来自哪里、审批处于什么状态、哪些副作用已经发生，以及 Magic Task 的最终状态是什么。在该证据完成前，可以继续产品裁定、Adapter 原型和明确标记的受控灰度，但不得冻结首版数据库、API、完整状态机和开发排期。

### 14.4 仍由用户裁定的事项

U-07 已由用户确认采用：Agent 核心能力完整，任务角色由 CEO/PM/组长等派发者动态决定，固定角色只作为默认团队模板，成员可以挂接项目或经授权跨工程借调；跨工程借调首版默认不开放。U-09 已由用户确认采用：工作偏好可以就近覆盖，权限受上级硬边界约束，预算需要预留、归集和拦截，撤销不改写历史。U-10 已由用户确认采用：工作区可包含多个工程，工程可关联多个资源，主资源只是默认入口；代码资源重叠修改使用独立修改空间和 Git 变更，由授权责任人检查并合并，任务状态与资源变更状态分开记录；非 Git 资源使用自身的版本、锁、审批或补偿机制。U-11 已由用户确认采用：同一工程同一时间只有一名当前 PM，允许助手和代理协作；PM 交接必须显式记录，且不自动改变成员任务责任、运行、审批、资源变更或历史。U-12 已由用户确认采用：前台提供“请求批准、当前范围内自动处理、完全访问当前工程”三档入口；访问边界、审批策略、预算、风险和有效期分开治理，高风险和系统禁止项独立生效。U-01 要求成员、任务、会话、回合、运行、派发、执行、交付、责任和依赖关系必须分开表达；U-03 要求 Magic 不改写 OpenCode/AgentCore 的运行事实，而是在产品任务层组织多个运行结果并形成收口状态。Magic 对象与 OpenCode Session/Run 的具体绑定基数、跨会话读取和借调隔离仍属于待技术核查。

### 14.6 U-01 用户确认的团队画布预留

团队画布属于后续增量方向，不是首版必须交付的完整页面。它应展示 Magic 产品账本中的真实关系，而不是把 OpenCode Session、Run 或 SSE 事件直接画成组织节点。
