# U-01 团队画布讨论：OpenCode 前端总监意见

## 1. 是否支持

**有条件支持。**工程团队在画布中展示真实工作有价值：它能让用户同时理解成员身份、任务进度、责任归属、阻塞和交付去向，减少逐个打开会话、阅读日志和反复询问的管理负担。条件是画布展示 Magic 的任务账本和责任投影，OpenCode 的 Session、Run、SSE 和工具事件只能作为证据；不能把“正在运行”伪装成“任务完成”，也不能把运行节点伪装成长期成员。

## 2. 画布节点与对象区分

- **成员节点**：`AgentIdentity` 加 `ProjectMember` 关系，表示谁属于工程、具有什么职责；不是进程，也不是一次 Run。
- **任务节点**：`MagicTask`/子任务，表示可交付目标、当前责任人和最终状态；这是画布的主要业务节点。
- **会话入口**：`MagicSession` 或任务会话关联，表示围绕目标持续交流的上下文；不等于任务或成员。
- **回合记录**：`Turn`，表示一次输入及响应；可属于任务，但不承担最终责任。
- **运行投影**：`TaskAttempt` 及其 OpenCode Session/Run、子运行，表示一次执行尝试和实时活动；应作为任务节点内的状态层或展开详情，默认不成为独立团队成员节点。

最小原则是：成员回答“谁”，任务回答“交付什么”，会话回答“在哪个连续上下文工作”，回合回答“这一轮发生了什么”，运行回答“这次尝试实际执行到哪里”。

## 3. 四种关系必须拆开

必须拆成不同关系：

1. **正在做什么**：成员与当前 `MagicTask`/`TaskAttempt` 的执行关系，是运行负载投影。
2. **上派给谁**：父任务或 PM 向成员任务的派发关系，记录派发者、接收者、时间和约束。
3. **结果给到谁**：产物、汇报或事实向任务、PM、用户或下游任务的交付关系。
4. **谁负责**：任务唯一当前责任人关系，独立于执行者、派发者、接收者和 PM。

OpenCode parent/child session 最多证明运行层级，不能直接证明上述四种 Magic 关系。成员失败不会自动改变任务责任；显式移交必须记录原因、已有结果、未完成事项、审批和副作用。

## 4. “开发一个电商网站”示例

用户提出“开发一个电商网站”。工程 PM 创建总任务，当前责任人为 PM，并拆出：产品方案、前端实现、后端接口、测试验收。PM 将前端任务派给前端项目成员，将接口任务派给后端成员，将验收任务派给测试成员；每个任务进入工程账本并建立自己的任务会话。

前端成员在自己的会话中进行多个 `Turn`，一次提交创建一个 `TaskAttempt`，由 Magic Adapter 绑定一个 canonical OpenCode Session；OpenCode Run 和子运行只显示为“实现首页/购物车”等当前执行证据。前端成员交付代码和截图产物给前端任务，测试成员收到该产物并执行验收。测试失败时，测试任务为失败或阻塞，前端任务仍由前端成员负责，PM 获知影响并决定重派或调整计划。全部子任务完成且产物通过验收后，PM 汇总结果交给用户并对工程总任务收口；“Run 已结束”本身不构成网站完成。

## 5. U-01 首版预留与画布后延

首版必须预留稳定的 `MagicSession`、`MagicTask`、`TaskAttempt`、`Turn`、`AgentIdentity`、`ProjectMember` 标识，以及任务会话关联、父子任务关系、派发关系、结果交付关系、唯一责任人、运行绑定、事件游标和产物来源。即使首版不做完整画布，也不能把这些关系压成一个 session 或 run 字段。

后延：自由拖拽布局、全量 DAG/时间轴、多人实时协同编辑、跨工程连线、复杂依赖自动重排、无限层级团队、完整圆桌和把所有工具日志常驻画布。首版可先做工程总览中的成员列、任务卡、责任标识、阻塞提示和按需展开的运行详情。

## 6. 对当前模型的修正

“每个成员自己的独立会话”不能推出“每个成员永远有一个在线进程”；“正在做什么”不能推出任务状态；“结果交给谁”不能推出最终责任人；PM 也不应自动成为所有成员任务的责任人。画布若直接按 OpenCode Session/Run 建节点，会把执行拓扑误当组织拓扑。

**结论：有条件支持。**

**唯一最重要的产品建议：先冻结四种独立关系和其权威来源，再设计画布；画布只能是 Magic 任务账本的可解释投影，不能反过来成为第二套任务真相。**
