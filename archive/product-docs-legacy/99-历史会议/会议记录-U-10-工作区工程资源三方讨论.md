# U-10 工作区、工程、文件夹与外部资源三方讨论记录

> 本记录总结 U-10 的多轮独立审阅和交叉质询。用户已确认采用第五部分的规则；技术核查项仍需由技术团队验证。

## 一、讨论目标

本轮要解决的不是“文件放在哪里”这么简单，而是四个对象如何同时成立：

- 一个工作区能否容纳多个工程；
- 一个工程能否拥有多个代码仓库和外部资源；
- 多个 Agent 或工程如何安全地修改资源；
- 文件和外部资源发生变化时，任务责任如何继续保持清楚。

## 二、第一轮独立意见

### 用户体验与产品边界意见

用户做真实项目时，前端、后端、文档、设计和部署资料经常不是一个目录。如果产品把工程强行等同于一个文件夹，用户会被迫拆出多个工程，PM 也会失去整体目标。

体验侧支持以下方向：

- 一个工作区可以有多个工程；
- 一个工程可以关联多个资源；
- “主资源”只作为打开工程时的默认入口；
- 用户只需要看到“这个任务要改哪个资源”，不需要理解资源绑定的内部对象；
- 共享资料可以被多个工程引用，但默认不产生写入责任。

体验侧最担心的风险是：如果用户必须手动配置每个资源、每个目录和每个 Agent，Magic 会退化成资源管理后台。因此系统应根据任务自动带出候选资源，只有出现歧义或风险时才让用户选择。

### 资源、竞品与安全意见

竞品通常把工作区、项目、代码仓库、工作树和任务执行环境分开；公开资料更能证明“任务输入、文件产物、分支或工作树交接”，不能证明多个会话天然互读。

资源侧支持：

- 产品层使用统一的资源身份和工程资源关联关系；
- 本地目录、Git 仓库、URL、数据库和 API 使用不同的类型和能力字段；
- 同一资源可被多个工程引用，但引用关系必须分别授权；
- 写入责任要落到具体任务/执行范围，而不是只落到工程名称；
- 同一资源重叠范围不能同时有多个默认写入者；
- 资源失联或版本变化不能被自动解释为任务完成。

资源侧最担心的风险是：只在界面上显示“隔离”，但底层 Agent 仍能任意读写同一目录；或者为了多资源自由，允许多个任务静默覆盖同一文件。

## 三、交叉质询后的共识

### 1. “一个主资源”不能是工程上限

双方一致认为，一个项目拥有前端、后端和文档仓库是正常情况。更准确的产品规则是：

> 工程可以关联多个资源；主资源只是默认入口。每次具体任务必须明确目标资源和写入范围。

例子：

```text
工程：Magic 产品
主资源：Magic 前端仓库
附加资源：Magic 后端仓库、产品文档仓库、设计资料、部署服务
当前任务：只修改前端仓库的登录页面
```

用户看到的是“项目资源”列表和当前任务目标，不需要看到 `ResourceBinding` 之类的术语。

### 2. 单一写入责任应该落在“资源范围 + 当前任务”

双方一致认为，“一个工程只有一个 Agent 能写”太粗，“所有 Agent 随便写”太危险。

建议的产品语义是：

```text
同一资源
+ 重叠写入范围
+ 同一时间
= 只能有一个当前写入责任主体
```

不同资源、不同目录或不重叠路径可以并行。多个工程可以只读引用同一资源；如需写入，必须建立明确的任务授权、写入范围和冲突处理关系。

底层可以采用工作树、补丁、锁、变更集或其他机制，但具体技术方案仍需核查。

### 3. 外部资源可以统一登记，但不能假装能力相同

双方接受统一的 `Resource` 产品抽象，但必须保留资源类型差异：

- 本地文件夹有路径、读写范围和文件变更；
- Git 仓库有远端、分支、提交和同步状态；
- URL 有访问状态和内容快照；
- 数据库/API 有连接方式、操作动作、凭据引用和副作用等级；
- 云文档或设计平台有版本、编辑权限和发布动作。

统一身份便于工程关联和审计，类型能力差异用于权限、成本、同步和风险判断。

### 4. 资源变化不应直接改写任务结果

文件移动、删除、目录失联、远端版本变化、凭据过期和同步失败，都应保留底层事实并通知任务责任人。

默认行为是进入等待或阻塞，说明：

- 哪个资源发生了什么变化；
- 哪些任务受到影响；
- 当前谁负责处理；
- 可以重试、切换资源、调整范围还是重新规划。

不能因为文件消失或运行结束，就自动把任务标为失败或成功。

## 四、用户确认后的首版规则

用户确认 U-10 首版采用：

1. 一个工作区允许多个工程。
2. 一个工程允许一个默认主资源和多个附加资源。
3. 附加资源可以是本地目录、代码仓库、文档、URL 或外部服务，但类型能力分别治理。
4. 每个任务必须明确目标资源、读写动作、范围、当前责任人和预算/副作用边界。
5. 同一资源的重叠写入范围在同一时刻只允许一个当前写入责任主体。
6. 其他工程可以只读引用共享资源；跨工程写入首版默认禁止，除非后续另有明确产品裁定和技术方案。
7. 资源移动、删除、失联、同步失败和并发冲突不自动结束任务，进入等待、阻塞或待决策状态。
8. 用户界面用“项目资源”“本次任务修改范围”“正在由谁修改”表达，不要求用户管理底层绑定和锁。

## 五、后续需要技术方案或增量裁定的问题

- 首版多个可写资源的技术实现和任务级启用方式；
- 自动发现任务目标资源后，哪些歧义必须让用户选择；
- 资源版本冲突时，独立变更集、人工处理和自动检查的组合方式；
- 非 Git 资源的快照、锁、版本或补偿机制；
- 自动合并的低风险条件，以及合并后测试和回退要求。

## 六、技术核查清单

- Magic 工程、资源和关联关系的稳定 ID；
- OpenCode 工作区、Git 分支/工作树和工具路径权限；
- 多资源并发读写和重叠范围冲突检测；
- 文件移动、删除、外部资源失联和远端变更事件；
- 资源类型差异化的凭据、审批、预算和副作用拦截；
- 任务、Attempt、Agent 和资源写入责任的最终收敛；
- 资源版本、变更集、产物引用和恢复后的审计。

## 七、主持人结论

U-10 的核心不是限制用户拥有多少文件夹，而是让 Magic 在资源变多时仍然回答清楚三句话：

```text
这个项目关联了哪些资源？
这项任务现在要改哪个资源、哪个范围？
如果发生冲突，谁对这次写入负责？
```

本记录建议把“主资源”从硬性数据模型降为用户体验入口，把“单一写入责任”从工程级限制收敛为资源重叠范围和当前任务级责任。最终是否采用，等待用户确认。
