# U-01 / U-02 三方对齐：外部评估员回应

## 一、立场

我确认产品经理提出的六项共识：U-01 是对象与关系模型，U-02 是责任治理规则；画布只能是 Magic 任务账本的投影；唯一责任人不等于唯一执行者、派发者或结果接收者；失败、重试、断连和下级失败不自动转移责任；PM 不应成为所有任务的同步审批瓶颈；首版只预留关系和稳定标识，完整画布后延。

我的挑战集中在一个点：**“唯一当前责任人”必须是可持续的收口责任，而不能被实现成一个需要持续在线、亲自执行或逐项批准的操作角色。** 只要这一点写清，U-02 不会把用户变成责任管理员，也不会把 PM 变成串行调度器。

## 二、逐条回应

### 1. “当前责任人”的定义

是。建议定义为：

> 当前责任人是被明确授予任务收口责任的主体，负责根据可追溯证据，让任务最终形成一个诚实、可解释、可恢复的状态，并说明已有结果、未完成事项、阻塞原因和已发生副作用；他不必亲自执行任务，也不必成为所有协作者的派发者或所有结果的接收者。

这里的“形成状态”包括已完成、部分完成、失败、等待、已停止和已取消，不只包括成功。责任人可以把执行委派给成员或临时 Agent，但不能把最终状态的解释责任隐式转给运行实例、工具结果或下级 Agent。

需要补充两个边界：

- 责任人是任务级角色，不是永久在线进程；成员空闲、断连或当前没有运行，不代表责任自动消失。
- 责任人不等于批准人。审批权应由权限和副作用策略决定，不能由“当前责任人”这个字段自动推导。

### 2. 等待时是否保留责任

原则上保留。任务等待用户输入、等待依赖、等待审批或被策略阻塞时，当前责任人仍然保留，除非发生显式责任移交。这样可以保证等待期间仍有人负责解释任务为何没有继续，以及下一步需要什么。

但“保留责任”不能成为悬空任务的借口。每个等待状态至少要记录：

- 等待类型：用户输入、依赖、审批、策略、外部系统或资源；
- 等待对象和具体问题；
- 解除条件和下一步动作；
- 进入等待的时间、最后更新时间和最近一次证据；
- 超时或无人响应后的升级目标。

建议把 `waiting` 作为任务状态，把 `waiting_reason`、`waiting_on`、`resume_condition` 作为强制字段。阻塞不应被显示成“运行中”，也不应被包装成失败或完成。

为避免任务长期悬空，首版应支持以下机制：

1. 责任人可以主动标记等待并给出解除条件；
2. 系统根据等待时长和类型提出升级或移交建议；
3. PM、用户或具备授权的上级责任人可以发起显式移交；
4. 在移交完成前，原责任人仍是责任人，任务可暂停执行但不能进入无人负责状态。

### 3. “建议移交”与不同异常情形

系统可以提出建议，但不能仅凭运行状态自动改变责任。建议移交的触发条件可以包括：负责人停用、长期断连、重复失败、等待超时、明确拒绝接手或任务范围发生重大变化。建议本身必须带理由和证据，不是隐式状态变更。

不同情形的处理建议如下：

| 情形 | 系统行为 | 责任变化 |
|---|---|---|
| 负责人停用 | 立即标记“需要处理”，冻结新的派发；通知 PM/用户并提出候选接手者 | 不自动转移，显式移交后生效 |
| 长期断连 | 展示最后更新时间和同步缺口；达到策略阈值后提出升级/移交建议 | 原责任保留，直到授权主体确认移交 |
| 负责人拒绝接手 | 记录拒绝原因；任务进入待重新派发或等待决策 | 不得强行把责任写给未接受者 |
| 超时未响应 | 按等待类型通知责任人和 PM；可升级给用户 | 不因超时自动转移；授权主体可显式接管 |
| 运行失败或重试 | 保留原责任人；创建新的 `TaskAttempt` | 不转移 |

“接手确认”不应成为新的死锁点。建议允许 PM 或用户在有权限时直接完成带审计的移交；新责任人可以在接手后标记无法执行并再次显式移交，但系统不能把任务留在“已指定但无人接受”的半状态。

### 4. PM 通知与 PM 审批

两者必须是不同事件：

- **通知**：让 PM 知道工程计划可能受到影响，由成员或系统异步提交；不阻止成员继续执行。
- **审批/决策**：只有在变化超出成员授权范围或会改变工程取舍时才需要 PM（或用户）作出明确决定；在决定前，相关动作暂停。

成员通常可以自行推进：

- 已分派任务范围内的分析、编码、测试和可逆修改；
- 不增加预算、不扩大目录/网络/权限范围的常规操作；
- 不改变工程目标、优先级和对外承诺的局部方案选择；
- 对自己任务的重试、降级和部分交付，只要副作用策略允许。

需要 PM 决策或用户确认的变化包括：

- 改变工程目标、范围、优先级、里程碑或交付承诺；
- 新增或取消跨任务依赖，造成其他任务重排；
- 修改共享事实、项目级架构取舍或验收标准；
- 扩大资源、预算、权限、目录、网络或外部服务范围；
- 发布、部署、付费、删除或其他难以撤销的副作用；
- 成员之间发生文件/资源冲突且无法在本任务范围内解决。

PM 的角色是计划和风险的决策入口，不是每个工具调用的审批代理。底座工具审批和 Magic 策略审批也不能被“PM 已收到通知”替代。

### 5. U-01 是否保留额外字段

应保留，但分为“关系审计字段”和“画布展示字段”，避免把所有内部字段都变成视觉节点。

关系和任务至少应保留：

- 等待原因、等待对象和解除条件；
- 最后更新时间、事件新鲜度和同步状态；
- 关系来源、创建者、时间和适用范围；
- 撤销、替代或结束记录；
- 当前责任人、派发者、执行者和结果接收者的独立标识；
- 运行尝试、产物、事实和副作用的来源关联。

首版画布不必全部常驻展示。默认只显示任务、成员、责任人、当前状态、阻塞/等待摘要和产物；其余字段在详情、审计或关系检查面板中按需展开。

这些字段的目的不是增加管理工作，而是防止用户把“没有新事件”误认为“仍在运行”，把“结果交付给 PM”误认为“PM 对成员任务负责”，或把“底层 Session 有 parent”误认为 Magic 已建立派发关系。

### 6. 建议的 U-02 最终白话表述

> **每个正式任务在任何时刻都明确一个当前责任人。当前责任人不一定亲自执行，也不一定负责派发或接收所有结果；他负责汇集证据，并让任务最终形成一个诚实、可解释、可恢复的状态。任务等待输入、依赖、审批或策略处理时，责任人仍保留，系统必须说明等待什么、等待谁以及如何继续。失败、停止、断连、重试和下级失败不会自动改变责任。责任只有在获得授权的主体进行显式移交并记录原因、已有结果、未完成事项、待审批项和已发生副作用后才会改变。**

这段表述覆盖普通代理、CEO、工程成员、用户直达成员和临时 Agent，同时保留了 U-02 的核心约束。

## 三、首版必须验证的最小场景

首版不需要完整团队画布，但必须用任务账本和最小投影验证以下闭环：

1. **普通代理委派**：会话主 Agent 是任务责任人；临时 Agent 执行局部工作并回报；运行结束后责任仍由主 Agent 收口，临时 Agent 不成为长期成员。
2. **工程派发**：PM 派发成员任务；成员是成员任务责任人；PM 负责计划和汇总，但不成为成员任务责任人。
3. **等待与解除**：任务分别进入等待用户输入、等待依赖和等待审批；责任人不变；界面显示等待对象、解除条件和最后更新时间；解除后可继续同一任务。
4. **失败与重试**：一次运行失败后创建新的 `TaskAttempt`；任务责任人、已有产物和副作用记录保持不变；重试成功后由责任人形成最终状态。
5. **停用/断连/超时**：责任人停用或长期无事件时，系统提出移交建议并通知 PM/用户；在显式移交前不得自动改写责任；授权主体完成移交后，新责任人可继续未完成部分。
6. **用户直达成员**：用户给成员的新工作写入工程账本，由成员承担该任务责任；若影响目标、资源、依赖或交付，PM 收到通知并作计划判断，但普通执行不必等待 PM。
7. **跨任务依赖**：下游任务在依赖未满足时保持原责任人并进入明确等待；系统能识别循环依赖，向 PM/用户升级，而不是自动转移责任。
8. **画布真实性**：成员节点不被显示为永久在线进程；运行结束、断连和同步缺口可见；关系来源和撤销记录可追溯；画布没有独立的状态修改真相源。

## 四、最终建议

U-01 和 U-02 不需要撤回，但首版需要做三项调整：

1. 把责任人的定义从“谁在做”改成“谁负责让任务诚实收口”；
2. 把等待、超时、停用和移交写成明确的生命周期契约；
3. 把画布字段分成默认展示字段和审计字段，避免形成管理后台或实时运行错觉。

首版的 Go 条件不是“画布能画出多少节点”，而是：在等待、失败、重试、断连、直达成员和责任移交场景中，系统始终能回答谁负责、当前在等什么、下一步如何继续、哪些副作用已经发生，以及最终状态由谁作出解释。

本回应不修改 Magic 正式产品文档，等待产品经理继续确认。
