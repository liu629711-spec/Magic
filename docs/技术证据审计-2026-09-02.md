# Magic 产品文档技术证据审计

## 1. 目的和边界

本文件记录 2026-09-02 对 Magic 现行五份 PRD 中“可由参考源码验证”的技术陈述所做的审计结果。它不是第六份 PRD，不新增或改变产品语义，也不替代用户对产品取舍的确认。

参考源码只能证明候选底座当前做了什么，不能证明 Magic 应该做什么。PRD 中关于代理/CEO、工程、责任、权限和交付的设计，除非另有用户确认，均不能因标注“已确认产品规则”而被当成可由源码推出的结论。

### 1.1 审计口径

| 标记 | 含义 | 可否直接用于开发 |
| --- | --- | --- |
| `U` | 用户产品决策，源码不能证明 | 必须确认仍有效 |
| `S` | 当前参考源码可直接证明的事实 | 仅能作为候选底座事实 |
| `H` | 技术假设，需以锁定版本和实验验证 | 不能据此冻结设计 |
| `X` | 当前源码证实不准确或表述过强 | 必须修正或删除 |

## 2. 已确认的问题

### X-01 OpenCode 子代理权限不是“完整继承后再收紧”

受影响文档：已删除的 OpenCode 核心理解导航（历史导航文件）第 37 行。

`deriveSubagentSessionPermission` 只从父会话传递拒绝规则和外部目录规则；子代理是否能使用能力由子代理自身规则决定。任务工具随后再补充 `todowrite`、`task` 等拒绝项。不能将其描述成完整父权限集合的衰减继承。

源码证据：`reference-project/opencode/packages/opencode/src/agent/subagent-permissions.ts:5-26`，`reference-project/opencode/packages/opencode/src/tool/task.ts:139-172`。

影响：Magic 不能把 OpenCode 子代理权限逻辑直接当作“最小转授权”实现；Magic 若要保证该产品规则，必须在自身适配层维护授权上限与派发范围。

### X-02 OpenCode 没有已确认可绑定的第一方 `Run` / `TaskAttempt` 对象

受影响文档：[PRD-01](01-产品/PRD-01-Magic产品总览.md) 第 228 行、[PRD-04](01-产品/PRD-04-任务执行与治理.md) 第 159 行。

对锁定 OpenCode 工作树的 CodeGraph 查询未发现 `RunV2` 或 `TaskAttempt` 领域对象。当前实现同时存在 V1 的进程内 `SessionRunState` 和 V2 的 `SessionExecution` / `SessionRunner` 协调结构；它们不能在未实验前被等同为 Magic 的一次执行尝试。

源码证据：`reference-project/opencode/packages/opencode/src/session/run-state.ts:27-149`，`reference-project/opencode/packages/core/src/session/execution/local.ts:1-40`。

影响：Magic 应把 `TaskAttempt`、运行状态和绑定记录定义为自身对象；与底座的关联应暂时表达为“Session、输入/消息、事件、进程执行状态的可审计引用”，不可预设一对一 `Run` 映射。

### X-03 OpenCode 不是所有入口都走一条 V2 执行链路

受影响文档：已删除的 OpenCode 核心理解导航（历史导航文件）第 43-68 行。

当前 HTTP 会话处理器仍依赖 V1 `SessionPrompt` 与 `SessionRunState`；子代理工具也通过 `TaskPromptOps.prompt` 调用提示服务。V2 耐久输入与执行协调器确实存在，但当前不应画成 CLI、TUI、Web、Desktop、ACP 全部统一进入的唯一已验证主链路。

源码证据：`reference-project/opencode/packages/opencode/src/server/routes/instance/httpapi/handlers/session.ts:1-61`，`reference-project/opencode/packages/opencode/src/tool/task.ts:197-224`。

影响：F-10 的首项不是“锁定某个 Run”，而是锁定 Magic 实际调用的入口、协议、会话版本和事件来源。

### X-04 AgentCore 的审批和恢复不是可无条件继承的生产保证

受影响文档：已删除的 AgentCore 核心理解导航（历史导航文件）第 77、85 行。

AgentCore 的审批门可由配置关闭；当前审批协调明确是单 worker、进程内状态，进程或 lease 恢复后旧审批会成为 `ORPHANED`。已完成 worker 的会话复用有进程级注册表，也有默认开启的 `RunSession` 持久化与按 miss 恢复路径；但该持久化写入是 best-effort，失败会退化为内存行为。结构化暂停持久化同样默认开启，但其保存失败会显式报错。不能将这些路径表述为跨进程恢复的无条件生产保证。

源码证据：`reference-project/AgentCore/apps/server/agentcore/runtime/approvals.py:1-16`、`89-101`，`reference-project/AgentCore/apps/server/agentcore/runtime/session_persistence.py:1-17`、`62-91`，`reference-project/AgentCore/apps/server/agentcore/config/persistence.py:7-13`，`reference-project/AgentCore/apps/server/agentcore/conversation/turn_runner.py:38-58`，`reference-project/AgentCore/apps/server/agentcore/runtime/suspension/persistence.py:58-104`。

影响：AgentCore 可以作为任务图、审批交互和审计设计的参考。Magic 仍须自行验证断连、重启、审批恢复与最终一致性，尤其应覆盖持久化写入失败、重新领取 lease 与遗留审批的场景。

### H-01 AgentCore 的执行者不是 Magic 长期成员模型的证据

AgentCore 的当前 `RunSpec` 在阶段一直接携带角色、目标和工具；源码明确说明此阶段没有独立 Agent 实体。它能证明一次会话可运行多个角色化执行节点，不能证明存在可跨任务复用、授权和治理的长期项目成员。

源码证据：`reference-project/AgentCore/apps/server/agentcore/runtime/runs/types.py:1-14`。

影响：PRD-03 的 PM、项目成员和成员生命周期是 `U`，需要用户确认后由 Magic 自建，不能继承 AgentCore 对象。

## 3. 五份 PRD 的当前分类

| PRD | 当前可保留的内容 | 必须重新确认或取证的内容 | 当前结论 |
| --- | --- | --- | --- |
| PRD-01 产品总览 | 产品愿景、用户问题、术语和边界均为 `U` | OpenCode `Session/Turn/Run` 映射为 `X/H`；首版技术闭环为 `H` | 不可作为技术设计输入直接实现 |
| PRD-02 代理与 CEO | 模式平等、建议非阻塞、切换体验均为 `U` | 会话复用、运行中切换、断连补齐、成员复用均为 `H` | 可保留为待确认产品草案 |
| PRD-03 工程组织 | 工程、PM、长期成员、唯一责任人均为 `U` | worktree 并发、成员隔离、PM 接管和冲突收口均为 `H` | 不能从 AgentCore 或 OpenCode 直接继承实现 |
| PRD-04 任务治理 | Task、Attempt、Artifact、验收规则是 `U` | OpenCode Run 绑定为 `X/H`；事件重放、重启恢复和 F-10 场景为 `H` | 必须重写技术准入，而非直接执行 F-10 |
| PRD-05 权限成本 | 三档授权、预算四数、事实与副作用规则均为 `U` | 底座的授权拦截、成本计量、凭据隔离、撤销、生效范围和副作用审计均为 `H` | 只能作为 Magic 自建治理目标 |

`U` 不表示内容错误，只表示正确性只能由用户意图决定。`H` 不表示底座不支持，只表示当前尚无锁定版本、调用入口和可复现实验足以证明 Magic 可以依赖它。

## 4. 可由源码确认的候选能力

| 候选能力 | 参考项目事实 | 对 Magic 的限制 |
| --- | --- | --- |
| OpenCode 子代理 | 会创建带 `parentID` 的子会话，可前台执行；后台子代理受实验开关控制 | 不是长期成员或权限衰减机制 |
| OpenCode 会话事件与同步 | V1 会话处理器使用事件桥，HTTP 同步接口可处理带序列号的事件 | 不能据此推导 Magic Task 状态或断连收口 |
| AgentCore 协作任务图 | `CAPTAIN` 根运行可按需委派，`RunPlan` 与 `WaveScheduler` 支持依赖和并行 | 当前执行角色不等于可持久复用的成员身份 |
| AgentCore 审批交互 | 每回合可配置审批门，授权可覆盖本回合后续同类调用 | 当前为进程内机制，崩溃/恢复需单独验证 |
| DeepSeek Harness 会话日志 | Agent Loop 将用户、模型和工具事件写入追加式 Session Event Log | 仓库仍处于预发布阶段，不能把存储或协议兼容性当作产品承诺 |

## 5. F-10 的替代定义：底座取证，而非产品开发门禁

现有 F-10 不应以 `TaskAttempt ↔ OpenCode Run` 一致性为前提。替换为下列可重复的取证工作；每项都必须使用锁定提交、实际启动命令、输入、事件记录和结果。

1. 选定一个候选底座和一个实际客户端入口，确认其会话版本、输入投递方式、取消语义和事件协议。
2. 在该入口上验证一次低风险读操作、一次工作区写入、一次需要确认的动作和一次子代理调用，记录可观察的对象 ID 与事件序列。
3. 验证客户端断开、服务进程重启、重复或乱序事件、取消与重试；不能恢复时明确记录缺口，而不是推定成功。
4. 确认费用计量、凭据、Git/worktree、MCP 与外部写入的真实接口和审计信息；未提供的能力列为 Magic 自建范围。
5. 仅当以上结果足以定义 Magic 的最小绑定模型时，再创建 Magic 的数据库、API 与状态机设计。

## 6. 后续决策顺序

1. 用户确认或撤销 PRD-01 至 PRD-05 中的 `U` 类产品规则。
2. 为每个仍需保留的产品规则写出所需的 Magic 自有对象、用户可见状态和验收证据。
3. 对每个 `H` 类底座假设建立最小实验，而不是预先设计适配器或表结构。
4. 实验完成后，将已证实的技术事实回写到对应既有 PRD 的“待技术核查”位置；不新建平行 PRD。
