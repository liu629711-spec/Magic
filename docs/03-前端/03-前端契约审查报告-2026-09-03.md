1. **FZ-1/FZ-2（实质阻塞）**：Recovery Worker 默认每 30 秒自动对账所有活跃 Attempt，而源码的 `safe_reconciled_status` 对任何无终态证据的观察一律落 `unknown_after_restart`，OpenCode 适配器对仍在运行的会话返回的正是 `UnknownAfterRestart`——三者叠加，**每个正常运行超过一个 Worker 周期（≤30 秒）的 Attempt 都会被自动改写为"重启后状态未知"**，且此后无人补写终态。C-4 的"10 分钟阈值"与前端 §6.6 轮询模型的前提不成立。需后端决议修复方向 + 产品判定体验红线。
2. **FZ-3（一行修订）**：事件查询 `confirmed_seq` 若按方案 §6.5 对齐 `event_cursor`，则恒为 0（该表只被 OpenCode 聚合推进），字段失效；需固定定义。
3. **FZ-4（一行修订）**：Task 列表 `items` 投影字段未定义，任务列表是阶段 1 第一个界面，DTO 无法编写。

## 二、必须修订的结论

### 2.1 C-4 + 方案 §6.6/§9.10/S13：`unknown_after_restart` 的进入前提与源码根本冲突 【阻塞冻结；阻塞阶段 1 的工作台语义】

- **原结论**：C-4"启动时逐个提示 + 活跃超过 10 分钟才显示对账建议"；S13/§9.10 把 unknown 归因为"无 binding 或对账失败"。
- **问题**：源码中 Recovery Worker 默认每 30 秒对**所有** `admitted/running/cancelling` Attempt 自动对账（`apps/local-service/src/main.rs:74-94`，默认 `30_000ms` 见 `:79-83`；对账循环 `crates/reconciliation/src/lib.rs:114-142`），而 `safe_reconciled_status` 对任何无终态证据的观察一律落 unknown（`crates/application/src/lib.rs:222-240`，尤其 `:233-238`；`crates/reconciliation/src/lib.rs:153-171`）；OpenCode 适配器对**仍在运行**的会话返回的就是 `UnknownAfterRestart`（`crates/execution-opencode-v1/src/lib.rs:230-260`，`:254-258` 无 finish/completed 即 unknown，测试 `:454-458`）。三者叠加的必然结果：**每个正常运行超过一个 Worker 周期（≤30s）的 Attempt 都会被自动改写为 `unknown_after_restart`**，且此后 Worker 不再处理它（`active_attempts` 只查三活跃态，`crates/persistence/src/lib.rs:214-215`），即使会话最终成功也没有人补写终态。OpenCode 短暂不可达同样触发（`crates/reconciliation/src/lib.rs:129` 把对账错误映射为 unknown）。文档"无 binding 或对账失败才 unknown"的归因与源码不符；C-4 的"10 分钟阈值"隐含"活跃态可存活 ≥10 分钟"，源码不成立。`crates/application/src/lib.rs:390-405` 的测试（对账无证据→unknown，event_seq=3）进一步证明这是现行语义而非偶然。
- **建议修改**：后端先收口"unknown 进入规则"的权威口径，至少满足"正常运行中、有 binding、会话存活的 Attempt 不得被周期任务自动转入 unknown"。可选方向（由后端定，前端不预设）：(a) Worker 仅启动时对账一次；(b) 周期任务只补拉 history、不翻状态；(c) 为 `ExecutionPort::reconcile` 增加可表达"仍在运行"的返回（需改端口）；或提出新方案。决议后回写 C-4 与方案 §6.6/§9.10。
- **对前端的影响**：工作台"进行中"区、unknown 卡数量、"需要你处理"区形态、轮询停止条件（§6.6"到达终态或 unknown 即停"）全部取决于此规则。若不修，用户看到的是：每个超过 30 秒的任务显示"重启后状态未知，需要你决定"，即使它最终执行成功。
- **是否阻塞阶段 1**：**是**（工作台与"需要你处理"区的核心语义）。

### 2.2 B-1 / 方案 §6.5：`confirmed_seq`、`next_cursor` 语义未定且与 `event_cursor` 实际作用域矛盾 【阻塞冻结；一行修订可解除】

- **原结论**：B-1 响应 `{events,next_cursor,confirmed_seq}`；方案 §6.5 称"`confirmed_seq` 概念对齐后端 `event_cursor.last_confirmed_seq`"，并将 `next_cursor` 回写为前端 `last_seq`。
- **问题**：`event_cursor` 只被 `Reconciler::ingest` 为 **opencode 聚合**推进（`crates/reconciliation/src/lib.rs:54-57`，调用点 `:100-108` 固定 `aggregate_type="opencode"`）；Magic 状态事件写入 `append_status` 从不触碰 `event_cursor`（`crates/persistence/src/lib.rs:237-282`）。因此 attempt 聚合在 `event_cursor` 中**永远没有行**——按 §6.5 的对齐口径，`confirmed_seq` 恒为 0，字段失效。
- **建议修改**：在 B-1 中固定：`confirmed_seq` = 服务端该 Attempt 聚合已落账的最大 seq（取法同 `crates/persistence/src/lib.rs:255-261` 的 `MAX(seq)`）；`next_cursor` = 本页最后一条事件的 seq，无更多数据为 null；并注明 `event_cursor` 仅是 OpenCode 外部事件续传的内部机制，前端不消费。同步修正方案 §6.5。另需补 `limit` 默认值与上限（建议默认 100）。
- **对前端的影响**：游标推进、追平判断、缺口检测（方案 §5.4）全部建立在这两个字段上。
- **是否阻塞阶段 1**：**是**——按 B-3 承诺，事件查询在阶段 1 开始前交付；修订本身是一行文本。

### 2.3 清单第 4 节第 2 条：Task 列表 `items` 投影字段未定义 【阻塞冻结；一行修订可解除】

- **原结论**：响应 `{items,next_offset,ordering}` + 排序与降级规则。
- **问题**：`items` 元素的字段集缺失。方案 §4.2 的列（任务标题、状态、责任人、当前 Attempt 序号与状态、最近事件 seq）与 §3 的 `TaskView` 都依赖它；且 `goal` 文本在 domain Task 上不存在（`crates/domain/src/lib.rs:156-162` 只有 `id/status/current_owner_id/acceptance_criteria_defined`），必须落到待建的 tasks 投影表。
- **建议修改**：固定 `items = [{task_id, goal, status, owner_id, current_attempt_no?, current_attempt_status?, last_seq}]`；时间戳列就绪前无 `updated_at`，排序一律读 `ordering`；`next_offset` 末页为 null。
- **对前端的影响**：任务列表/工作台是阶段 1 第一个界面，字段不定则 DTO 与 mock 服务无从写起。
- **是否阻塞阶段 1**：**是**（一行修订解除）。

### 2.4 第 12/14 条："能力未接入"的线上形态未定 【不阻塞阶段 1，冻结文本必须补】

- **原结论**："未接入时返回能力未接入而非空冒充无证据"。
- **问题**：未定 wire 形态（501+`{error}` 还是 200+`{available:false}`）。第 13 条成本已用 `{available:false,...,source}`，同类能力不统一则方案 §11 的 Empty 双文案（"无数据" vs "能力未接入"）无法稳定映射。
- **建议修改**：统一 200 `{available:false, reason}`（与成本一致）；`artifacts/changesets/test-evidence/side-effects` 四个查询适用。
- **对前端的影响**：四态包装与区域级错误渲染。
- **是否阻塞阶段 1**：否（这些数据属阶段 3）。

### 2.5 `request_hash` 口径补全 + 方案 §6.4 与 B-5 同步 【不阻塞阶段 1】

- **原结论**：B-5 冻结派发口径 `SHA-256(task_id ␟ attempt_no ␟ input ␟ directory)`；但第 7/8/11 条（cancel/resolve/complete）的 body 含 `request_hash` 未给口径；同时方案 §6.4 仍写"对 `(input, directory)` 规范化后哈希"，与 B-5 冲突。
- **问题**：服务端只做相等比较（`crates/application/src/lib.rs:76-77`），口径技术上自由，但前端需要唯一可复现的规范；§6.4 若不同步会直接写错哈希。
- **建议修改**：合并版 §6.2 按冻结口径书写；非派发写接口统一为"对排除 `idempotency_key` 后的规范化请求体做 SHA-256"，由后端确认。
- **对前端的影响**：`api/ids.rs` 实现；写错即触发 409 幂等冲突。
- **是否阻塞阶段 1**：否（阶段 2/3 的写路径使用）。

### 2.6 取消语义两处收口 【不阻塞阶段 1；可用性矩阵属本次冻结范围】

- **原结论**：B-2"仅 `running` 可发起，终态返回当前状态"；方案 §4.4 状态表把"取消"列为 `admitted` 态可用操作。
- **问题**：① domain `request_cancel` 仅允许从 `Running`（`crates/domain/src/lib.rs:83-89`），§4.4 的 `admitted` 行与源码冲突，`admitted` 应为 409 非法状态；② "终态返回当前状态"未定状态码/`reused`/`event_seq`。
- **建议修改**：从方案 §4.4 `admitted` 行删除取消操作；契约补一句：终态（`succeeded/failed/cancelled`）调用返回 200 `{attempt_id, status:<终态>, event_seq:null, reused:true}`；`created/admitted/cancelling/unknown_after_restart` 一律 409（unknown 不可取消，测试 `crates/domain/src/lib.rs:299-307` 佐证）。
- **对前端的影响**：操作按钮可用性矩阵与 409 分支文案。
- **是否阻塞阶段 1**：否（取消接口阶段 3 接入，但矩阵现在就要冻结）。

### 2.7 Task 状态推进归属未写 【不阻塞阶段 1；阶段 2/3 前必须补】

- **原结论**：15 条契约中没有任何一条定义 `proposed→ready→in_progress→awaiting_review` 由谁触发（domain 已有迁移规则，`crates/domain/src/lib.rs:190-222`）。
- **问题**：第 11 条 complete 依赖 `awaiting_review`，但"谁把 Task 推进到 awaiting_review"未定义；前端无法解释状态变化的来源，也无法判断是否需要轮询等待。
- **建议修改**：契约补一句"Task 状态推进由服务端用例自动执行（创建→proposed/ready；派发→in_progress；Attempt 落 succeeded→awaiting_review），不提供独立状态推进 API，前端永不调用"（具体时机由后端确认）。
- **对前端的影响**：阶段 1 只读渲染不受影响；§9.9 横幅与 §9.8 验收按钮的语义解释依赖它。
- **是否阻塞阶段 1**：否。

### 2.8 方案文档同步项（低风险，随冻结一并改） 【不阻塞】

- 方案 §6.2 事件查询的 `?source=opencode` 应更正为 `source=opencode-v1`（源码实际写入值，`crates/reconciliation/src/lib.rs:105`）；
- 方案 §6.5 的 `event_cursor` 对齐表述按 2.2 更正；
- B-7 与清单第 15 条字段重叠（`protocol_version`/`worker` 两处出现）：声明 `service-info` 为能力发现权威、`/health` 仅存活+可选诊断；`cursor_watermark` 指明是 OpenCode 侧水位（`event_cursor`，`crates/persistence/src/lib.rs:86-92`、`:482-504`），前端不消费其 attempt 语义；

### 6.2 待实现接口（冻结候选，按《前端契约确认清单 2026-09-02》确认结果合并）

除 §6.1 三个已实现接口外，本节全部接口均为【待实现】。现状基准：路由仅 `GET /health`、`POST /api/tasks/{task_id}/attempts`、`POST /api/tasks/{task_id}/attempts/{attempt_id}/reconcile`（`apps/local-service/src/main.rs:106-115`）。实现前不得按已存在接口编码。

**通用约定**

1. **错误体**：统一 `{ "error": string }`；状态码沿用现有映射（409 幂等冲突/非法状态/无 binding、502 执行失败、500 存储，`apps/local-service/src/main.rs:208-229`）并扩展 400 参数、404 不存在/归属不符、401/403 传输层。
2. **幂等键与 request_hash**：派发接口二者的确定口径冻结为 `SHA-256(UTF-8(task_id + U+001F + 十进制 attempt_no + U+001F + input + U+001F + directory))`，空 directory 用空串（B-5；服务端仅做相等比较，`crates/application/src/lib.rs:76-77`、`crates/persistence/src/lib.rs:164-188`）。取消/收口/验收/计划等非派发写接口：`request_hash` = 对排除 `idempotency_key` 后的规范化请求体做 SHA-256（待后端确认，FZ-5）。
3. **事件游标**：`next_cursor` = 本页最后一条事件的 seq（无更多数据为 null）；`confirmed_seq` = 服务端该 Attempt 聚合已落账最大 seq（取法同 `crates/persistence/src/lib.rs:255-261`）。`event_cursor` 表仅服务 OpenCode 外部事件续传（`crates/reconciliation/src/lib.rs:54-57`、`:100-108`），**前端不消费**。查询不推进任何游标、不触发 reconcile。
4. **能力未接入**：统一返回 200 `{ "available": false, "reason": string }`，禁止返回空数组冒充"无数据"（与成本接口形态一致）。
5. **传输**：HTTP + `Authorization: Bearer <manifest 令牌>`；生产 CORS 白名单，开发模式经明确开关保留无令牌本机回退（B-4，开关命名待后端补记，FZ-9）。能力发现以 `GET /api/service-info` 为权威，`/health` 仅存活+可选诊断（B-7）。
