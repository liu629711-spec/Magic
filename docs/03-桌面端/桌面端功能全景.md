> **本文是什么**：对 Magic 当前全部功能的一次盘点，供桌面端界面设计使用。内容来自五份正式 PRD（`docs/01-产品/PRD-01` 至 `PRD-05`）、实现基线文档（`docs/02-实现/`）和插件源码（`plugins/`），每节标注出处。

## 1. 产品一句话与架构

**Magic 是建立在 DSH（DeepSeek Harness）之上的统一 AI 工作台**：DSH 提供 Agent 执行、工具、文件、终端、底层会话和运行能力；Magic 在其上建立用户可理解的工作方式、任务账本、责任体系、信息共享、权限治理和真实交付（PRD-01 §2）。

产品承诺："简单的事，直接做；复杂的事，组织做；长期的事，将来建成一支可持续工作的 Agent 团队。"（PRD-01 §2）

```
用户目标
   │
   ▼
Magic 产品层（自研 DSH 插件）────────────── 工作方式 / CEO编排 / 账本 / 记忆 / 治理 / 导出
   │                                          ▲
   ▼                                          │ 按DSH插件方式重做（不搬代码）
DSH 执行底座 0.1.5-rc.2 ── agent-team 服务 ──┘ 名册/信箱/任务板/崩溃恢复（官方 experimental）
   │
   ▼
会话 · 工具 · 文件 · 终端 · 存储 · 工作区
```

- 架构出处：`AGENTS.md`、`README.md:3`、PRD-01 §5。
- **Magic 不重写** DSH 的 session、tool、agent-loop（`AGENTS.md` 当前架构节）。

## 2. 当前运行形态与桌面端的关系

当前产品以 **DSH web profile + 插件 overlay** 形态运行（`patches/web.patch.yml`）：

```sh
node scripts/start-web.mjs
# 等价于：dsh web --patch /abs/path/to/Magic/patches/web.patch.yml --no-open
# 打开 http://127.0.0.1:3080
```

overlay 分两层加载（`patches/web.patch.yml`）：

1. **官方 Agent Teams 层（experimental，形态 A'）**：只挂官方"服务 + 面板"（名册 / 持久信箱 / 任务板 / 崩溃恢复），**不挂官方 Team 工具**（避免每个普通会话都看到 9 个 Team 工具）。
2. **Magic 产品插件层**：work-mode / ledger / memory / consult / devtools / export / ceo / ceo-ui。
3. **vendored 社区插件层**：共享浏览器、侧边聊天、提示词优化、汉化、侧边栏工作台、Univer Office。

**桌面端已有的两个明确裁定**（做桌面 UI 时直接生效）：

| 裁定 | 内容 | 出处 |
|---|---|---|
| 通知归桌面端 | 浏览器通知**不做浏览器内实现**，整体归入桌面端阶段。设计基线：两个触发点（"CEO 拍板抽屉挂起等你""成员任务完成/失败"）、信噪纪律（只送"哪条会话/哪个成员 + ≤120 字标题"、窗口失焦才提醒）、点击跳回对应成员工作区 | `docs/02-实现/07-体验对标调研.md` §3.1 |
| 浏览器内嵌 | 共享浏览器在 web 形态由插件自托管 Electron 窗口；**桌面端把 `electronViewHost` 接上即变成产品内嵌浏览器面板，语义不变** | `patches/web.patch.yml`（browser-electron 节）、PRD-02 §18.1 |

**历史说明**：旧 Rust/Tauri 桌面栈归档在 `old-design` 分支，只用于追溯（`README.md:5`）。本仓 `apps/desktop/` 目录是本地 gitignore 残留构建产物，**不代表当前实现**。

## 3. 领域词汇表（界面文案必须统一）

出处：`CONTEXT.md`、PRD-01 §16。

| 词汇 | 含义 | 界面上不要说成 |
|---|---|---|
| 项目（Project） | 产品侧容器，管理多个工作区和会话 | Agent 的工作目录 |
| 工作区（Workspace） | 项目下的本地工作目录，Agent 读写运行文件的地方 | 项目、工程 |
| 会话（Session） | 围绕一项连续工作的交流和执行现场 | 运行、任务 |
| 任务（Task） | 有目标、责任人、验收标准和最终结果的一项工作 | 消息、回合 |
| 计划步骤（Plan Step） | 任务中的普通执行步骤，不一定有独立 Agent 或交付 | 子任务 |
| 子任务（Child Task） | 需要独立责任、交付、验收、等待或依赖的任务 | 计划步骤 |
| 执行尝试（Attempt） | 针对一个 Task 实际发起的一次执行；重试产生新 Attempt | 回合、Session、Run |
| 执行底座（Execution Base) | 提供 Agent 运行能力的外部运行时（当前为 DSH） | Magic 产品层 |
| 代理（Agent mode） | 当前会话主 Agent 直接理解、计划、执行、验证、交付 | — |
| CEO（CEO mode） | 主 Agent 显式组织协作、依赖、汇报和统一交付 | 永久组织、工程 |
| 工程（Engineering） | 用户确认后建立的长期组织（**暂缓**） | CEO 模式的别名 |
| 产物（Artifact） | 用户可访问、验证并使用的交付结果 | 回复、输出 |
| 事实（Fact） | 项目认可、带来源和版本的可复用信息 | 记忆、摘要 |
| 副作用（Side Effect) | 文件写入、命令执行、费用、网络请求、发布等真实影响 | 普通消息 |
| 验收（Acceptance） | 责任人依据预定标准和证据确认 Task 完成 | 模型成功、请求成功 |
| 状态未知（Unknown） | 证据不足以判断结果的诚实状态 | 空闲、异常、失败 |
| 幂等键（Idempotency Key) | 一次有副作用请求的稳定标识，防重复执行 | 底层消息 ID |

## 5. 分模块功能详解

### 5.1 工作方式（代理 / CEO）— `magic-work-mode`

**是什么**：每个会话有两种平等的工作方式（PRD-02 §1.1）。代理 = 主 Agent 直接干；CEO = 主 Agent 组织成员协作。两者可组合切换，不改变权限。

**规则要点**（PRD-02）：

- 三种操作作用域必须区分（§4）：代理内部调协作者（不改模式）/ 单次输入启用 CEO（`once`）/ 修改会话默认方式。
- 默认值优先级（§8）：**当前输入临时选择 > 当前会话默认 > 工程/工作区默认 > 账户默认 > 系统默认（代理）**。
- 切换前必须显示（§5/§15.3）：目标、未完成任务、当前责任人、在飞运行、已产生副作用、成员关系、可/不可继承上下文；CEO→代理切换有交接确认（`plugins/magic-work-mode/src/handoff.ts`）。
- 系统建议永远非阻塞：采用 / 稍后 / 不再建议（§15.1）。

**实现面**（源码：`plugins/magic-work-mode/src/`）：

- 命令 `/mode [agent|ceo|once agent|once ceo]`（`src/index.ts:238`）。
- UI：composer 左侧模式 chip（slot `conversation.input.left`，order 0，`src/client/register.ts:83`）；会话中"模式已变更"卡片（slot `conversation.chat.node`，key `magic-work-mode-changed`）。
- 按当前模式注入系统提示 section `magic-work-mode`（order 250）。
- 服务缝：`ctx.provide('magicWorkMode', { getMode, getState })`，被 memory / consult / ceo 消费。

### 5.2 CEO 编排核心 — `magic-ceo` + 官方 agent-team

**是什么**：用户把目标交给主 Agent，由它拆工作包、派成员、收结果、统一交付（PRD-02 §10）。成员是完整 Agent 会话，不是弱化工具。

**三个模型工具**（`plugins/magic-ceo/src/index.ts:1205,1286,1427`）：

| 工具 | 作用 |
|---|---|
| `ceo_plan` | 记录 CEO 分析与拟派 run graph；复杂任务必须先 plan 再 delegate（fingerprint 校验一致） |
| `ceo_delegate` | 派发 tasks[] 运行图（role + task + depends_on + contract）；独立节点并行、依赖就绪才启动；成员自报 trailer + 账本物证复核可推翻"自述达标" |
| `ceo_replan` | 对已开图做 binds / steers / add / continue / replace / halt / redirect / resume / stop |

**复杂任务前置规划**（PRD-02 §10.1）：≥3 个工作包、有依赖、多来源调研、多专业判断统合——必须先在会话中给出"CEO 分析与派发计划"（目标摘要、分析、共享简报、任务图），计划可回放、修订留版本。简单任务不阻塞。

**成员生命周期**（PRD-02 §14）：临时 Agent（默认不保留）→ 会话成员（明确复用）→ 项目成员（用户确认入工程，暂缓）。

**半改道**（`docs/02-实现/05-CEO派活改道映射.md`、00-基线 §4）：官方名册在场时成员经 `spawnTeammate` 派出、steer 走官方持久信箱、halt 走官方 interrupt；官方缺席/异常回退 `ctx.subagents`。容量 `maxMembers: 32`。

**状态持久化**：`magic_ceo` 存储域 v1（layout single），tables `members / plans / usage / channels`（`src/store/ceo-domain.ts:107-119`）；同时写 session 事件日志（`CEO_PLAN`、`CEO_RUN_JOURNAL`、`CEO_RUN_PROGRESS`、`CEO_RUN_PHASE`、`CEO_RUN_PROCESS`、`CEO_MEMBER_RESULT/USAGE/CONTEXT/HALTED/REDIRECTED`，`src/journal.ts`）——崩溃重启可恢复。缺 storageDomain 时降级内存端口（`src/store/memory-port.ts`）。

### 5.4 交付契约与验收账本 — `magic-ledger`

**是什么**：把"成员说完成"变成"有落盘物证的完成"。验收绝不读成员自由文本（PRD-04 §1、§5）。

- 工具 `ledger_record_evidence`：worker 落盘自报物证（landed_paths / sections_produced / citations）。
- 工具 `ledger_verify`：基于契约 + 物证 + 地面事实做验收。
- 存储：`magic_ledger` 域 v1（layout per-record），tables `contracts` + `evidence`（`plugins/magic-ledger/src/index.ts:24-32`）；id 强制 path-safe。
- 服务缝：`ctx.provide('magicLedger', { putContract, getContract, latestEvidence, verify })`；事件 `magic:ledger:evidence-recorded / verified`。
- **UI 含义**：验收状态/物证目前经 CEO 会话与画布透出；桌面端若做"交付页"，数据源即此域。

### 5.5 记忆 — `magic-memory`

**是什么**：跨回合、跨会话的项目记忆，按角色可见性分发（PRD-01 §8）。

- 工具：`magic_memory_search`（按 audience/layer/tags/自由文本检索；member 看不到 CEO 私有记忆）、`magic_memory_record`（写入；layer: episodic/semantic/user/rule；audience: ceo/member）、`memory_consolidate`（把 `topic:<name>` 散记合并为一条 semantic 主题笔记）、`memory_maintain`（清理超龄争议记录 + 统计）。
- 常驻注入：systemPrompt section `magic-memory`（order 200，按角色过滤）+ `magic-memory-rules`（order 210，rule 层带 `always` 标签的硬规则）。
- 存储：`magic_memory` 域 v1（per-record），table `memories`（`src/store.ts:274-283`）。
- 服务缝：`ctx.provide('magicMemory', { store, audienceOf, topics, rules })`。
- **UI 缺口（P1-2）**：缺"这次回答用了哪些记忆"的 citation 块与用户侧记忆管理入口（`07-体验对标调研.md` §3.5）。

### 5.6 统一按需检索 — `magic-consult`

- 工具 `consult`：按 name 查阅"按需目录"条目（记忆主题笔记 + 不带 `always` 的按需规则）；缺 name 时列出可查项；输出 8000 字符截断，缓存 64 条（`plugins/magic-consult/src/index.ts:88-130`）。
- 系统提示词 section `magic-consult-directory`（order 220）与目录共用一份数据（`src/catalog.ts`），防漂移。

### 5.7 会话历史检索 — DSH 原生 `tool-session-query`

web overlay 启用（`patches/web.patch.yml` 会话历史检索节）：`session-query-sqlite` 索引落 `dshHomePath('session-query.sqlite')`，`openAt: first-search`；挂 `tool-session-query` 五工具：`session_search / session_event_search / session_trace / session_event_trace / session_event_read`（workspace 授权范围内检索）。

- **UI 缺口（P1-5）**：只有模型侧工具，无用户侧检索面板（`07-体验对标调研.md` §3.8）。

## 7. 界面必须遵守的产品规则（前端契约汇总）

这些是 PRD 明文要求，桌面 UI 设计逐条对照：

### 7.1 信息分层（PRD-01 §12、PRD-02 §15.2）

- **会话** = 两种方式共同的实时工作现场：可理解的思考说明、计划、工具调用、文件变化、测试、派发、回传和结果；未经整理的原始内部推演不作展示承诺。
- **侧边导航** = 切换会话、工程（暂缓）和进行中的工作。
- **检查器/临时面板** = 当前选中的文件、Diff、产物、审批或子会话；工程团队总览是按需打开的独立视图，**不规定为固定万能 Tab**。
- 失败、同步缺口、预算超限、权限拒绝、不可逆副作用**不能被折叠隐藏**。

### 7.2 工作入口（PRD-02 §15.1）

- 输入框旁显示当前工作方式和作用域（如"代理 · 当前任务"/"CEO · 当前会话"）。
- 一键选择：代理 / 单次 CEO / 修改会话默认——三者用不同文案说明影响范围。
- 系统建议非阻塞：采用 / 稍后 / 不再建议。

### 7.3 切换确认页（PRD-02 §15.3）

必须列出：继续的目标、待完成计划、当前责任人、在飞运行、会话成员、可继承上下文、无法继承内容、已发生副作用、用户需要选择的处理方式；确认后生成"工作方式已改变"系统记录。

### 7.4 任务与治理呈现（PRD-04 §12、§20）

- 任务板**只读**（智能体驱动生命周期）；唯一展示面是画布；右坞 tab 以选中成员命名。
- 失败/阻塞不得只用颜色或图标：结构化失败卡（失败工具、错误摘要、未完成内容）+「重试 / 交回 CEO 重规划」；阻塞卡指明等待对象。
- 验收矩阵：运行完成→显示"运行完成，等待验收"；断连→显示同步缺口；重试→新旧 Attempt 区分；审批拒绝→原因+已完成部分+下一步；停止后有写入→副作用清单；部分完成→已完成/未完成分栏。
- **V1 范围注记**：任务完整状态机里的"部分完成、已停止、已归档"等在 V1 延后——实际交付状态以 `plugins/magic-ceo/src/delivery.ts:3-4` 的 `DeliveryStatus`（`completed / blocked / failed / partial / unverified`）为准，运行状态以 `src/plan.ts:1-10` 的 `RunPhase`（`queued / running / completed / failed / skipped / cancelled / unverified / unknown_after_restart / blocked`）为准；**不在界面伪造未实现的状态**。

### 7.5 治理卡片（PRD-05 §15）

| 卡片 | 必须显示 |
|---|---|
| 权限请求卡 | 动作、资源、范围、环境、风险、预算、有效期、批准/拒绝 |
| 成本卡 | 上限、已预留、实际消耗、剩余、归属、超限原因（预算四数：PRD-05 §5） |
| 事实卡 | 内容、来源、版本、确认者、状态、争议、影响任务 |
| 副作用卡 | 已发生动作、资源变化、是否可逆、补偿入口 |
| 访问拒绝卡 | 拒绝规则、缺少的授权、可申请的最小范围 |

- 权限三档入口（PRD-05 §3）：请求批准 / 当前范围内自动处理 / 完全访问当前工作区——三档不能突破系统禁止项、高风险规则、预算上限。
- 审批等待以"审批卡 + 横幅"呈现，不改变状态机（PRD-04 §16 V1 注记）。
- 成员结构化结果模板（PRD-04 §19）：任务 / 状态 / 完成内容 / 未完成内容 / 产物与链接 / 验证依据 / 风险与阻塞 / 已发生副作用 / 建议下一步 / 需要用户决定。

### 7.6 长期不变量中与 UI 直接相关的（PRD-01 §6）

- 系统建议不能变成强制升级；代理与 CEO 平等。
- 每个正式任务任一时刻只有一名当前责任人；任务状态与运行状态分离。
- 失败、等待、停止、取消、部分完成必须诚实呈现；不承诺任意无损切换，无法无损时说明影响。
- 取消运行不撤销已发生的副作用。

## 8. 状态机与数据模型速查（UI 渲染依据）

- **任务状态机**（产品完整模型，PRD-04 §3）：草拟 → 待执行 → 执行中 ⇄ 等待 → 已完成 / 部分完成 / 失败 / 已停止 / 已取消 → 归档。等待必须说明等待谁/什么/开始时间/继续方式。
