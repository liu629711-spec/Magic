# Magic 代码架构基线 V1

## 1. 目的

这份文件先确定代码如何组织，再约束已验证的 Rust UI 路线和仍待评审的基础设施库。它约束模块职责、依赖方向、替换接缝和测试方式。

## 2. 建议代码布局

```text
apps/
  desktop/                Tauri 桌面入口、Rust UI 和安全桥接
  local-service/           Rust 本地 API、Worker、进程启动和配置装配
crates/
  domain/                 Task、Attempt、Plan、Fact、Artifact 和状态规则
  application/            用例编排：创建、派发、取消、重试、对账、验收
  contracts/              Magic API 和事件的请求/响应类型
  execution-port/         执行底座的唯一 Interface
  execution-opencode-v1/  OpenCode V1 Adapter（同步 HTTP 调用置于 blocking 边界）
  persistence-port/       仓储和事务 Interface
  persistence/            rusqlite/SQLite 数据库 Adapter
  policy/                  权限、审批、预算和资源范围判断
  reconciliation/         实时事件、补拉、去重和重启对账
  observability/          日志、指标和审计写入
tests/
  contract/               API 和 Adapter 合约测试
  integration/            数据库、执行底座和恢复测试
  e2e/                    用户可见的完整闭环测试
docs/adr/                 需要记录的不可逆技术决策
```

## 3. 依赖方向

```text
desktop/local-service -> application -> domain
                         -> execution-port -> execution adapter
                         -> persistence-port -> persistence adapter
                         -> policy / reconciliation / observability
contracts <-> local-service/application（只共享数据契约，不承载业务规则）
```

领域模块不能依赖 HTTP、数据库驱动或 OpenCode SDK。Application 只依赖 Interface；具体 Adapter 在启动装配层注入。这样未来替换 OpenCode V2 或 DeepSeek Harness 时只替换 Adapter 和合约测试，不改 Task/Attempt 规则。

## 4. 外部 Interface

### ExecutionPort

最小 Interface：`createSession`、`submit`、`readMessages`、`cancel`、`subscribeEvents`、`readHistory`、`reconcile`。Interface 必须定义对象 ID、顺序、错误、取消和“结果未知”的行为；不能只暴露底层 HTTP 转发。

### PersistencePort

最小 Interface：Task/Attempt 读写、幂等查找、事件追加、游标更新、审批/费用/副作用追加和事务执行。具体引擎不出现在 domain/application 包中。

### PolicyPort

输入必须包含动作、资源范围、授权快照和预算上下文；输出为 allow/ask/deny 以及可审计原因。

## 5. 桌面运行形态

Magic 是本地桌面应用，代码上分为桌面壳、Rust UI、本地 Rust API/Worker 和 OpenCode 进程四个角色。桌面壳负责窗口、生命周期、进程拉起和安全桥接；Rust UI 只能调用 typed desktop bridge 或本地 Magic API；API/Worker 负责产品状态和恢复；OpenCode 作为受控的 Bun/TypeScript 执行子进程。

桌面窗口关闭不能自动等于 Attempt 取消。生产环境的本地 API/Worker 必须是独立于 Tauri 窗口的进程；它可以由桌面层启动或发现，但不能依赖窗口进程存活。应用生命周期策略（后台驻留、退出时等待、重新打开后的对账）由 Worker 和 supervisor 负责，不能由渲染层自行处理。

## 6. 运行进程

首版至少包含两个逻辑角色：

- API 进程：接收用户请求、读取投影、提交用例和推送已提交事件；必须独立于 Tauri 窗口。
- Worker/Recovery 进程：执行派发、消费底座事件、补拉 history、执行启动对账；必须独立于 Tauri 窗口。

API 和 Worker 在最初实现中可以运行在同一个独立 Rust 进程内，但代码 Interface 必须保持分离，避免把 HTTP 请求生命周期当成 Attempt 生命周期。客户端断开或窗口关闭不能自动终止 Worker。

## 7. 写入和事件规则

每次产品状态变更通过 Application 用例完成：校验幂等键和权限 → 写入不可变事件 → 更新当前投影 → 写审计/用量/副作用引用 → 提交事务 → 异步通知订阅者。

实时通知不是权威存储。订阅者断开、重复或乱序时，以事件账本和游标重新读取；对账失败进入 `unknown`，禁止静默重派。

## 8. 测试策略

- Domain：纯状态转移、责任人约束和幂等规则，完全不启动服务。
- Application：使用 fake Adapter 和 fake Persistence 验证用例与错误收口。
- Adapter contract：每个执行底座都必须通过同一组 create/submit/read/cancel/history 测试。
- Integration：真实数据库事务、唯一约束、迁移、重启扫描和事件游标。
- E2E：真实 OpenCode V1 进程、工作区 diff、审批、取消、重试和恢复。

验收标准不是“HTTP 返回 200”，而是 Task/Attempt 状态、事件、底层消息、资源变化和审计记录能相互解释。

## 9. 现在不冻结的内容

以下选择必须单独评审并记录 ADR：部署形态、认证方式和消息传输方式。Rust UI 已由 ADR-0003 冻结为 Yew 0.23 + Trunk + WASM；本地服务基础栈已由 ADR-0005 冻结为 Tokio + Axum + rusqlite/SQLite。本基线只规定基础设施必须满足上述 Interface 和依赖方向。OpenCode V1 的 Bun/TypeScript 运行时属于外部底座约束，不改变 Magic 自有代码语言栈。

## 10. 开发顺序

1. 确认本基线和领域词汇。
2. 分别评估部署、认证和消息传输方案，形成必要的技术选型 ADR。
3. 搭建空模块和契约测试，不接真实执行。
4. 实现 Domain/Application 的 Task → Attempt 状态闭环。
5. 实现数据库 Adapter 和迁移。
6. 实现 OpenCode V1 Adapter，通过合约测试后接入 Worker。
7. 实现前端首屏和事件对账，再做真实工程 E2E。
