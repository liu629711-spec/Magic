# 首次开发准入清单

## 当前结论

现在可以开始写技术验证代码，但不能把它称为首次正式产品开发。

## 立即允许

- F-10 harness、故障注入器、证据采集与回放工具；
- runtime/client 构建和锁定脚本；
- 可丢弃的 OpenCode Adapter、Projection 与 Reconciler spike；
- JSON Schema、fixture、contract test 和假事件 UI；
- 独立临时仓库中的 Git/worktree、审批和副作用实验。

## First Development 转 Conditional Go 的必要条件

- [ ] 首版生产拓扑与底座锁定 ADR 完成五方签署；
- [ ] canonical runtime/client/env 形成不可变 lock 与 hash；
- [ ] Magic 最小执行与收敛契约 v0 完成五方签署；
- [ ] 技术验证与产品切片均使用版本化 ContextEnvelope、TaskResultPacket 和唯一 acceptance_authority_id；
- [ ] F-10 全部阻塞场景及组合场景完成可重复实验；
- [ ] 每项实验留存原始事件、快照、Projection、审批、Git、产物和副作用证据；
- [ ] 首版关键能力不再处于 unknown/blocked；无法自动恢复的路径有明确人工核对状态、责任人和下一步；
- [ ] F-10 与首次开发准入验收规范获得五方签署；
- [ ] First Development 的范围仅限首条产品切片，未隐含放行后续能力。

## 首条正式产品切片

单用户、单工程、唯一 PM、一个成员、一个正式成员任务、一个 Git 主资源和独立 worktree。PM 通过版本化 ContextEnvelope 派发，成员执行并通过不可变 TaskResultPacket 回传，系统分别记录 Task、Attempt、Approval、Artifact、ChangeSet 和 SideEffect。

首切片中，PM 派发的成员任务由当前 PM 验收；用户发起的根任务或工程交付由用户验收。验收权通过 `acceptance_authority_id` 固定在对应任务上，成员任务与根任务分别形成唯一终态，任何一方的验收都不能自动改写另一任务的历史。

## 不随首切片自动放行

第二成员并发、身份复用、PM 交接、冲突合并、完整停止重开交互、U-12 全量预算/高风险矩阵、团队画布、圆桌、多层 PM、跨工程和多用户多端。
