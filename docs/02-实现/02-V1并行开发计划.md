> 2026-09-11 相对 DSH 0.1.5 的结论：ledger / memory **已经挂进** `patches/web.patch.yml`；官方 Teams 只挂服务 + 面板（形态 A'）；CEO 派活仍走 `ctx.subagents`；检查器的 `details` / `openDetails` 在官方 UI 里已删除。

## 1. 目标与范围

### 1.1 目标（一句话）

在**不改 DSH 内核**的前提下，以插件方式把 AgentCore 的核心产品能力重建进 Magic，使 Magic 成为龙哥自己的产品——**DSH 出执行底座，Magic 出组织与治理**。

### 1.2 V1 范围（五个能力域）

| 编号 | 能力域 | 交付形态 | 依赖的 DSH 机制 |
|---|---|---|---|
| A | 状态持久化（地基） | `magic-ceo` 内新增 `src/store/**` | `ctx.storageDomain` |
| B | 交付契约与验收账本（命门） | 新插件 `magic-ledger` | `ctx.tools` + `ctx.storageDomain` + 事件 |
| C | 记忆 | 新插件 `magic-memory` | `ctx.systemPrompt.section` + `ctx.tools` + `ctx.storageDomain` |
| D | 统一检索（consult） | 新插件 `magic-consult` | skill 注册 + `inject()` |
| E | 升级体检（护栏） | `tools/contract-smoke/**` | DSH 源码 checkout 内真实加载 |

### 1.3 非目标（V1 明确不做）

- 不搬运 AgentCore 代码，不做分叉，不做第二套执行引擎；
- 不 import 任何 `@deepseek-ai/dsh-*` 包（理由见 §2.4）；
- 不做工程组织（PRD-03 暂缓）；
- 后置能力域：文件夹与多工作区、笔记墙/看板、辩论、升级/交接、Playbook、成本配额、可观测回放。

### 1.4 V1 验收的最终标准

**跑通一个真实交付闭环**：CEO 接收一个真实任务 → 派发成员 → 成员产出落盘物证 → 账本验收 → 结果可追溯、可重启恢复。不以插件数量或代码行数为准。

## 2. 决定并行可行性的关键事实（全部已核实）

这一节是并行方案的地基。**任一事实若不成立，对应的工作流就不能并行。**

### 2.1 插件骨架零依赖、测试零依赖 → 并行不改锁文件

- 每个插件是独立 `package.json`，`pnpm-workspace.yaml` = `plugins/*`，新目录自动入workspace（`pnpm-workspace.yaml:1-2`）。
- 测试用 Node 内置 runner 直跑 TS：`node --test tests/*.test.ts`（`plugins/magic-ceo/package.json:23-25`）。
- **实测**：`node --test plugins/magic-ceo/tests/plan.test.ts` → 12 通过、0 失败，**无需任何安装**。
- 插件运行时零第三方依赖；根 `node_modules/` 为空，依赖按插件隔离。

> **推论**：三个新插件可以并行创建，只要**不并发执行 `pnpm install`**，就不会在 `pnpm-lock.yaml` 上打架。本轮并行方案据此设计为"零新增依赖"。

### 2.2 一个插件一套 `cordis.patch.yml` → 加载项互不冲突

每个插件自带 `cordis.patch.yml`，只 insert 自己：

```yaml
# plugins/magic-ceo/cordis.patch.yml
- insert:
    - id: magic-ceo
      name: '@magic/dsh-ceo'
```

`patches/web.patch.yml`（Magic 的总 overlay）是**共享文件**，新增插件时必须改它 —— 见 §5.3 的所有权规则。

### 2.3 存储域是"单域名单次 open" → 必须一插件一域

`DomainFacility.open()` 用 `reserved` 集合拒绝同名重复打开，抛 `already-open`（`DSH/packages/storage/storage-domain/src/index.ts:101-104`）。

> **设计约束**：**一个插件独占一个 storage 域，域内多表。禁止两个插件共用一个域名。**

### 2.4 不能 import DSH 包（更正此前结论）

**此前我断言"DSH 包装不到，物理上不可能"——不准确，现更正如下（均经实测）：**

| 事实 | 证据 |
|---|---|
| `@deepseek-ai/cordis@4.0.2` 是公开包，**已安装在 Magic** | `plugins/magic-ceo/node_modules/@deepseek-ai/cordis` → 软链到 `node_modules/.pnpm/@deepseek-ai+cordis@4.0.2` |
| 一批 DSH 产品包发布在 npm，但版本仍可能落后 checkout | 2026-09-11 抽查：`@deepseek-ai/dsh-session` = `0.0.1-rc.1`；本地 checkout = `0.1.5-rc.2` |
| experimental Agent Teams 已发 npm | `@deepseek-ai/dsh-experimental-agent-team` = `0.1.5-alpha.2`；五包 `publishConfig.access: public`（`DSH/packages/experimental/README.md`） |
| 即便发了，CLI runtime 闭包仍不含它们 | experimental 在 `apps/cli` 的 **devDependencies**；`profileDependencyNames` 只扫 `dependencies` + `peerDependencies`（`DSH/packages/boot/app-boot/src/profile.ts:460-461`） |

**不 import 的结论不变，理由更新为**：

1. **版本倒挂仍在**：至少 session 等产品包的 npm 快照落后于运行时 checkout；
2. **experimental 能装不等于能被 `--patch` 按包名解析**：heal 只给 install-anchor 闭包和 profile bundle 建链接；
3. **公共 API 仍 pre-stable**（`DSH/AGENTS.md:5-7`）。Session 数据从 0.1.5-alpha.1 起按 writer=3 做相邻迁移，这与「不要把 npm 版本写进 Magic package.json」不冲突。

**保留的口子**：等 CLI runtime 把 experimental 放进 dependencies、且产品包与 checkout 同版本后，再评估按版本依赖发布包。当前仍路径挂载。

### 2.5 存储域 spec 的结构与最小依赖实现

`ctx.storageDomain.open(spec)` 的 `spec` 是 `DomainSpec`（`storage-domain/src/spec.ts:35-52`）：

```ts
{ name, version, layout?: 'single' | 'per-record', global?: { schema, initial }, tables: { [t]: { valueSchema } } }
```

运行时**只**做三件事：读 `spec.name/version/layout/global/tables`、调 `valueSchema.parse(raw)`、调 `global.schema.parse(v)`（`storage-domain/src/index.ts:114-132`）。

- `defineDomain` / `domainTable` 只是**校验用的恒等函数**（`spec.ts:71-114`），**不参与运行时**；
- `defineDomain` **不会**被 `open()` 调用，所以 spec 可以手搓；
- 因此 **Magic 可以零依赖地直接构造 spec 对象**，只要 `.parse` 存在即可。

> **V1 决策**：手搓 spec + 本地 `schema` 帮助函数（实现 `.parse`），不引入 zod。zod 作为后续可替换项，通过 §4.3 的 schema 端口升级。

### 2.6 契约测试缺位 → 升级体检是并行开发的安全气囊

`plugins/*/tests/*` 全部只 import 自己的 `../src/*`，**没有一个测试加载真实 DSH**。上游改字段名 → 编译不报错、测试不失败、运行期才炸。

> 这是工作流 E 存在的理由，也是**所有并行工作流的共同护栏**。

## 4. 并行方案

### 4.1 波次安排

```
Wave 0（串行，主代理，阻塞后续）
  W0 契约内核冻结 ── 文档 + 参考实现 + 接口签名冻结
        │
        ├──────────────────┬──────────────────┬
        ▼                  ▼                  ▼
Wave 1（并行 3 个子代理）
  W2 magic-ledger     W3 magic-memory    W5 升级体检
        │                  │
        │                  ▼
        │            Wave 2（串行）
        │              W4 magic-consult
        │
        └──────────┬───────┘
                   ▼
Wave 2（串行，主代理）
  W1 magic-ceo 状态外移   （与 W2/W3/W5 并行进行，但文件不冲突）
  W6 文档回写（最后）
```

**说明**：W1 与 Wave 1 的三个子代理**同时进行**，因为文件所有权完全不相交（一个改 `magic-ceo`，一个建 `magic-ledger`，一个建 `magic-memory`，一个建 `tools/contract-smoke`）。

### 4.2 依赖关系

| 依赖 | 类型 | 说明 |
|---|---|---|
| W2/W3/W5 → W0 | 硬依赖 | 必须按冻结的接口写；接口未冻结前不得开工 |
| W4 → W3 | 硬依赖 | consult 的检索源包含记忆；记忆域未就即前无法联调 |
| W1 → W0 | 硬依赖 | store 端口来自 W0 |
| W6 → W1..W5 | 硬依赖 | 文档记录实现现状 |
| W2 ↔ W3 ↔ W5 | 无依赖 | 三者的域、目录、测试完全独立 |

**关键**：W2/W3 之间**没有**代码依赖 —— 因为"一插件一域"已经切断了共享状态。这正是 §2.3 约束带来的并行红利。

### 4.3 为什么这样切

并行切分的唯一原则是 **"文件所有权不相交 + 接口先冻结"**：

- 按**插件目录**切，而不是按"层"切（按层切必然多人改同一文件）；
- 新能力一律**新插件**，天然隔离；
- 共享文件（`patches/web.patch.yml`、根 `package.json`、`pnpm-lock.yaml`）由主代理**独占串行**修改。

## 5. 协调机制

### 5.1 接口冻结（最重要）

W0 产出的 `docs/02-实现/03-插件契约内核.md` 是**唯一接口来源**。冻结内容：

1. 插件骨架约定（`name` / `inject` / `apply` / `package.json` / `cordis.patch.yml` / `tests`）；
2. **鸭子类型 ctx 契约**（各扩展点的结构化类型签名，逐字段写全）；
3. **存储端口**（`Store` 接口）+ DSH 适配器 + 内存适配器（测试用）；
4. 域命名与 spec 约定（命名正则、版本、layout、schema 帮助函数）；
5. 事件命名约定（`magic:*`）；
6. 文件所有权矩阵。

> **冻结后，任何工作流不得私自改接口。** 需要改接口 → 提变更请求回主代理 → 主代理统一改内核 → 全体同步。

### 5.2 子代理的工作契约

每个子代理必须收到（并在开工前阅读）内核文档。其工作契约：

- **只写自己所有权目录内的文件**；
- **不执行 `pnpm install`**（零新增依赖是硬约束）；
- **不修改任何共享文件**（见 §5.3）；
- **测试自证**：`node --test` 自己包内全绿；
- **交付即报告**：列出新增/修改文件、测试结果、未决问题。

### 5.3 共享文件所有权（主代理独占）

| 共享文件 | 谁可以改 | 规则 |
|---|---|---|
| `patches/web.patch.yml` | **仅主代理** | 新插件上线时由主代理统一追加 |
| 根 `package.json` | **仅主代理** | 脚本变更由主代理统一处理 |
| `pnpm-lock.yaml` | **仅主代理** | 本轮零新增依赖，不该动 |
| `docs/01-产品/**`（PRD） | **仅主代理** | 产品语义变更先改 PRD，不在并行流内 |
| 各插件的 `package.json` | 对应工作流 | 仅限自己插件目录内的那份 |

### 5.4 冲突处理规程

1. 子代理发现必须改接口 → **停手**，把诉求回报主代理，不自行改；
2. 子代理发现必须改共享文件 → **停手**，回报主代理；
3. 主代理发现接口设计错误 → 改内核文档 → **通知所有受影响工作流同步**（因为文件不相交，同步成本低）；
4. 集成阶段由主代理统一执行：追加 `patches/web.patch.yml`、跑根 `pnpm test`、更新文档。

## 6. 并行开发必须遵守的约束（红线）

1. **不动 DSH 源码**：`reference-project/` 只读。
2. **不 import `@deepseek-ai/dsh-*`**：只用结构化类型鸭子匹配（§2.4）。
3. **不复制 AgentCore 代码**：重做，不搬运（`AGENTS.md` 第一原则）。
4. **不越文件所有权**（§5.3）。
5. **不新增第三方依赖**：V1 内核零依赖。
6. **不新建平行 PRD**：产品语义变更先改既有 PRD。
7. **不猜**：接口/字段以源码为准；未核实标"待核查"。
8. **一插件一域**：禁止共享 storage 域名。

### 10.5 W2 接线暴露的运行期缺陷（**208 个单元测试全部漏检，仅真实加载可发现**）

1. **工具缺 `output` 声明**：`magic-memory` 的 `magic_memory_search` / `magic_memory_record`
   只给了 `parameters` + `execute`，缺 `output: { schema, render }` ⇒ 加载期 fatal：
   `tool "magic_memory_search" must declare output { schema, render, presentationMeta? }`。
   **整个 profile 启动失败**，而单元测试用假的 `tools.register`，不触发该校验。
   ⇒ 已修（`magic-memory/src/index.ts`）；`magic-ledger` / `magic-ceo` 可作正确写法范本。
2. **`ctx.get` 缓存时机**：账本服务若在 `apply` 时一次性读取并缓存，插件加载顺序会静默决定
   增强是否生效。⇒ 改为每次使用时读取（`readLedger(ctx)`）。

⇒ **结论**：凡改动 `ctx` 用法（`inject` / `effect` / 服务访问 / `tools.register`），
必须跑一次真实 profile 启动，静态测试与 `--dump-config` 都覆盖不到。

### 10.4 W1 接线暴露的两个运行期缺陷（**195 个单元测试全部漏检，仅真实加载可发现**）

1. **`inject` 漏声明**：`storageDomain` 加进了 TS 类型却漏进 `export const inject` ⇒ 运行期
   `cannot get property "storageDomain" without inject`，**插件整棵树加载失败**（`exit=1`）。
2. **`ctx.effect` 语义误用**：把 disposer 直接当 setup 传入 ⇒ 域被当场作废，表现为
   `open` 永不就绪、写队列空转（无任何报错）。同类误用已一并修复：`magic-memory`、`magic-ledger`。

**根因**：单元测试直接调 `apply`、**不走 Cordis DI**；`--dump-config` 只解析配置、**不 import 包**。
两者都覆盖不到 `ctx` 用法的运行期语义。

⇒ **新增护栏（已写进契约内核 §3.4）**：凡改动 `ctx` 用法（inject / effect / 服务访问）后，
**必须在真实 profile 里启动一次**再收工。
