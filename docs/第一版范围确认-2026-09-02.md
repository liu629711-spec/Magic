# Magic 第一版范围确认

本文是第一版范围对齐记录，不是新的 PRD。产品语义以 `docs/01-产品/PRD-01` 至 `PRD-05` 为准；本文只把第一版要实现的范围和技术限制收敛成可执行清单。

## 2. V1 的真实状态规则

1. 客户端关闭窗口不等于取消任务；重新打开后先读取 Magic 状态并进行对账。
2. OpenCode 重启后不能自动推断任务成功；无法确认时显示“重启后状态未知”。
3. 取消不撤销已经发生的文件写入、命令、费用或外部副作用。
4. 重试一定创建新的 Attempt，旧 Attempt 和历史费用保留。
5. 同一幂等键只能对应一次 Magic 派发；请求内容变化必须报冲突。
6. Task 只有在验收证据满足并由责任人收口后才是“已完成”。

## 3. 明确不纳入 V1

- OpenCode V2 执行器或 DeepSeek Harness 作为生产底座；
- OpenCode 进程级自动接管未完成执行；
- 多用户、多工程、多层 PM 和跨工程成员借调；
- 两名以上成员的自动并发编排和自动合并冲突；
- 自动撤销、自动补偿和对已经发生副作用的回滚承诺；
- 任意无损的运行中模式切换；
- 多人实时画布、复杂团队看板和完整原始思维展示。

## 4. 进入开发的验收门槛

只有以下条件同时满足，才把范围标记为 `confirmed` 并进入实现：

- 用户确认第 1 节的范围和第 3 节的排除项；
- 后端、数据库、前端三份方案与本清单一致；
- OpenCode V1 的版本、启动方式、目录和适配器配置被写入实现配置；
- 首个真实工程场景的验收证据已定义：任务、Attempt、审批、worktree、产物、费用和副作用均可追溯；
- 未确认的 T-10、T-12、T-13、T-14 项不被包装成底座保证，而是有明确的 Magic 处理策略。

## 5. 当前状态

用户已确认本清单，状态为 `confirmed`。前端视觉细节可以在开发过程中逐步完善，但后端对外 API、状态、事件、幂等和验收语义按本清单执行。
