# DSH Desktop 作为 Magic 桌面基座的评估（2026-09-04）

## 结论

不把 [dataelement/dsh-desktop](https://github.com/dataelement/dsh-desktop) 作为 Magic 的代码基座，也不将其 UI 嵌入 Magic；保持 **Magic 自有 Tauri/Yew 界面 + 独立 Rust Local Service + 隔离 DSH 进程**。

它值得借鉴和复用的是「DSH 的生产级桌面托管方式」：打包 DSH/Node、隔离 `DSH_HOME`、启动和退出管理、启动失败恢复、安全模式、Profile/插件维护、原生目录选择与更新机制。它不是一个可让 Magic 仅靠换皮就得到 Codex 式产品界面的通用桌面前端。

这不是否定 DSH。DSH 仍是 Magic 的 Agent 执行底座；拒绝的是把另一个产品的 Electron 壳和 DSH Web UI 当成 Magic 产品层。

## 它实际做了什么

### 1. Electron 宿主，不是第二套 Agent Runtime

DSH Desktop 的架构文档明确说明：Electron Main 启动隔离的 Node-capable Harness 进程；Harness 在随机 loopback 端口提供 Web UI；`BrowserWindow` 加载这个 Web UI。它“不维护第二个 Agent runtime，也不重写 Harness frontend”。[​架构文档](https://github.com/dataelement/dsh-desktop/blob/7cb9e046e8ec58864d95c3ce30541e369fdc833e/docs/architecture.md)

源码也与此一致：

- `src/main/runtime/harness-runtime.ts` 用打包 Node 启动 `dsh web --no-open --host 127.0.0.1 --port <随机端口>`，并把独立目录写入 `DSH_HOME`。[​启动参数与环境](https://github.com/dataelement/dsh-desktop/blob/7cb9e046e8ec58864d95c3ce30541e369fdc833e/src/main/runtime/harness-runtime.ts)
- `src/main/index.ts` 的 `openHarness()` 调用 `BrowserWindow.loadURL(rendererUrl)`，加载的是 DSH 的本机 Web 地址。[​窗口加载](https://github.com/dataelement/dsh-desktop/blob/7cb9e046e8ec58864d95c3ce30541e369fdc833e/src/main/index.ts)
- 它从 DSH stdout 取得一次性启动 token，以 cookie 方式完成窗口认证；这个处理是桌面壳与 DSH 间的安全桥，而不是给第三方产品的高层 UI API。[​token 处理](https://github.com/dataelement/dsh-desktop/blob/7cb9e046e8ec58864d95c3ce30541e369fdc833e/src/main/runtime/harness-runtime.ts)

因此，用户看到的聊天、会话、设置和工作区主界面，本质仍是 DSH Web UI。DSH Desktop 解决的是「把它可靠地装进桌面应用」，而不是「提供另一套可独立演进的 Agent 产品 UI」。

### 2. 桌面端加的能力是真实且有价值的

其 README 与架构文档可验证以下桌面层能力：本机目录选择、托管 DSH 生命周期、保持 Profile/插件/会话/模型设置、启动诊断和恢复、无破坏安全模式、可选手机桥接、桌面更新、原生菜单和窗口行为。[​README](https://github.com/dataelement/dsh-desktop/blob/7cb9e046e8ec58864d95c3ce30541e369fdc833e/README.md) [​架构](https://github.com/dataelement/dsh-desktop/blob/7cb9e046e8ec58864d95c3ce30541e369fdc833e/docs/architecture.md)

其持久化布局也把 DSH profile、sessions、settings 与安装目录分离，升级不会覆盖用户数据。这个思路与 Magic 当前「Local Service 受控启动隔离 DSH」一致，应该借鉴。[​持久化布局](https://github.com/dataelement/dsh-desktop/blob/7cb9e046e8ec58864d95c3ce30541e369fdc833e/docs/architecture.md)

### 3. 它确实用 DSH 插件，但插槽并不等于完整 UI 替换能力

DSH 官方架构是 everything-is-a-plugin；插件通过 `inject` 声明服务依赖、通过 `apply(ctx)` 访问服务和事件。这是 Magic 为执行规则、工具、供应商或补充 UI 能力写 DSH Bundle/Profile 插件的正式接缝。[​DSH README](https://github.com/deepseek-ai/deepseek-harness/blob/4e84901e6471b79ec0338099867ebb4606d12bb5/README.md) [​Cordis primer](https://github.com/deepseek-ai/deepseek-harness/blob/4e84901e6471b79ec0338099867ebb4606d12bb5/docs/cordis-primer.md)

但 DSH Desktop 自己的 UI 插件 `dsh-desktop-client-ui` 只替换 `sidebar.brand.mark`、`sidebar.brand.name` 和 `conversation.hero.brand.mark` 三个品牌插槽；其源码没有实现完整的三栏会话管理或 Magic 的领域界面。[​插件声明](https://github.com/dataelement/dsh-desktop/blob/7cb9e046e8ec58864d95c3ce30541e369fdc833e/packages/dsh-desktop-client-ui/package.json) [​插件实现](https://github.com/dataelement/dsh-desktop/blob/7cb9e046e8ec58864d95c3ce30541e369fdc833e/packages/dsh-desktop-client-ui/client.js)

它的桌面 patch 主要是替换官方品牌、挂载市场安装器、HMR fallback 与 preset transfer，并非提供一个「替换整个聊天与会话布局」的稳定扩展层。[​Desktop patch](https://github.com/dataelement/dsh-desktop/blob/7cb9e046e8ec58864d95c3ce30541e369fdc833e/build/dsh-desktop.patch.yml)

## 插件市场的含义

DSH Desktop 默认集成的是 `dshmarket` 社区插件市场：其功能是为 **DSH Profile 安装、更新、启停 DSH 插件与主题**。[​dshmarket README](https://github.com/dataelement/dsh-desktop/blob/7cb9e046e8ec58864d95c3ce30541e369fdc833e/packages/dshmarket/README.md)

这可作为 Magic 的底层插件供应与安装能力的候选来源，但不等同于 Magic 已定义的「插件市场」产品页面。Magic 仍应拥有自己的目录、审查、授权、展示与失败状态；对已批准的 DSH 插件，可由 Magic Local Service 调用 DSH Profile/Bundle 安装流程。

## 为什么不应直接 fork 它来改 UI

| 方案 | 直接收益 | 对 Magic 的代价 | 判断 |
| --- | --- | --- | --- |
| fork DSH Desktop，改其 DSH Web UI | 快速得到 Electron 打包、Profile 管理、安全模式、市场入口 | Magic 要从 Tauri/Yew + Rust Local Service 迁到 Electron/TypeScript；三栏连续布局、置顶/工程/项目/最近分组、Magic 领域状态和右侧工作区都要深改 DSH UI；维护目标变成 DSH Desktop patch + DSH alpha 两层上游 | 不采用 |
| Magic UI 内嵌 DSH Desktop/DSH Web UI | 很快显示完整 DSH 功能 | 两套会话、设置、状态和导航并存；无法保持已确定的 Magic 交互，也会暴露不受 Magic 管理的原始界面 | 不采用 |
| 保留 Magic UI，用 DSH 作为受控服务 | 保持已完成的视觉和产品边界；直接使用 DSH 的会话、模型、工具与插件能力 | 需要逐项把用户可见功能接到 Magic API/界面；模型设置和真实执行链路仍要完成 | 采用 |

DSH Desktop 自己也承认上游升级是显式兼容性工作：开发文档要求升级 DSH 后重新验证 Settings、Credentials、Provider Directory、workspace/preset 合约，重写或重放 patch 并走完整测试。[​升级维护说明](https://github.com/dataelement/dsh-desktop/blob/7cb9e046e8ec58864d95c3ce30541e369fdc833e/docs/development.md) 其 `0.1.2-alpha.4` 升级记录还列出 19 个需要追踪的上游 patch，涉及 sidebar、chat、model、workspace、session 等 UI/行为区域。[​升级记录](https://github.com/dataelement/dsh-desktop/blob/7cb9e046e8ec58864d95c3ce30541e369fdc833e/docs/harness-0.1.2-alpha.4-upgrade.md)

所以「fork 后始终用上游最新 DSH」不是低维护路径。即使直接采用 DSH Desktop，也应锁定 DSH 版本、回归验证、再升级；Magic 当前的 DSH Adapter 已经遵循这一原则。

## 对 Magic 的具体动作

1. **继续当前路线。** 保留 Magic 桌面 UI 与 Rust Local Service；DSH 仅由 Local Service 启动和访问，DSH token 不进入前端或持久化。
2. **借用桌面托管经验，不复制代码基座。** 在正式打包阶段补齐：打包固定 DSH/Node、独立 `DSH_HOME`、启动健康检查、正常退出、日志、恢复与 Safe Mode。每项先按 Magic 的 Tauri/Rust 边界实现。
3. **把 DSH 能力逐一接入 Magic。** 近期优先完成 `模型设置 -> DSH -> 真实会话/工具执行 -> session/follow -> Magic UI 对账`，不要改 UI 基座。
4. **把 DSH 插件作为底座扩展。** Magic 独有执行规则、工具或供应商能力做 DSH Bundle/Profile 插件；产品列表、分组、审批、交付物和治理仍归 Magic。
5. **插件市场分两层。** V1 可先让 Magic 的“插件”入口管理已批准 DSH Bundle/Profile；是否接入 `dshmarket` 及其第三方代码，另做安全和产品审查，不能默认等同于 Magic 插件市场。

## 复核结论

`dataelement/dsh-desktop` 是很成熟的 DSH **桌面宿主参考实现**，尤其值得参考其进程生命周期、隔离数据目录、插件恢复和打包策略；但它不是能替代 Magic 的桌面产品框架。对于已确定要复刻 Codex 式布局并发展 Magic 自有项目/会话/工作区产品逻辑的目标，直接以它为基座会把节省的壳层工作，换成更大的 UI fork 与升级维护负担。
