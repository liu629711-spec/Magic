# 桌面 Agent 会话管理对照（2026-09-04）

## 目的与边界

本记录只研究 Codex、Claude Code、Zcode 的会话管理。来源限于厂商官方文档或官网；没有公开证据的功能不作为产品事实。结论用于修正 Magic 左栏当前“同名 New session + 重复已更新”的低信息密度呈现，不构成后端数据模型变更。

## 已验证的产品事实

| 产品 | 官方证据 | 可作为 Magic 参考的事实 |
| --- | --- | --- |
| Codex / ChatGPT desktop | [Desktop app](https://learn.chatgpt.com/docs/app.md)、[Projects and chats](https://learn.chatgpt.com/docs/projects.md)、[Codex changelog](https://learn.chatgpt.com/docs/changelog#changelog-content)、[Rename command](https://learn.chatgpt.com/docs/developer-commands#rename-the-current-task-with-rename) | 用户可从 `New chat` 开始；项目用于收纳相关聊天、文件、指令和来源。项目下有 `Chats` 区，建议每个不同交付目标使用独立 chat，之后回到该项目的 Chats。官方更新记录还确认任务搜索覆盖标题和对话内容，任务列表可排序/置顶，已保存会话可重命名、归档与恢复；计划任务在独立的 `Scheduled` 管理界面中查看。 |
| Claude Code desktop | [Desktop application](https://code.claude.com/docs/en/desktop)、[Manage sessions](https://code.claude.com/docs/en/sessions) | 每个会话独立保存聊天历史、项目目录与代码变更；左侧栏列出会话并支持并行工作。会话可命名；官方 session picker 支持按当前工作树、仓库所有工作树或全部项目扩大范围，支持项目/工作树关联、搜索、重命名和从当前会话切换。会话行的信息包括名称/摘要、上次活跃时间、Git 分支等上下文。 |
| Zcode | [Zcode 中文官网](https://zcode.z.ai/cn) | 官网工作区示例清晰呈现 `新建任务`、`打开工作区`、`技能`，左侧以工作区/项目名称组织多个任务条目，中央是当前任务的连续执行记录。官网未公开说明置顶、重命名、搜索、归档或删除的具体交互。 |

## 不应臆测为“行业标准”的内容

公开一手资料没有同时证明三者都具备删除、右键菜单或按日期分组。因此 Magic 可以做这些能力，但应明确是自身的产品选择；不能写成“复刻 Codex/Claude/Zcode”。Codex 已公开置顶、重命名、归档/恢复；Claude Desktop 已公开归档与重命名。

## 对当前 Magic 左栏的直接判断

截图中的列表存在三个结构问题：

1. **标题不可辨识。** 所有行都是自动生成的 `New session - 2026...`，用户无法通过列表判断哪个会话解决了什么目标。
2. **分组没有承载上下文。** `项目` 下只堆会话，项目名、工作区路径或仓库/文件夹身份未成为可扫描的父级信息；`最近` 又重复相同条目。
3. **状态噪声高于状态价值。** 每行重复显示“已更新”，但没有说明是运行中、等待用户、未读完成还是仅更新时间变化。

## 建议的 V1 左栏结构

采用信息层级，而不是增加新的“Task”实体：

| 区域 | 内容 | 行内优先信息 | 操作原则 |
| --- | --- | --- | --- |
| 置顶 | 用户明确固定的会话 | 名称、必要时运行/待输入状态 | 只作为快捷访问，不复制原会话数据 |
| 项目 | 文件夹图标 + 项目名；展开后显示该项目 chats | 会话名称、状态、相对时间 | 新会话时归属当前项目；无项目会话不硬塞进项目 |
| 最近 | 非置顶的跨项目最近会话 | 会话名称、项目/文件夹次信息、相对时间 | 同一会话可作为“最近”索引出现，但点击仍打开同一会话 |
| 计划任务 | 与聊天分离的入口 | 名称、下次运行/结果状态 | 不混入普通会话列表 |

会话行遵循以下最小交互：当前会话才使用选中底色；运行中使用旋转状态标识，完成未读或需输入才给强提示；悬停时显示会话摘要、项目路径与更新时间，并提供置顶与更多操作入口。标题应在首个有效用户请求后生成可编辑摘要，避免保留“New session”。

## 实施顺序

1. 先接入会话标题、首次提示摘要、更新时间、DSH 工作目录关联和运行状态，不先做大而全的管理页。
2. 以已存在的 `置顶 / 项目 / 最近` 左栏分区重排同一批会话；确保点击任一索引都打开同一会话。
3. 再实现搜索、重命名、归档/删除等需要 DSH 明确支持或 Magic 本地持久化策略的操作。未落库前不展示会误导用户的按钮。

## 结论

成熟桌面 Agent 的共同点不是“更多条目”，而是让用户在切换前就看懂会话的**目标、所属上下文与需要处理的状态**。Magic V1 应优先完成这三项，随后才扩展归档或批量管理。

## 会话内容与模式对照

### 先说结论

Magic 当前有两个“模式”入口，这是概念重复：

- `Agent · 标准模式` 实际对应 DSH 的 Agent preset（`standard / ptc / minimal / cordis`），它是本次会话采用的 Agent 能力组合，应放在会话标题附近或作为一个明确的 Agent 入口。
- 右侧永久显示的 `Standard` 没有对应的独立 DSH 产品概念，应移除。计划模式也不是一个永久的第二模式按钮；DSH 的 `ui-plan` 只在 plan projection 激活时显示 Plan 控件，OpenCode/Claude 也把 plan 作为当前回合的工作状态，而不是每条消息旁边的常驻模式。
- `工作区可写` 是权限/访问模式，和 Agent preset 是不同维度，可以保留；模型选择是第三个独立维度。

因此，正常 composer 只需要：附件/引用、权限、模型、发送/停止；Agent preset 放到会话级入口；Plan 只在激活时出现。

### DSH 的真实会话结构

来源：`reference-project/deepseek-harness/packages/client/ui-chat/README.zh.md`、`ui-chat/src/client/chat/TurnProcessNodeView.tsx`、`ui-chat/src/client/chat/ReasoningRow.tsx`、`ui-tool/src/client/tool/components/ToolRow.tsx`。

DSH 的事件源仍然包含 `turn/start`、`step/start`、`step/end` 和 `turn/end`，但 Chat target 不把它们逐条画成聊天消息。完成的 Turn 会折叠成一个过程控件，摘要只显示有价值的事实，例如工具调用数、消息数、子代理数；没有可计数过程时显示 `Thought for a while`。打开中的 Turn 才持续展示思考、工具、重试等过程行。

DSH 用户实际看到的内容是：

1. 用户消息。
2. 运行中的思考行，使用 shimmer/进行中状态；结束后可折叠。
3. 工具行：工具名 + 一行摘要 + 状态点；展开后显示输入、输出或专用卡片。终端、读取、搜索、diff、网页结果都属于工具行的具体视图。
4. 权限确认、询问用户、失败和重试等需要行动的状态。
5. 最终 Assistant 正文，支持 Markdown、代码、图片和文件引用。

系统提示、上下文注入、压缩等只在确实影响阅读或需要审计时显示，并默认收起。生命周期边界不是用户消息，不应显示成“回合开始/步骤完成/回合完成”。

### OpenCode 的真实会话结构

来源：`reference-project/opencode/packages/app/src/pages/session/timeline/message-timeline.tsx` 以及其 `timeline/`、`session-ui/message-part` 实现。

OpenCode 用 TimelineRow 将 UserMessage、AssistantPart、Thinking、Tool/ContextToolGroup、Retry、DiffSummary 和 TurnDivider 分开。`turn/start`、`step/end` 等协议边界用于排序、折叠和滚动锚点，不作为可见状态行。工具内容按类型使用终端、diff、读取、搜索等专用 renderer；过程在完成后折叠，最终回答保持为正文。

OpenCode 还把自动跟随底部、暂停阅读、加载更早、跳回最新和工具详情展开作为会话体验的一部分，而不是把所有事件堆在一个列表中。

### Claude Code 的可见行为

来源：[Claude Code interactive mode](https://code.claude.com/docs/en/interactive-mode.md)、[How Claude Code works](https://code.claude.com/docs/en/how-claude-code-works.md)、[Permissions](https://code.claude.com/docs/en/permissions.md)。

Claude Code 的 agentic loop 内部会持续使用工具，但默认 transcript 只突出用户输入、模型输出、工具调用/结果和需要用户确认的权限提示。`Ctrl+O` 才进入更详细的 transcript，展开默认折叠的 MCP 调用，并显示时间戳和模型信息。正在运行时允许停止、排队下一条消息；权限模式（Manual、Plan、Auto 等）是会话级控制，不会把每个 turn 的起止协议写成聊天内容。

### Codex 的可见行为

来源：[ChatGPT desktop app](https://learn.chatgpt.com/docs/app.md)、[Projects and chats](https://learn.chatgpt.com/docs/projects.md)。

Codex 桌面端把 `New chat` 作为进入点，每个 chat 保留自己的 transcript 和工作目录；项目只是组织相关 chats、文件和指令的父级容器。官方文档没有把 turn/step 生命周期暴露为聊天行，也没有把“任务”作为用户必须填写的第二对象。普通会话以用户消息和 Agent 回复为主，执行中的工具、终端和审批属于该回合的过程反馈；项目/会话管理与回合过程是两个层级。

这也说明 Magic 不应把 `Task`、`Agent preset`、`Permission mode` 和 `Turn lifecycle` 混成多个常驻按钮：它们分别属于会话组织、Agent 配置、访问控制和内部运行状态。

### Magic 当前的错误映射

Magic 的 `conversation_messages()` 当前把以下内部事件直接投影成可见 `Status` 行：

- `turn/start` → 回合开始
- `step/start` → 思考
- `step/end` → 步骤完成
- `turn/end` → 回合完成

这正是截图中“回合开始/步骤完成/回合完成”反复出现的根因。正确做法是保留这些事件用于计算 Turn 状态和折叠边界，但在会话视图中折叠或过滤，只生成一个 Turn process summary；只有运行中、错误、权限确认、重试和最终结果进入主 transcript。

## Magic 的合理 V1 会话规则

| 场景 | 主会话区显示 | 默认状态 |
| --- | --- | --- |
| 空会话 | 空状态标题 + composer | 可直接输入 |
| 用户发送 | 用户消息 | 展开 |
| Agent 思考 | `思考中` + 单个进行中指示 | 展开；结束后可折叠 |
| 工具调用 | 工具名、摘要、运行/成功/失败状态 | 摘要可见，详情折叠 |
| 权限/询问 | 可行动的内联确认区 | 展开并聚焦 |
| 回合完成 | `已思考 · N 次工具调用` 或 `已思考一会儿` | 收起 |
| 最终回答 | Assistant Markdown 正文 | 展开 |
| 失败/中断 | 错误摘要 + 重试/继续操作 | 展开 |

这套规则同时满足 DSH 的事件事实、OpenCode 的 Timeline 组织和 Claude Code 的 transcript 克制性。下一步应先重做事件投影，再调整视觉；继续只改颜色或间距会保留根本问题。
