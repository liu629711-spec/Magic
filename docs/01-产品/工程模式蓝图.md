# 工程模式蓝图

> 本文是方向蓝图，不是完整 PRD，也不是技术实现设计。工程模式的规模很大，当前只冻结它为什么存在、解决什么问题、必须具备哪些边界，以及后续应按什么顺序对齐。

## 一、产品定义

工程模式是围绕一个长期工程建立稳定 Agent 组织的工作方式。

它支持的不只是一次任务的多 Agent 并行，而是持续的组织能力：角色可以复用，记忆可以积累，协作关系可以演进，任务可以长期推进，结果可以被反复评审和交付。

## 二、它解决的问题

工程模式适用于以下类型的问题：

- 工作会持续数天、数周或更久
- 工程需要多个稳定分工
- 同一批协作关系会被反复使用
- Agent 需要积累各自的工作记忆
- 工程需要任务队列、状态、评审和回顾
- 用户希望把“建设一支团队”本身作为工作对象

它不适合仅仅因为一次任务很复杂就被自动创建。

## 三、可能的组织形态

工程模式可以包含但不限于：

- 工程负责人或 CEO
- 产品经理
- 项目经理
- 前端 Agent
- 后端 Agent
- 测试 Agent
- 代码审查 Agent
- 产品质量评判 Agent
- 视觉或美术评判 Agent
- 文档与研究 Agent
- 各专业方向的组长
- 组长管理的组员团队

这些名称是代表性工种，不代表第一版必须预置固定角色。首版需要先验证“稳定职责是否有价值”，再决定角色创建和模板机制。

## 四、工程模式的核心能力方向

### 1. 团队建立

用户可以从空工程开始，也可以从当前对话或 CEO 临时团队转入。系统可以基于工程目标推荐初始团队，但用户必须知道并确认长期关系的建立。

### 2. 稳定职责

每个长期 Agent 应有明确的职责、边界、输入、输出、工具权限和协作对象。职责可以调整，但调整应留下可理解的记录。

### 3. 独立记忆

每个 Agent 可以积累与自身职责相关的长期记忆，但独立记忆不能天然等于事实。产品需要区分个人工作经验、工程共享事实、临时任务上下文和用户决策。

### 4. 共享关键信息

Agent 之间需要共享工程目标、约束、接口、决定、风险和交付状态等关键信息。共享应有范围和来源，不能把所有上下文无差别塞给所有 Agent。

### 5. 层级派发

组长可以管理自己的小团队，并向上汇报。层级派发必须有边界、可观察、可停止、可回收，不能因为理论上支持无限递归就让系统失去控制。

### 6. 圆桌会议

多个 Agent 可以围绕目标、方案、风险或验收结果进行结构化讨论。圆桌会议需要有议题、证据、发言顺序、冲突记录和结论，不应只是多个 Agent 同时输出长文本。

### 7. 工程交付

工程模式的交付必须回到统一工作区和产物体系。团队组织再复杂，用户最终仍需要知道完成了什么、产出了什么、哪些部分没有完成。

## 五、关键边界

- 工程模式不是自动升级的结果
- Agent 的稳定职责不等于不可更改的职业身份
- 独立记忆不等于完全隔离，也不等于可以任意共享
- 层级越深不代表智能越强
- Agent 数量越多不代表结果越可靠
- 圆桌会议不应成为所有任务的固定仪式
- 用户始终保留最终目标、范围和关键决策权
- 工程模式不能掩盖失败、冲突或交付缺口

## 六、建议的设计顺序

1. 先定义工程实体和生命周期
2. 再定义长期 Agent 的身份、职责和版本变化
3. 再定义独立记忆与工程共享信息的边界
4. 再定义任务分派、汇报和停止机制
5. 再定义组长与组员的层级规则
6. 再定义圆桌会议与冲突收敛
7. 最后定义团队模板、自动建队和规模治理

不能先从“预置多少种 Agent”开始，因为角色数量不是工程模式成立的理由。

## 七、首版验证问题

- 用户是否真的需要长期 Agent，而不是持续使用 CEO 模式
- 哪些职责最适合稳定复用
- 独立记忆能否提升连续工作的质量
- 共享信息如何避免遗漏和污染
- 组长派发是否比 CEO 统一派发更自然
- 圆桌会议在什么场景下比单 Agent 审查更有价值
- 用户愿意管理哪些组织信息，哪些应该由系统维护
- 一个工程的合理 Agent 规模和层级上限是什么

## 八、明确不提前承诺的内容

- 固定的 PM、前端、后端、测试等预制团队
- 自动为每个工程生成完整组织
- 无限层级和无限数量的 Agent
- 每个 Agent 拥有永久不变的个人记忆
- 所有 Agent 默认共享所有文件和对话
- 没有证据的自动投票或自动裁决
- 将工程模式包装成“更高级”的产品等级
