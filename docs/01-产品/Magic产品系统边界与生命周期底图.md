# Magic 产品系统边界与生命周期底图

> 本文将 Magic 用户看到的长期对象与 OpenCode 实际执行对象分开。它是产品和技术共同讨论数据模型、状态机、恢复与权限的底图，不提前指定数据库、接口或具体实现。

本文是对象、责任、状态和生命周期的共同基线；《核心对象模型》提供更适合产品阅读的对象词典，本文件负责更严格的边界和生命周期关系。两者重叠时，以本文件的生命周期与责任表述为准。

## 一、最小对象层级

```text
账户
└── 工作区
    ├── 文件夹与资源
    ├── 普通会话
    │   ├── 会话主 Agent
    │   ├── 会话成员关系
    │   └── 任务
    │       ├── 子任务
    │       ├── 任务会话或关联会话
    │       ├── 多个回合
    │       ├── 一个或多个运行实例
    │       └── 产物与运行证据
    └── 工程
        ├── PM 关系
        ├── 项目成员关系
        ├── 默认工作位置与多个资源关联
        ├── 工程任务与成员任务会话
        ├── 共享事实账本
        ├── 产物登记
        └── 权限、成本与治理记录
```

工程可以关联工作区中的多个文件夹和资源，但工程不是文件夹的别名。主资源或默认工作位置只是用户进入工程时的默认入口，不是工程的资源数量上限或唯一写入位置。Agent 身份可以参与多次任务和运行，但身份不是永久运行的进程。

## 二、对象定义与权威来源

| 对象 | 产品定义 | 建议权威来源 | 不能等同于 |
|---|---|---|---|
| 账户 | 用户偏好、模板和账户级默认值范围 | Magic 账户记录 | 当前会话或当前工作区 |
| 工作区 | 文件、代码、会话和基础权限的资源边界 | Magic 注册记录与真实文件系统 | 工程或文件夹 |
| 文件夹 | 工作区内的目录资源 | 文件系统加 Magic 元数据 | 工程组织 |
| 资源 | 可被工程、任务或运行实例引用和授权的本地或外部对象 | Magic 资源登记与外部系统事实 | 工程、文件夹或某个 Agent |
| 工程资源关联 | 工程与资源之间的用途、默认入口、动作、范围、版本和成本关系 | Magic 工程资源关联记录 | 资源所有权或 Agent 身份 |
| 执行目标 | TaskAttempt 实际使用的资源版本、目录、Checkout、Branch、Worktree 或其他隔离空间 | Magic 映射加底座资源事实 | 任务、会话或分支本身 |
| 变更集 | 一次执行对资源产生的文件/对象变化、版本引用和检查证据 | Magic 变更登记加资源版本记录 | 任务最终状态或合并结果 |
| 合并任务 | 检查变更、解决冲突并将变更纳入目标主版本或正式资源的独立工作 | Magic 合并任务记录加资源操作事实 | 创建分支的 Agent 或普通任务完成 |
| 工程 | 经用户确认建立的长期目标与组织边界 | Magic 工程记录 | 大型会话、文件夹、工作区 |
| 会话 | 用户或 Agent 围绕连续目标交流和工作的范围 | Magic 会话记录，绑定底座会话 | 单个任务或单次运行 |
| 任务 | 有目标、当前责任人和统一最终状态的可交付工作；草拟工作项正式派发前由创建者或 PM 维护 | Magic 任务账本 | 用户的一条消息、一次 Run |
| 任务计划与步骤 | 任务内可见的阶段、顺序、进度、前置条件和验收提示 | Magic 任务账本 | 正式子任务、Agent 身份或 OpenCode Run |
| 子任务 | 从父任务拆出的可追踪责任单元 | Magic 任务账本 | 临时内部思考步骤 |
| 任务会话 | 围绕某项任务保持交流和上下文的会话关联 | Magic 关联记录 | Agent 身份本身 |
| 回合 | 一次输入及其响应过程的记录单元 | 追加式会话记录 | 完整任务或长期责任 |
| 运行实例 | 某个任务或回合的一次实际执行尝试 | OpenCode 运行证据加 Magic 映射；若底座缺少稳定运行 ID、状态或事件，则由 Magic 建立权威运行实例记录 | Agent 身份、任务最终状态 |
| Agent 身份 | 有稳定 ID、角色、归属和生命周期的参与者 | Magic 身份目录 | 模型进程、单次 Run |
| 临时执行 Agent | 服务一次局部工作、任务结束后默认不保留成员关系的完整 Agent 会话；临时描述生命周期，不描述能力等级 | 当前任务的参与关系、独立会话与运行证据 | 弱化工具、弱化上下文或不完整 Agent |
| 会话成员 | 完整 Agent 身份/会话与某个协作范围的持续成员关系 | Magic 会话成员记录 | 固定职业或永久工程归属 |
| 项目成员 | 完整 Agent 身份/会话与某一工程的成员关系，任务角色可动态变化 | Magic 工程成员记录 | 相同角色模板创建的其他成员 |
| 借调成员 | 来源 Agent 身份与目标工程建立的临时成员关系 | Magic 借调关系、隔离任务会话与授权记录 | 两个工程自动共享完整记忆、权限和任务 |
| PM | 工程中的特殊协调责任关系 | Magic 工程角色记录 | 永久在线进程、每个任务责任人 |
| 共享事实 | 有来源、范围、状态和版本的项目共识候选或结论 | Magic 事实账本 | 文件、摘要、私有记忆 |
| 产物 | 可访问、验证、验收和追踪来源的交付结果 | Magic 产物登记加真实资源 | 工具调用成功或模型输出 |
| 权限授予 | 某主体对某资源执行某动作的有范围、时效授权 | Magic 审批账本加底座拦截记录 | 角色名称或工程成员身份本身 |

## 三、责任模型

### 3.1 唯一当前责任人

每个进入正式账本并允许执行的任务任一时刻只有一名当前责任人。草拟工作项尚未派发时，由创建者或 PM 承担临时维护责任；它只能被编辑、补充或等待派发，不能在无人负责时开始执行。正式派发后，任务必须明确唯一当前责任人；子任务也必须在开始执行前明确自己的当前责任人。PM、协作者、审阅者和运行实例可以参与任务，但不能形成多个互相冲突的最终收口主体。

```text
任务当前责任人
├── 对任务目标和统一最终状态负责
├── 汇集协作者、运行与产物证据
├── 说明完成、部分完成、失败、等待、停止或取消
└── 需要移交时发起显式责任转移
```

责任移交至少记录：原责任人、新责任人、原因、时间、目标与约束、已完成结果、未完成事项、在飞运行、待审批项和已发生副作用。

### 3.2 PM 的责任

PM 对工程目标、计划、优先级、依赖、项目级风险和汇总负责。PM 不因为是 PM 就自动成为所有成员任务的当前责任人，也不能通过汇总把成员的失败改写成成功。

### 3.3 用户直达成员

工程内直达成员产生的新任务统一写入工程任务账本，并明确归属和当前责任人。它若影响工程目标、计划、资源、文件、预算或交付，还必须通知 PM 并形成计划影响判断。通知不等于所有行为都必须等待 PM 审批。

## 四、任务、回合与运行的分层

```text
任务：产品承诺与责任单位
├── 回合：输入和响应记录
├── 子任务：可单独追踪的责任分解
└── 运行实例：一次真实执行尝试
    ├── 模型生成
    ├── 工具调用
    ├── 审批等待
    └── 文件或外部副作用
```

关键规则：

- 一个任务可以跨多个回合完成。
- 一个任务可以因重试、恢复或模式移交拥有多个运行实例。
- 运行成功只代表一次执行尝试结束，不自动代表任务完成。
- 运行失败也不必然代表任务最终失败，责任人可以基于已有结果重试、降级或部分交付。
- 用户停止运行后，任务可以进入停止、等待决策、部分完成或取消，不能由底座状态直接猜测。
- 任务可以拥有轻量计划和多个计划步骤；计划步骤用于向用户展示和推进工作，不自动成为正式子任务。
- 计划步骤可以动态调整；涉及目标、范围、验收标准、正式依赖、派发或责任人的变化必须保留计划版本或变更记录。
- 长任务可以由主 Agent 自动进入计划推进并持续展示进度，但计划推进不等于自动进入 CEO 或建立工程组织。

## 五、建议状态分层

### 5.1 任务状态

以下是产品语义候选，最终枚举在技术会议后冻结：

```text
草拟 → 待执行 → 执行中 → 等待
                   ├── 已完成
                   ├── 部分完成
                   ├── 失败
                   ├── 已停止
                   └── 已取消

终态或停止状态 → 归档
等待 / 已停止 / 失败 / 部分完成 → 经明确操作重新打开
```

“等待”必须说明等待谁、等待什么、从何时开始以及如何继续。“已停止”表示执行被终止但任务历史与已有结果保留；“已取消”表示不再继续履行该任务目标，但不等于撤销副作用。

### 5.2 运行实例状态

```text
已创建 → 排队 → 运行中
                 ├── 等待审批
                 ├── 已暂停
                 ├── 已完成
                 ├── 失败
                 └── 已中断
```

运行实例状态由底座事件提供证据，Magic 负责映射和收敛。技术团队必须验证 OpenCode 的真实状态，而不是直接采用本候选枚举。

### 5.3 成员关系与工作负载状态

```text
成员关系：建议加入 → 已加入 → 暂停职责 → 已停用 → 已归档
工作负载：空闲 / 工作中 / 等待 / 阻塞
```

成员关系是长期、可持久化的组织状态；工作负载是根据当前任务形成的运行投影，两者不能合并为一个状态机。工作中或空闲都不代表底层进程永久存在。停用不删除身份、历史任务、事实贡献和产物。

### 5.4 共享事实状态

```text
候选 → 已确认
  └────→ 受争议
已确认 / 受争议 → 已撤销或已废弃
```

所有变化保留来源、版本、操作者、时间、原因和受影响范围。新的事实不能物理覆盖旧版本。

### 5.5 产物状态

```text
草稿 → 待验收 → 已接受
  ├── 验证失败
  ├── 被替代
  └── 已归档
```

产物存在不等于任务已经成功；任务取消也不自动删除已经形成的产物。

### 5.6 资源与变更状态

资源、变更和合并不能共用任务状态：

```text
资源：已登记 / 可访问 / 状态过期 / 不可访问 / 已撤销 / 有冲突
修改空间：准备中 / 工作中 / 待检查 / 有冲突 / 已合并 / 已放弃
变更集：未检查 / 检查中 / 检查通过 / 检查失败 / 已接受 / 被拒绝
合并任务：待处理 / 合并中 / 冲突阻塞 / 已合并 / 合并失败 / 已回退
```

代码、文本和配置等可版本化资源的重叠修改，首选独立修改空间和 Git 变更；branch、worktree、checkout、补丁或副本是底层实现选项。非 Git 资源使用快照、版本、锁、草稿、测试环境、审批或补偿机制。任务完成、变更可合并、变更已进入主版本和最终验收必须分别记录。

## 六、生命周期边界

| 对象 | 创建 | 复用与恢复 | 停止、失败或停用 | 归档与历史 |
|---|---|---|---|---|
| 工程 | 用户明确确认后创建 | 可暂停后恢复或归档后重开 | 工程不会因单个任务失败自动结束 | 保留目标、成员、任务、事实、产物和治理记录 |
| 会话 | 用户或获授权流程创建 | 断连后继续；能否跨进程恢复待核查 | 单次运行失败不结束会话 | 可归档和重开，历史保留策略待定 |
| 任务 | 用户、PM 或获授权 Agent 创建 | 可等待、重试、重新打开 | 必须由责任人形成诚实状态 | 归档不删除运行、事实和产物来源 |
| 运行实例 | 执行任务时按需创建 | 恢复原实例或建立新实例取决于底座证据 | 中断不自动撤销副作用 | 作为运行证据保留，不承担长期身份 |
| Agent 身份 | 用户确认或按授权规则创建 | 可跨其允许范围参与多次任务 | 停用后不能接收新任务 | 历史贡献和产物继续存在 |
| 会话成员 | 用户或获授权 Agent 创建完整会话并建立成员关系 | 在授权的会话、任务和下属协作中复用 | 离开或停用不删除身份历史 | 可挂接工程；跨工程借调属于后续扩展，边界单独记录 |
| 项目成员 | 在单一工程内建立成员关系 | 在本工程授权范围跨会话与任务复用 | 停用不删除私有记忆和历史，访问权按策略回收 | 首版不直接服务其他工程；未来借调必须默认隔离上下文 |
| 借调成员 | 后续扩展中由来源工程同意并在目标工程建立关系 | 目标工程的授权任务和隔离工作会话 | 借调结束后解除目标关系 | 不自动合并来源与目标工程私有记忆 |
| PM | 工程建立或交接时确认 | 同一工程同一时间只有一名当前 PM；可有助手或代理协作 | 可暂停职责或显式交接；失联时进入待接管，不静默生成第二个当前 PM | 历任 PM、交接记录与决策记录保留 |
| 共享事实 | 从用户表达、任务、产物或成员发现中形成 | 按范围被任务引用 | 可争议、撤销、废弃，不物理删除历史 | 归档工程时一并保留 |
| 产物 | 运行、任务或人工操作产生并登记 | 可继续编辑、验证、替代和引用 | 失败产物仍可保留用于审计 | 按资源和工程策略归档 |
| 权限授予 | 用户批准或策略预授权 | 在主体、资源、动作、范围和时效内复用 | 可拒绝、过期、撤销；副作用不可假装回滚 | 审批和使用记录保留 |
| 资源 | 工作区或外部系统登记 | 被多个工程、任务和会话按授权引用 | 不因被引用就共享权限或写入责任 | 资源事实和版本记录保留 |
| 工程资源关联 | 工程建立或用户添加资源时创建 | 按任务和权限范围复用 | 可解除或暂停；不删除资源和历史 | 关联、授权和版本历史保留 |
| 执行目标/变更集 | TaskAttempt 获得资源授权时创建 | 可在重试或检查中继续引用 | 冲突、失败或放弃不删除已有证据 | 版本、范围、来源和检查记录保留 |
| 合并任务 | 变更集需要进入目标主版本或正式资源时创建 | 可等待检查、审批或冲突处理 | 失败或拒绝不改写源任务的运行事实 | 合并、回退和目标版本保留 |

## 七、模式变化与对象影响

| 行为 | 任务 | 会话 | Agent 身份与成员 | 工程 | 运行实例 |
|---|---|---|---|---|---|
| 代理内部调用协作者 | 不改变产品模式，可产生子任务 | 不改变默认方式 | 可使用临时 Agent 或会话成员 | 不自动建立 | 按需创建 |
| 长任务进入计划推进 | 任务增加计划和步骤展示 | 不改变默认方式 | 不自动创建成员 | 不自动建立 | 步骤可关联一个或多个运行 |
| 当前任务使用 CEO | 当前任务显式采用团队治理 | 默认方式不必改变 | 复用或增加当前会话协作者 | 不自动建立 | 新运行按切换契约创建 |
| 修改会话默认方式 | 当前执行默认不追溯改变 | 影响后续新任务 | 不删除成员关系 | 无影响 | 不自动中断 |
| 普通工作转工程 | 需确定哪些任务进入工程 | 可成为 PM 主会话或保留来源会话 | 成员迁移逐项确认 | 用户明确创建 | 在飞运行不静默迁移 |
| CEO 回到代理 | 后续新一轮工作按代理职责继续 | 后续恢复代理默认 | 会话成员不删除，CEO 记录保留 | 工程内同样适用 | 不改写已经开始的旧运行 |

## 八、信息权威与冲突

建议使用以下判断顺序，而不是简单以“最新时间”覆盖：

1. 用户对目标、范围和取舍最新、明确且有权作出的决定；
2. 经确认、仍有效的项目事实和可复现客观证据；
3. 经验收的任务结果和产物证据；
4. 候选事实、未验收产物和运行结果；
5. 会话摘要、成员私有记忆和模型推断。

若信息之间冲突，应记录冲突并向责任人或用户升级。用户改变既有目标或取舍时，应产生新的决定版本和影响分析，而不是改写历史；用户对代码状态、测试结果或文件内容的描述若与可复现证据冲突，应先展示和核验，不能静默覆盖客观事实。

## 九、权限与副作用边界

权限至少需要表达：

```text
主体 + 资源 + 动作 + 范围 + 时效 + 成本上限 + 副作用等级 + 授权来源
```

需要分开：

- 模型是否建议执行；
- Magic 策略是否允许执行；
- OpenCode 工具层是否实际放行；
- 动作是否已经产生副作用；
- 副作用是否可撤销或需要补偿。

工程成员身份不能自动获得 PM 或账户的全部权限。角色模板也不能携带跨工程的隐式授权。

### 9.1 U-09 默认授权与成本治理

- 工作偏好按“当前任务 > 当前会话 > 当前工程或工作区 > 账户 > 系统默认”继承；明确选择只影响后续工作，不追溯改写历史任务。
- 权限采用 `allow / ask / deny`，并记录主体、资源、动作、范围、时效和授权来源。下级只能缩小权限，不能突破上级硬边界；角色名称不自动授予更高权限。
- Agent 向下派发只能传递自己拥有且允许转授的权限、预算和派发深度，默认不传递原始凭据或全部私有记忆。创建下属 Agent 不自动扩大预算或副作用权限。
- 预算记录上限、已预留、实际消耗、剩余额度和成本归属。超限时停止继续派发或等待有权主体批准。
- 权限撤销影响后续工具调用、新 Agent 创建和新的信息访问，不改写已经发生的运行、文件写入、费用和外部副作用。
- 首版默认禁止跨工程直接调用和隐式借调；未来借调必须使用独立关系、任务、会话、预算、责任和最小上下文。

### 9.2 U-12 权限模式与审批

用户界面提供“请求批准、当前范围内自动处理、完全访问当前工程”三档入口。三档入口只简化用户选择，不合并底层治理维度：资源访问边界、审批策略、动作风险、预算范围、环境范围、授权有效期和授权来源必须分别记录。

“当前范围内自动处理”默认作用于当前任务，高风险动作仍需询问；扩展到当前会话或工程必须明确显示范围。“完全访问当前工程”只放宽当前工程的文件和网络边界，不自动扩大到其他工程、账户、私有记忆、原始凭据或生产环境。上级硬边界、系统禁止项和预算上限始终有效。

低风险且可逆的读取、计划、独立修改空间、Git 分支/工作树、本地测试和本地提交可以自动执行。合并主版本、远程推送、共享资源修改和超预算动作按策略处理；生产部署、生产数据写入、删除重要资源、付费和对外发布必须确认或首版禁止。审批暂停时必须保留运行事实，恢复不能重复执行已经发生的副作用。

## 十、必须通过场景验证的生命周期

技术方案至少要演示并记录以下场景：

1. 普通代理任务调用临时 Agent，任务完成后不产生长期成员。
2. 会话成员在同一会话的后续任务中继续工作，新会话不能直接调用它。
3. 单次 CEO 完成后回到代理默认，目标、产物和成员关系仍连续。
4. 旧运行保持原有事实；用户在后续新一轮工作中启用 CEO，已有结果、上下文、排队输入和责任关系能够连续处理。
5. PM 派发成员任务，成员失败或部分完成，PM 汇总时仍呈现真实状态。
6. 用户直达成员产生冲突任务，任务入账、PM 知情、责任和优先级可解释。
7. 用户、CEO、PM 或组长动态创建完整 Agent 会话，并将其挂接为会话成员或项目成员；角色、权限、上下文、责任和结束条件可追溯且不跨项目泄露。跨工程借调作为后续扩展单独验证。
8. 项目事实被争议或撤销，受影响任务收到变化且历史版本仍可追溯。
9. 文件被两个成员并发修改，冲突不被静默覆盖。
10. 运行断连、事件重复或进程重启后，任务、产物和审批状态最终收敛。
11. 用户停止运行后，已写文件或外部副作用被准确展示而非假装撤销。
12. PM 交接后，在执行任务、待审批项、资源变更和项目历史仍有明确责任归属。

## 十二、首次四方技术对齐补充

2026-08-29，Magic AI 核心总监、AgentCore 项目架构技术总监、OpenCode 项目架构技术总监和 OpenCode 前端技术总监完成首次三轮对齐。四方状态为“有条件一致”：产品方向通过，首版技术冻结仍受底座收敛证据约束。

### 12.1 首版候选对象关系

首版采用以下产品层候选关系，具体底座绑定必须经过实机验证：

```text
MagicSession 1-N MagicTask
MagicTask 1-N Turn
MagicTask 1-N TaskAttempt
TaskAttempt 1-1 RootExecutionBinding
RootExecutionBinding 1-1 canonical OpenCode Session（若有稳定 ID）
TaskAttempt 1-N 底座根运行与子运行
```

若底座没有稳定运行 ID，`RootExecutionBinding` 必须由 Magic 标记为 synthetic，并保存 request ID、底座 Session 标识、事件 cursor、来源 runtime 和版本。synthetic binding 不能伪装成底座稳定身份。

首版不开放 Magic 会话共享 OpenCode Session、跨工程共享底座 Session 或身份、任意任务跨 Session 动态迁移，以及将 child session 直接冒充 Magic 子任务。

### 12.2 责任与状态补充

CAPTAIN 是一次 Attempt 内的运行编排角色，不是 PM；PM 是工程级长期协调责任，不是所有成员任务的当前责任人。普通代理由会话主 Agent 对用户侧收口，工程成员对被分派任务负责，临时 worker 只负责局部运行。失败、停止或下级运行失败不会自动改变 Magic 当前责任人。

U-02 已由用户确认采用：每个正式任务在任何时候都明确一个当前负责人。负责人不一定亲自执行，也不一定负责派发或接收所有结果；他负责根据真实证据，让任务最终形成一个诚实、清楚、可以继续处理的状态。任务等待输入、依赖、审批或策略处理时，负责人仍然保留，系统必须说明正在等待什么、等待谁以及如何继续。失败、停止、断连、重试和下级失败不会自动改变负责人。只有经过授权的主体明确完成移交，并记录原因、已有结果、未完成事项、待审批项和已发生副作用后，负责人才能改变。

Task、TaskAttempt/Run、Connection/Sync、Approval、Artifact、Fact 和 Responsibility 必须保持独立。底座运行完成、事件结束、工具成功、文件写入或连接断开都不能直接改写任务最终状态；任务必须由 Magic 责任人依据证据形成统一且可解释的收口。

U-03 已由用户确认采用：Magic 任务账本是 Magic 产品任务关系、进度、责任和最终收口状态的权威记录，但不覆盖 OpenCode 或 AgentCore 的底层执行事实。OpenCode/AgentCore 负责记录运行开始、运行结束、工具结果、测试结果、异常、中断和恢复等事实；Magic 不得改写、伪装或否认这些事实。普通代理中，Magic 任务状态可以直接映射或接近一次底层运行；CEO 或工程模式中，一个 Magic 任务可能组织多个底层运行，运行结束只说明一次执行尝试结束，不能自动说明父任务整体完成。当前责任人依据运行事实、依赖、交付和验收信息，组织多个结果并形成产品任务状态。

U-04 已由用户确认采用：任务模式决定当前工作如何组织，会话默认决定该会话后续新任务如何开始，工程默认只为新会话提供初始偏好；任务计划推进是所有任务都可使用的任务级能力。长任务可以由主 Agent 自动生成轻量计划并展示当前步骤、下一步和阻塞，低风险步骤可自动连续执行；计划步骤不自动等同正式子任务、Agent 或 OpenCode Run。

### 12.3 事实、记忆和动态成员关系补充

transcript 是会话或运行证据，memory 是有范围的上下文材料，NoteWall 是协作材料，文件是工作区资源，Artifact 是有来源和验收关系的交付登记，Fact 是有来源、版本、范围、确认者和争议/撤销状态的产品对象。它们不能互相自动升级。

U-07 已确认：所有参与工作的 Agent 核心都是完整 Agent，会话可以由用户、CEO、PM、组长或获授权成员动态创建。临时、会话、项目和借调描述的是成员关系，不是能力等级；调研、架构、实现、测试等角色由派发者按任务分配。挂接项目或跨工程借调时建立新的关系和授权记录，不自动迁移完整 transcript、私有 memory、NoteWall 或全部权限；可共享内容必须有来源、范围和撤销路径。

### 12.4 唯一冻结阻塞

四方共同确认的首版技术阻塞是：锁定 OpenCode runtime、commit/tag 和 protocol/client contract 后，验证 TaskAttempt 在断连、进程重启、重复或乱序事件、重试、停止、审批和已发生外部副作用组合场景下的可重复最终收敛。该验证要能还原任务状态、当前责任人、Attempt 列表、审批、产物来源和已发生副作用。

在该证据完成前，产品模型和 Adapter 原型可以继续，未纳入首版的多层 PM、完整圆桌、跨工程、多用户多端和永久 Agent 不构成首版冻结阻塞；但也不得被包装成已支持。

## 十三、团队画布预留关系

用户已确认：未来工程团队可以在一个团队画布中展示真实工作。画布的核心不是展示更多 Agent，而是让用户能够看懂“谁在做什么、任务派给谁、结果给到谁、谁对结果负责，以及任务依赖谁”。

画布需要分别表达以下关系：`Assignment` 表示谁把任务派给谁；`Execution` 表示谁正在执行哪个任务或尝试；`Delivery` 表示产物、汇报或事实交给谁；`Responsibility` 表示任务唯一当前责任人；`Dependency` 表示任务之间的依赖。OpenCode 的 parent/child Session 最多证明底层运行层级，不能直接证明这些 Magic 关系。

首版只需预留这些关系的稳定标识和可追踪记录，不要求交付自由拖拽画布、全量 DAG、多人实时编辑、跨工程连线或无限层级团队。画布只能读取 Magic 任务账本和责任投影，不能建立第二套任务真相。
