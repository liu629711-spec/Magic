# Magic 产品路线图

> 本文是 Magic 重构阶段的产品路线图，不是工程排期。优先级应根据真实使用反馈、用户行为和主循环瓶颈持续调整。

本文只表达产品验证顺序、进入条件和后置方向，不承诺同时实现所有阶段，也不替代技术计划。当前阶段的首版范围、产品门槛和 OpenCode 核查要求，以《Magic 最终产品裁定与技术会议输入》及《技术会议议题与裁定表》为准。

## 一、路线图判断标准

每个方向至少回答：

- 它解决什么用户问题
- 它服务哪一种工作模式
- 它是否改善模式切换的连续性
- 它是否增加用户管理负担
- 它依赖哪些 OpenCode 或 Magic 能力
- 做到什么程度可以验证价值
- 哪些内容明确不在本阶段范围内

## 二、阶段 0：产品基线与架构边界

状态：当前阶段。

目标：让新项目先拥有一致的产品语言和清晰的重构边界。

范围：

- 确认代理与 CEO 两种执行方式，以及工程组织形态的产品定义
- 建立会话主 Agent、会话成员、项目 PM 与项目成员的生命周期底图
- 确认“建议可以自动，长期建立必须确认”的原则
- 明确 OpenCode 与 Magic 的职责边界
- 建立跨模式共享对象模型
- 锁定 OpenCode 版本并实机识别可以直接复用、需要适配和需要补建的能力
- 列出需要 Magic 补足的产品能力
- 完成首版所需的 P0 任务责任、状态、模式作用域、执行中移交、共享事实和权限契约

完成标准：

- 新需求可以判断属于哪种模式和哪类对象
- 产品文档不再把所有任务默认描述成 Multi-Agent
- 代理模式不被描述成低级模式
- 使用子 Agent 不被错误等同于进入 CEO 模式
- 会话成员与工程成员的归属和复用范围清楚
- 工程模式不会在未对齐前被实现细节绑死
- OpenCode 关键能力拥有版本、复现方式、限制和证据结论
- 影响首版的待用户裁定项已经完成裁定并同步回专题文档

## 三、阶段 1：代理模式落地

目标：以 OpenCode 为基础，形成自然、可靠、低管理成本的 Agent 工作体验。

重点：

- 用户可以直接提出目标并让 Agent 持续执行
- 文件、代码、工具和验证能力稳定可用
- 用户可以补充要求、停止、继续和查看结果
- Agent 对部分完成、失败和等待状态诚实汇报
- 内部步骤不会强迫用户管理
- 主 Agent 可以派发临时 Agent，并在当前会话内复用有价值的会话成员
- 新会话不会隐式继承其他会话的成员身份和私有上下文

首版不包含：

- 自动建立长期 Agent 团队
- 强制显示完整的多 Agent 组织图
- 复杂的工程组织面板

验收重点：

- 用户能否不学习编排概念就开始工作
- Agent 是否能在工程中连续完成真实任务
- 用户是否清楚 Agent 做了什么和还缺什么
- 子 Agent 派发是否提升执行效果，同时没有增加用户管理负担
- 复用会话成员是否比反复创建新 Agent 更有连续性

## 四、阶段 2：CEO 模式闭环

目标：在同一工作台中提供用户可主动选择的显式团队协作，并让团队在当前会话内持续复用。

重点：

- 用户可以主动切换到 CEO 模式
- 同一个会话主 Agent 可以从代理工作转为承担 CEO 职责
- CEO 可以复用已有会话成员，并按需要增加成员
- 会话成员可以在当前会话的后续任务中继续工作
- 协作过程可见但不要求用户逐项管理
- 支持必要的验证、辩论、检查点和统一交付
- 可以从代理模式继承上下文继续工作
- 可以在 CEO 模式中回到代理模式处理后续任务

首版不包含：

- 完整的长期 Agent 组织
- 无限层级和无限队员
- 自动把会话成员固化为工程项目成员
- 跨会话调用会话成员

验收重点：

- 用户是否知道何时值得进入 CEO 模式
- 团队协作是否真正减少用户拆解负担
- 用户是否能区分“正在协作”和“需要我管理”
- 用户是否理解返回代理后，已有会话成员仍然可以被复用

## 五、阶段 3：模式建议与连续切换

目标：让用户可以自主选择，同时获得适度的产品引导。

重点：

- 系统识别适合改变工作方式或建立工程组织的信号
- 以非阻塞方式建议切换
- 接受建议后不丢失上下文
- 拒绝建议后可以继续当前工作
- 用户可以设置默认执行方式
- 用户可以关闭主动工作方式建议，而不失去手动入口
- 代理对话可以只为一项任务临时调用 CEO
- 单次 CEO 完成后恢复对话默认方式，但不解散会话成员
- 账户、工作空间或工程、对话、单次任务形成分层默认与覆盖关系
- 工程模式的进入始终明确确认

验收重点：

- 建议是否帮助用户而不是打断用户
- 用户是否感到模式是自然变化而不是产品跳转
- 是否出现模式切换过于频繁的问题
- 无法无损移交时，用户是否理解影响并能选择继续、暂停、重新规划或回退

## 六、阶段 4：工程模式探索

目标：验证长期 Agent 组织是否形成独立且可持续的产品价值。

建议顺序：

1. 工程实体、项目专属组织和生命周期
2. 项目 PM 主入口及 PM 自动创建成员任务会话
3. 项目成员身份、职责、权限和多会话关系
4. 项目成员独立记忆与项目共享信息
5. PM 派发、成员汇报、用户直达和计划同步
6. 成员自主调用临时 Agent 或组织 CEO 协作
7. 圆桌会议、跨团队依赖与冲突处理
8. 角色模板、团队演化和跨工程协作

首版原则：

- 从一个真实工程场景开始
- 先验证少量稳定职责
- 允许用户调整团队，而不是一次生成完整组织
- 每个工程默认创建自己的 PM 与成员实例
- 工程可以只有 PM，也可以从少量核心成员开始
- 角色模板可以复用，但不同工程的成员身份和项目记忆默认隔离
- 先让组织可理解、可停止、可交付，再扩大规模

## 七、远期方向

以下内容暂不进入近期承诺：

- 跨工程共享同一个 Agent 身份
- 跨工程专家邀请与上下文隔离
- Agent 团队模板生态
- Agent 的跨工程身份市场
- 自动化组织演进
- 超大规模多层 Agent 网络

## 八、路线图维护规则

- 产品方向变更先更新总纲和相关模式文档
- 单个功能不能绕过模式边界直接进入实现
- 暂未验证的工程模式设想保留为问题，不写成已确定能力
- 已经确认的 Agent 归属和生命周期边界必须同步到所有模式文档
- 任何新增协作能力都要说明它减少了什么用户负担
- 路线图只保留产品方向，工程内部任务放入独立技术计划
- 首版范围、P0 裁定、OpenCode 核查和开发冻结门槛以《Magic 最终产品裁定与技术会议输入》为准
