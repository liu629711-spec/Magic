# Magic 产品路线图

> 本文是 Magic 重构阶段的产品路线图，不是工程排期。优先级应根据真实使用反馈、用户行为和主循环瓶颈持续调整。

## 一、路线图判断标准

每个方向至少回答：

- 它解决什么用户问题
- 它服务哪一种工作模式
- 它是否改善模式切换的连续性
- 它是否增加用户管理负担
- 它依赖哪些 OpenCode 或 Magic 能力
- 做到什么程度可以验证价值
- 哪些内容明确不在本阶段范围内

## 二、阶段 0：产品基线与架构边界

状态：当前阶段。

目标：让新项目先拥有一致的产品语言和清晰的重构边界。

范围：

- 冻结三种工作模式的产品定义
- 冻结“建议可以自动，长期建立必须确认”的原则
- 明确 OpenCode 与 Magic 的职责边界
- 建立跨模式共享对象模型
- 识别可以直接复用的 OpenCode 能力
- 列出需要 Magic 补足的产品能力

完成标准：

- 新需求可以判断属于哪种模式和哪类对象
- 产品文档不再把所有任务默认描述成 Multi-Agent
- 代理模式不被描述成低级模式
- 工程模式不会在未对齐前被实现细节绑死

## 三、阶段 1：代理模式落地

目标：以 OpenCode 为基础，形成自然、可靠、低管理成本的 Agent 工作体验。

重点：

- 用户可以直接提出目标并让 Agent 持续执行
- 文件、代码、工具和验证能力稳定可用
- 用户可以补充要求、停止、继续和查看结果
- Agent 对部分完成、失败和等待状态诚实汇报
- 内部步骤不会强迫用户管理

首版不包含：

- 自动建立长期 Agent 团队
- 强制显示多 Agent 组织图
- 复杂的工程组织面板

验收重点：

- 用户能否不学习编排概念就开始工作
- Agent 是否能在工程中连续完成真实任务
- 用户是否清楚 Agent 做了什么和还缺什么

## 四、阶段 2：CEO 模式闭环

目标：在同一工作台中提供用户可主动选择的任务级团队协作。

重点：

- 用户可以主动切换到 CEO 模式
- CEO 可以组织临时队员完成复杂任务
- 协作过程可见但不要求用户逐项管理
- 支持必要的验证、辩论、检查点和统一交付
- 可以从代理模式继承上下文继续工作
- 可以在 CEO 模式中回到代理模式处理后续任务

首版不包含：

- 完整的长期 Agent 组织
- 无限层级和无限队员
- 自动把临时队员固化为长期 Agent

验收重点：

- 用户是否知道何时值得进入 CEO 模式
- 团队协作是否真正减少用户拆解负担
- 用户是否能区分“正在协作”和“需要我管理”

## 五、阶段 3：模式建议与连续切换

目标：让用户可以自主选择，同时获得适度的产品引导。

重点：

- 系统识别适合升级的信号
- 以非阻塞方式建议切换
- 接受建议后不丢失上下文
- 拒绝建议后可以继续当前工作
- 工程模式的进入始终明确确认

验收重点：

- 建议是否帮助用户而不是打断用户
- 用户是否感到模式是自然变化而不是产品跳转
- 是否出现模式切换过于频繁的问题

## 六、阶段 4：工程模式探索

目标：验证长期 Agent 组织是否形成独立且可持续的产品价值。

建议顺序：

1. 工程实体和生命周期
2. 长期 Agent 的职责和身份
3. 独立记忆与共享信息
4. 任务队列和层级派发
5. 汇报、停止和恢复
6. 圆桌会议与冲突处理
7. 团队模板和自动建队

首版原则：

- 从一个真实工程场景开始
- 先验证少量稳定职责
- 允许用户调整团队，而不是一次生成完整组织
- 先让组织可理解、可停止、可交付，再扩大规模

## 七、远期方向

以下内容暂不进入近期承诺：

- 多工程之间的 Agent 组织复用
- Agent 团队模板生态
- Agent 的跨工程身份市场
- 自动化组织演进
- 超大规模多层 Agent 网络

## 八、路线图维护规则

- 产品方向变更先更新总纲和相关模式文档
- 单个功能不能绕过模式边界直接进入实现
- 暂未验证的工程模式设想保留为问题，不写成已确定能力
- 任何新增协作能力都要说明它减少了什么用户负担
- 路线图只保留产品方向，工程内部任务放入独立技术计划
