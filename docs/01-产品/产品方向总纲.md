# Magic 产品方向总纲

> 文档层级：方向基线。本文优先回答 Magic 为什么存在、代理/CEO/工程如何组合，以及哪些长期边界不可违反；不承载逐项技术方案、字段设计或会议过程。

## 一、文档目的

本文是 Magic 的产品方向基线，用于统一产品定位、工作模式、用户心智、核心边界和后续取舍。

本文只回答产品方向问题，不替代 OpenCode 的技术文档，也不提前规定工程模式的全部实现细节。凡是尚未经过产品对齐的内容，必须明确标注为待决策，不得从设想直接变成契约。

## 二、产品定位

Magic 是一个建立在 OpenCode 之上的统一 AI 工作台。

它既可以让用户把工作直接交给一个强大的会话主 Agent，也可以让主 Agent 以 CEO 职责组织一支在当前会话内可复用的 Agent 团队，还可以支持用户围绕长期项目建立由项目专属 PM 管理的长期组织。用户可以在开始工作时直接选择代理或 CEO，也可以在工作过程中自然改变工作方式。

一句话定位：

> **简单的事，直接做；复杂的事，组织做；长期的事，建成一支持续工作的 Agent 团队。**

Magic 的核心价值不是把每个任务都变成多 Agent 协作，而是让用户能够在不同工作复杂度和持续周期下，自由选择合适的工作方式，并且在切换时不丢失上下文。

## 三、产品关系

OpenCode 是底层 Agent 执行基础，Magic 是建立在其上的产品与协作层。

### OpenCode 负责

以下是 Magic 对底座能力来源的职责划分，不代表当前 OpenCode 版本已经逐项通过实机核查：

- Agent 的直接执行能力
- 文件、代码和终端工作流
- 工具调用与上下文处理
- Agent 的连续工作过程
- 执行状态、修改和验证
- 底层会话与工作区能力

### Magic 负责

- 代理模式、CEO 模式和工程模式
- 用户选择与模式切换
- 会话主 Agent 对会话成员的派发、复用和协作治理
- 项目专属 PM、成员、成员会话和长期组织关系
- 多 Agent 的信息共享与协作可见性
- 用户决策点、交付汇报和团队治理
- 跨模式的身份、记忆、工作区和产物连续性

Magic 不应重新复制经实机确认可复用的 OpenCode 单 Agent 能力。重构的价值在于补足工作方式和协作层，让 OpenCode 的强执行能力可以自然地扩展为更高层的团队协作能力。具体可复用范围以锁定版本的能力核查结果为准。

## 四、三种产品形态

“代理模式、CEO 模式、工程模式”是面向用户的三个产品入口，但它们并不完全处于同一个层级：

- **代理模式与 CEO 模式是会话工作方式**：决定会话主 Agent 以直接执行为主，还是以显式组织团队为主。两者都可以调用子 Agent。
- **工程模式是长期组织形态**：决定一个项目是否拥有专属 PM、长期成员、成员会话、独立记忆、共享信息和持续治理。

因此，工程模式可以包含代理执行和 CEO 协作；普通工作空间中也可以同时存在多个代理对话和 CEO 对话。三者不是只能三选一的互斥状态。

### 代理模式

用户直接把目标交给会话主 Agent。主 Agent 可以自主理解、拆解、调用工具、修改文件、验证结果，也可以派发并复用当前会话的其他 Agent，不要求用户管理任务分工。

产品心智：

> **我交代一件事，你直接帮我做。**

代理模式是默认的自然入口，也是完整、强大的工作方式，不是低级模式或能力受限模式。

### CEO 模式

用户将目标交给当前会话主 Agent，由它承担 CEO 职责，复用或增加会话成员并显式组织协作。团队可以并行执行、互相验证、继续委派、进行辩论并形成统一交付。

产品心智：

> **我把目标交给 CEO，由 CEO 负责组织团队完成。**

CEO 模式强调会话级协作组织。CEO 可以按任务动态创建调研、架构、实现或评审等完整 Agent 会话；任务角色不是固定职业。“临时”只表示成员关系和保留方式，不表示工具或执行能力较弱。成员可以在授权范围内被其他会话挂接或借调，但不自动形成工程长期组织，也不自动共享私有记忆和权限。

### 工程模式

用户围绕一个持续建设的项目，建立由项目专属 PM 管理、成员可跨本工程会话和任务复用的 Agent 组织。

工程模式可以拥有 PM 主会话、项目成员、成员任务会话、职责、层级、独立记忆、共享信息、权限、任务队列、评审机制和圆桌会议。它不是普通会话多派几个 Agent 的简单放大，而是项目级长期组织系统。

产品心智：

> **我建立并经营一支可以长期建设这个工程的 AI 团队。**

工程模式是确定的产品方向，但在第一阶段只冻结产品边界和核心问题，不提前冻结完整的组织模型和实现方案。

## 五、模式关系

三种产品形态不是能力高低，也不是会员等级。它们分属两个可以组合的维度：

| 维度 | 选择 | 回答的问题 |
|---|---|---|
| 会话工作方式 | 代理模式 / CEO 模式 | 主 Agent 以直接执行为主，还是以显式团队治理为主？ |
| 长期组织形态 | 普通工作 / 工程模式 | 项目是否需要专属 PM、长期成员、跨会话记忆和持续治理？ |

组合关系如下：

| 所在范围 | 代理执行 | CEO 协作 |
|---|---|---|
| 普通工作 | 主 Agent 直接负责，可调用会话成员辅助 | 主 Agent 显式组织会话成员协作 |
| 工程模式 | PM 或项目成员直接负责，可调用辅助 Agent | PM 或项目成员显式组织项目成员及会话成员协作 |

用户也可以不启用工程模式，只通过多个对话、自己的命名和工作习惯组织一个长期工程。这是一条合法的自由路径。工程模式提供的是更强的组织自动化和连续性，不是开展长期工程的唯一许可。

## 六、用户选择原则

用户可以主动选择适合当前工作的执行方式与组织形态：

- 新用户或未表达偏好时，产品预选代理模式，但选择器始终可见、可改
- 用户开始一次新对话或新任务时，可以直接选择代理模式或 CEO 模式
- 用户可以设置自己的默认执行方式，也可以只为代理对话中的某一项任务临时调用一次 CEO
- 用户可以将某项工作放进已有工程，也可以明确创建工程模式
- 在工程模式内部，每个对话或任务仍可选择代理模式或 CEO 模式
- 代理模式可以调用和复用会话成员，不因使用子 Agent 自动变成 CEO 模式
- 会话成员是完整 Agent 会话，可在授权范围内被其他会话挂接；未经授权不得跨范围读取或执行
- 每个工程默认拥有自己的 PM 与成员关系；固定角色只是启动模板，相同模板不等于相同 Agent
- 项目可以动态创建、保留和借调成员，跨工程关系必须隔离任务、上下文、权限、责任和成本
- 一个工程可以包含多个职责或任务范围不同的协作团队
- 系统可以根据上下文识别出更合适的执行方式或组织方式并提出建议
- 用户可以在设置中关闭主动工作方式建议，且不影响任何手动入口
- 系统不得未经用户确认自动建立长期工程团队
- 系统不得因为任务复杂就强制用户进入 CEO 模式
- 用户拒绝建议后，当前工作继续按原模式进行

“建议切换”是辅助，不是拦截。模式选择权属于用户。

## 七、统一体验原则

代理模式与 CEO 模式之间改变执行方式时，必须保持同一项工作的连续性。系统应沿用或明确移交：

- 当前对话和已完成的工作
- 当前工程或工作空间
- 已引用的文件与代码上下文
- 用户偏好和可用记忆
- 模型配置与权限状态
- 已生成的产物和执行记录
- 当前未完成任务的可恢复状态
- 当前会话成员的身份、职责、上下文和任务历史

这句话具体意味着：用户在当前对话里从代理模式改为 CEO 模式，或从 CEO 模式改回代理模式时，不需要重新创建对话、重新选择工作空间、重新描述目标，也不会被带到一套与原工作互不相认的历史和文件系统中。界面应明确记录执行方式已经改变，同时继续使用已有目标、消息、文件和结果。

进入工程模式比改变会话工作方式影响更大。系统应保留原会话和产物，但哪些内容成为工程共享信息、哪些会话成员转为项目专属成员，必须由用户确认或检查，不能用“无缝切换”掩盖组织边界。

当前会话主 Agent 可以承接项目 PM 职责，使原会话连续成为 PM 主会话。工程完成或归档后，用户也可以让当前主 Agent 退出项目管理职责并回到代理工作；项目组织、历史和产物继续保留。

## 八、核心产品原则

### 1. 直接性优先

直接性优先不等于强制代理模式。产品在开始位置提供轻量、清楚的代理模式 / CEO 模式选择；用户已经选定后就直接开始工作，不再强迫其填写角色、团队编制或流程表单。没有主动选择且没有历史偏好时，才预选代理模式。

### 2. 用户可选择

系统可以帮助用户发现更适合的工作方式，但不替用户做长期工作关系的决定。

### 3. 协作按需发生

多 Agent 是解决工作的手段，不等于 CEO 模式。只有协作治理成为主要工作结构时，才需要显式 CEO 体验。

### 4. 过程可见，管理可选

CEO 模式和工程模式提供充分的协作可见性，但不把所有过程都变成用户必须处理的待办事项。

### 5. 交付必须诚实

无论哪个模式，只有真实完成、真实写入或真实可访问的结果，才可以被报告为已交付。部分完成、失败、等待和用户停止都要清楚表达。

### 6. 底层能力复用

Magic 优先复用经当前版本实机确认的 OpenCode 执行能力，在产品层做必要的适配和扩展，避免重复建设两套互相漂移的 Agent 内核。

## 九、第一阶段产品边界

第一阶段优先把以下闭环做稳：

- OpenCode 单 Agent 能力在 Magic 中自然可用
- 代理模式作为默认入口完整可用
- 代理模式可以自主调用并在当前会话复用其他 Agent
- CEO 模式可以从同一工作台进入并完成显式团队协作
- 会话成员不会因代理与 CEO 变化而丢失
- 模式切换不丢失对话、工作区和执行上下文
- 用户可以主动选择 CEO 模式
- 系统可以提出非阻塞式工作方式或工程组织建议
- 共享的停止、恢复、权限、文件和交付语义保持一致

工程模式第一阶段只确定入口、边界、对象和验证顺序，不承诺一次交付完整的长期 Agent 组织。

## 十、明确边界与暂不承诺

当前不承诺以下内容：

- 自动替用户建立长期 Agent 团队
- 一开始就生成固定完整的 PM、前端、后端、测试等组织
- 每个 Agent 永久拥有不可变的职业身份
- Agent 之间无限层级派发
- 所有共享信息自动进入所有 Agent 的上下文
- 未经授权让会话成员跨范围读取或执行
- 借调成员时自动共享来源工程私有记忆、权限或未公开任务
- 圆桌会议可以自动解决所有冲突
- 多 Agent 协作必然比单 Agent 更好
- 不把工程模式设为管理长期工作的唯一方式；用户可以通过多个代理或 CEO 对话自行组织工程

## 十一、后续产品对齐顺序

1. 先冻结两种执行方式与工程组织形态的组合边界
2. 让代理模式在 OpenCode 基础上成为可靠的默认体验
3. 定义 CEO 模式的会话级显式协作闭环
4. 定义跨模式共享的核心对象和状态
5. 再单独深入工程模式的组织、记忆、协作和治理
6. 根据真实试运行反馈调整路线图，不用概念规模代替用户价值
