# Magic 产品方向总纲

## 一、文档目的

本文是 Magic 的产品方向基线，用于统一产品定位、工作模式、用户心智、核心边界和后续取舍。

本文只回答产品方向问题，不替代 OpenCode 的技术文档，也不提前规定工程模式的全部实现细节。凡是尚未经过产品对齐的内容，必须明确标注为待决策，不得从设想直接变成契约。

## 二、产品定位

Magic 是一个建立在 OpenCode 之上的统一 AI 工作台。

它既可以让用户把工作直接交给一个强大的 Agent，也可以让用户在需要时组织一支由 CEO 管理的 Agent 团队，还可以支持用户围绕长期工程建立稳定、可复用的 Agent 组织。

一句话定位：

> **简单的事，直接做；复杂的事，组织做；长期的事，建成一支持续工作的 Agent 团队。**

Magic 的核心价值不是把每个任务都变成多 Agent 协作，而是让用户能够在不同工作复杂度和持续周期下，自由选择合适的工作方式，并且在切换时不丢失上下文。

## 三、产品关系

OpenCode 是底层 Agent 执行基础，Magic 是建立在其上的产品与协作层。

### OpenCode 负责

- Agent 的直接执行能力
- 文件、代码和终端工作流
- 工具调用与上下文处理
- Agent 的连续工作过程
- 执行状态、修改和验证
- 底层会话与工作区能力

### Magic 负责

- 代理模式、CEO 模式和工程模式
- 用户选择与模式切换
- CEO 组织临时 Agent 团队
- 长期工程中的 Agent 组织关系
- 多 Agent 的信息共享与协作可见性
- 用户决策点、交付汇报和团队治理
- 跨模式的身份、记忆、工作区和产物连续性

Magic 不应重新复制 OpenCode 已经成熟的单 Agent 能力。重构的价值在于补足工作方式和协作层，让 OpenCode 的强执行能力可以自然地扩展为更高层的团队协作能力。

## 四、三种工作模式

### 代理模式

用户直接把目标交给 Agent。Agent 可以自主理解、拆解、调用工具、修改文件、验证结果并持续推进，不要求用户管理任务分工。

产品心智：

> **我交代一件事，你直接帮我做。**

代理模式是默认的自然入口，也是完整、强大的工作方式，不是低级模式或能力受限模式。

### CEO 模式

用户将目标交给 CEO，由 CEO 根据任务需要临时组织多个 Agent 协作。团队可以并行执行、互相验证、继续委派、进行辩论并形成统一交付。

产品心智：

> **我把目标交给 CEO，由 CEO 负责组织团队完成。**

CEO 模式强调任务级协作。团队通常服务于当前任务，完成后可以随任务结束，不默认形成长期组织。

### 工程模式

用户围绕一个持续建设的工程，建立一支稳定、可复用、可演进的 Agent 组织。

工程模式可以拥有职责、层级、独立记忆、共享信息、权限、任务队列、评审机制和圆桌会议。它不是 CEO 模式多派几个 Agent 的简单放大，而是一个长期组织系统。

产品心智：

> **我建立并经营一支可以长期建设这个工程的 AI 团队。**

工程模式是确定的产品方向，但在第一阶段只冻结产品边界和核心问题，不提前冻结完整的组织模型和实现方案。

## 五、模式关系

三种模式不是能力高低，也不是会员等级，而是三种工作关系：

| 模式 | 工作关系 | 主要时间范围 | 团队性质 |
|---|---|---|---|
| 代理模式 | 用户与一个强 Agent 直接合作 | 一次任务或连续对话 | 不建立用户可管理的团队 |
| CEO 模式 | 用户授权 CEO 临时组织团队 | 当前任务或当前协作阶段 | 临时团队 |
| 工程模式 | 用户经营长期 Agent 组织 | 长期工程周期 | 稳定、可复用、可演进的团队 |

三种模式共享同一个工作台，但不共享所有用户体验。共享的是基础对象和连续性，差异化的是执行组织方式、可见信息和管理面板。

## 六、用户选择原则

用户可以主动选择自己适合的模式：

- 默认进入代理模式
- 用户可以直接切换到 CEO 模式
- 用户可以直接进入工程模式
- 系统可以根据上下文识别出升级机会并提出建议
- 系统不得未经用户确认自动建立长期工程团队
- 系统不得因为任务复杂就强制用户进入 CEO 模式
- 用户拒绝建议后，当前工作继续按原模式进行

“建议切换”是辅助，不是拦截。模式选择权属于用户。

## 七、统一体验原则

模式切换必须发生在同一产品连续体验内。切换时默认继承：

- 当前对话和已完成的工作
- 当前工程、文件夹和工作区
- 已引用的文件与代码上下文
- 用户偏好和可用记忆
- 模型配置与权限状态
- 已生成的产物和执行记录
- 当前未完成任务的可恢复状态

切换不应要求用户重新解释已经说过的目标，也不应制造两个互相隔离的产品身份。

## 八、核心产品原则

### 1. 直接性优先

用户提出目标后，默认先让 Agent 开始工作。产品不把角色选择、团队编制、流程表单放在每一次工作的前面。

### 2. 用户可选择

系统可以帮助用户发现更适合的工作方式，但不替用户做长期工作关系的决定。

### 3. 协作按需发生

多 Agent 是解决复杂工作的手段，不是所有任务都必须展示或启用的仪式。

### 4. 过程可见，管理可选

CEO 模式和工程模式提供充分的协作可见性，但不把所有过程都变成用户必须处理的待办事项。

### 5. 交付必须诚实

无论哪个模式，只有真实完成、真实写入或真实可访问的结果，才可以被报告为已交付。部分完成、失败、等待和用户停止都要清楚表达。

### 6. 底层能力复用

Magic 优先复用 OpenCode 的成熟执行能力，在产品层做必要的适配和扩展，避免重复建设两套互相漂移的 Agent 内核。

## 九、第一阶段产品边界

第一阶段优先把以下闭环做稳：

- OpenCode 单 Agent 能力在 Magic 中自然可用
- 代理模式作为默认入口完整可用
- CEO 模式可以从同一工作台进入并完成任务级协作
- 模式切换不丢失对话、工作区和执行上下文
- 用户可以主动选择 CEO 模式
- 系统可以提出非阻塞式升级建议
- 共享的停止、恢复、权限、文件和交付语义保持一致

工程模式第一阶段只确定入口、边界、对象和验证顺序，不承诺一次交付完整的长期 Agent 组织。

## 十、暂不做的产品承诺

当前不承诺以下内容：

- 自动替用户建立长期 Agent 团队
- 一开始就生成固定完整的 PM、前端、后端、测试等组织
- 每个 Agent 永久拥有不可变的职业身份
- Agent 之间无限层级派发
- 所有共享信息自动进入所有 Agent 的上下文
- 圆桌会议可以自动解决所有冲突
- 多 Agent 协作必然比单 Agent 更好
- 任何工程都需要工程模式

## 十一、后续产品对齐顺序

1. 先冻结三种模式的边界和切换原则
2. 让代理模式在 OpenCode 基础上成为可靠的默认体验
3. 定义 CEO 模式的任务级协作闭环
4. 定义跨模式共享的核心对象和状态
5. 再单独深入工程模式的组织、记忆、协作和治理
6. 根据真实试运行反馈调整路线图，不用概念规模代替用户价值
