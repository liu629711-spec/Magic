# Magic 产品经理工作准则

> 本文是 Magic 产品设计、产品评审、子 Agent 协作和跨对话交接的共同准则。任何参与 Magic 产品工作的产品经理、审阅助手、研究助手或其他 Agent，都应先阅读本文，再进入具体专题。

## 一、本文解决什么问题

Magic 正在建立在 OpenCode 之上的新产品，同时继承 AgentCore 已经完成并试运行过的 CEO 与 Multi-Agent 协作经验。产品设计会持续经历重构、拆分和多轮讨论，因此必须有一份稳定的共同准则，避免出现以下问题：

- 新对话不了解 AgentCore 的历史背景，重新发明已经验证过的能力。
- 把旧文档中的蓝图或提案误认为已经实现的事实。
- 把代理、CEO 和工程误解成互相排斥的三个等级模式。
- 把一次任务中的临时协作者误写成长期团队成员。
- 为了追求自由而抹平权限、记忆、责任和数据边界。
- 为了追求自动化而重新制造用户必须管理的复杂编排器。
- 在总纲、专题文档、对象模型和路线图之间形成互相冲突的定义。

本文不是实现文档，不替代具体模式专题，也不提前冻结尚未对齐的细节。它规定的是产品判断方法、协作顺序和不可违反的方向边界。

### 2.3 第三阶段：再进行设计或审阅

只有完成前两阶段，才可以提出新的产品判断。每次审阅都要说明：

- 你从旧产品中确认了哪些事实。
- 你从 Magic 文档中确认了哪些方向。
- 你发现的是矛盾、遗漏、歧义，还是仅仅尚未展开的细节。
- 你的建议会改变哪个用户行为、对象关系或产品边界。

不能脱离旧产品和 Magic 当前共识，直接以通用 AI 产品经验替代本项目已有证据。

## 2.4 重构时的基础能力防遗漏

Magic 不是从空白开始设计。每次重构、模式拆分或底座迁移前，必须先建立“基础能力继承与防遗漏清单”，不能只按新的产品模式重新发明页面和流程。

能力至少分为以下五类：

1. **原样继承**：用户已经习惯，Magic 只做界面或协议适配，不改变核心体验。
2. **Magic 适配**：底座已经有能力，但需要映射到 Magic 的任务、计划、责任、成员或权限模型。
3. **Magic 新增**：底座没有等价能力，由 Magic 新建产品对象或组织规则。
4. **明确后置**：经过产品裁定，暂不进入当前版本，并在界面和发布范围中明确不支持。
5. **待核查**：文档、源码或版本信息不足以证明能力存在，必须安排实机验证。

每项能力都必须记录：

- 能力名称和用户价值；
- 来源产品、源码路径、文档章节、试运行经验或实机证据；
- 在 OpenCode、AgentCore 和 Magic 中分别处于什么状态；
- 对应的 Magic 对象、任务状态或交互入口；
- 代理、CEO、工程三种工作方式是否都可用；
- 失败、断连、权限不足或底座不支持时的降级方式；
- 首版验收场景、负责人和当前结论。

每次新产品设计至少要检查以下常用能力是否被保留、适配或明确后置：

- 对话输入、流式输出和多回合连续工作；
- 长任务的计划/Todo、步骤进度和下一步提示；
- 工具调用、文件修改、差异查看、撤销或恢复；
- 暂停、继续、停止、取消、重试和断连恢复；
- 用户问题、权限审批、成本提示和外部副作用确认；
- 会话历史、上下文、模型/Provider、工作区和项目范围；
- Agent 辅助调用、结果汇总、错误提示和同步状态；
- 产物、测试结果、交付状态和用户验收。

其中，当前 OpenCode 代码树已经存在计划和 Todo 相关能力，例如 `packages/opencode/src/tool/plan.ts`、`packages/opencode/src/tool/plan-enter.txt`、`packages/opencode/src/tool/plan-exit.txt`、`packages/opencode/src/tool/todo.ts` 和 `packages/app/src/pages/session/composer/session-todo-dock.tsx`。这证明当前版本具有对应底座能力，不代表 Magic 可以直接把底座 Todo 当作 Magic 任务计划，也不代表其他版本无需重新核查。

基础能力的最低继承规则是：

- 代理模式必须保留直接交代目标、自动执行、过程反馈、验证和真实交付能力；
- CEO 模式在保留代理基础能力的前提下增加派发、依赖、汇报和综合收口；
- 工程模式在保留前两者基础能力的前提下增加长期成员、项目任务和项目级治理；
- 计划推进可以嵌入三种工作方式，但不自动创建团队、不自动建立工程；
- 任何已有能力都不能因为“新架构暂时没有位置”而静默消失；若要移除，必须说明用户影响、替代方案、版本范围并完成产品裁定。

基础能力清单必须在产品设计、架构拆解、前端拆解和开发冻结前分别复核一次。四次复核结果不一致时，优先标记为“待核查”或“明确后置”，不得默认为已保留。

本轮《能力盘点-OpenCode与AgentCore常用能力》已完成 OpenCode 后端与运行时、OpenCode 前端、AgentCore 编排与运行治理、AgentCore AI 核心四个领域的技术总监复核。复核通过的含义是“作为防遗漏基线可用”，不是“所有能力已在 Magic 首选版本中实机验证”，更不是“首版开发冻结已批准”。后续文档必须同时写清这三个状态：

- **盘点基线通过**：范围、继承候选、遗漏风险和产品/底座边界已经过技术交叉复核；
- **能力事实已确认**：有当前版本的源码、测试或实机证据，且证据等级明确；
- **开发冻结可通过**：首版关键路径已经完成版本锁定、对象映射、权限/副作用方案和端到端收敛验证。

本轮复核特别要求产品文档不得把以下内容混为一谈：OpenCode 或 AgentCore 的 Session/Run/worker/CAPTAIN 与 Magic 的任务、运行尝试、会话成员、项目成员和 PM；底层 SSE/Journal/Replay 与 Magic 任务状态真相；工具 approval 与组织授权；运行恢复与外部副作用回滚；计划步骤与正式子任务。凡涉及输入幂等、事件缺口、断连重启、重试、审批、文件/Git/MCP/网络副作用和最终收口的内容，都必须保留“待实机核查”或明确验收条件。

## 三、产品事实的证据等级

所有产品讨论都必须区分证据强度：

| 等级 | 含义 | 可以怎样使用 |
|---|---|---|
| 已实现 | 已有代码、运行时或产品文档明确说明已落地 | 可以作为继承候选，但迁移到 Magic 前仍要重新映射边界 |
| 试运行可用 | 在 AgentCore 既有范围内实际运行过并得到经验 | 可以作为重要设计依据，不等于大规模市场验证 |
| 已确认方向 | 用户已经明确认可的 Magic 产品方向 | 可以作为产品前提，不应随意推翻 |
| 已提出方案 | 已写入专题，但用户尚未冻结 | 可以比较、修改和质疑，不能当作事实 |
| 蓝图或提案 | 未来可能实现的方向 | 只能作为候选能力，不默认进入首版 |
| 被否决设计 | 已经讨论并明确不采用 | 除非出现新证据，不应重新引入 |

出现“成熟”“验证”“保留”“自动”“长期”“默认”等词时，必须说明它们对应的是实现事实、试运行经验、用户共识还是假设方案。

## 四、Magic 的核心产品模型

Magic 不是三个互斥的等级模式，而是两个可以组合的维度：

```text
会话工作方式：代理方式 / CEO 方式
长期组织形态：非工程工作 / 工程组织
```

### 4.1 代理方式

代理方式是平等且完整的工作方式，不是低级模式。用户直接交代目标，主 Agent 负责理解、执行、验证和交付；必要时可以自主拆解任务、调用临时 Agent，或者复用当前会话成员。

代理方式的关键体验是：用户不需要先设计团队，系统也不要求用户理解内部编排。是否使用多个 Agent 不能单独决定产品模式。

### 4.2 CEO 方式

CEO 方式是显式的团队治理工作方式。主 Agent 的主要责任转为分工、协调依赖、追踪进度、收集汇报、调整计划、处理阻塞和统一交付。

CEO 方式不是更高级的智能，也不是代理方式的替代品。它适合用户希望从团队视角观察、干预和拍板的工作。

### 4.3 工程组织

工程不是代理和 CEO 的第三个同级执行模式，而是建立在工作区之上的长期组织对象。工程可以拥有项目 PM、项目成员、成员任务会话、共享事实、计划和治理记录。

工程内部仍然可以采用代理方式或 CEO 方式。用户也可以不建立工程，依靠多个普通会话、文件和自己的工作习惯组织长期工作。

工程的创建、项目 PM、长期成员、跨会话身份、权限变化和项目长期记忆，不能由一次普通委派或一次模式建议静默产生。

## 五、必须区分的几个概念

### 5.1 Agent 身份与 Agent 运行实例

Agent 身份代表可被识别、复用和授权的长期主体；运行实例代表一次具体执行。一次运行结束，不代表身份被删除；一个身份也不要求底层进程永久运行。

### 5.2 临时 Agent、会话成员和项目成员

- **临时 Agent**：只服务于当前局部任务，完成后不保留持续身份。
- **会话成员**：属于一个会话，可在该会话的多个任务中复用，默认不能被其他会话调用。
- **项目成员**：属于一个工程，可跨该工程多个会话和任务复用，默认不能跨工程调用。
- **角色模板**：可以跨工程复用职责、提示和配置，但不复制成员身份、私有上下文、私有记忆或权限。

### 5.3 会话主 Agent 与项目 PM

- **会话主 Agent**：当前会话面对用户并对会话任务理解、执行和收尾负责。代理和 CEO 方式切换时，默认不替换会话主 Agent。
- **项目 PM**：工程级长期协调身份，负责项目计划、派发、汇报收敛、跨成员依赖和项目级治理。PM 在某次工作中也可以采用代理方式或 CEO 方式。

### 5.4 共享文件与共享记忆

共享工作区文件不等于共享 Agent 身份、私有上下文、私有记忆、权限或汇报关系。任何“共享”设计都必须说明共享的是文件、产物、摘要、事实、任务状态还是完整记忆。

## 六、三种协作行为不能混为一谈

### 6.1 代理内部调用协作者

主 Agent 为了完成当前目标进行内部拆解、调用临时 Agent 或复用会话成员。这不会自动改变当前工作方式，也不会因为 Agent 数量增加就进入 CEO 方式。

### 6.2 当前任务启用 CEO 协作

当前目标形成用户可以理解、查看和必要时干预的正式协作结构。它可以是一次性或任务级的，任务完成后默认回到原来的工作方式。

### 6.3 切换会话默认工作方式

改变当前会话后续任务的默认入口。它与当前正在执行的任务是否移交、是否影响同工作区其他会话、新会话是否继承，必须分别定义，不能用一个“切换模式”概念全部代替。

评审任何模式切换方案时，必须回答四件事：作用范围、持续时间、当前执行任务的处理、完成后的回退方式。

## 七、自由度与自动化边界

Magic 的目标是让用户自由选择，但自由不是没有边界的自动化。

### 可以在当前授权内自主完成

- 理解目标和生成执行计划
- 任务内部的合理拆解
- 调用临时 Agent
- 在明确范围内复用当前会话成员
- 进行局部验证、交叉检查和结果汇总
- 在不改变长期归属的情况下调整当前任务执行顺序

### 默认只建议，不强制改变

- 建议当前任务启用 CEO 协作
- 建议用户从代理方式切换为 CEO 方式
- 建议将持续工作整理为工程
- 建议增加角色、成员或协作团队

### 必须获得用户明确确认

- 创建工程或项目 PM
- 创建、转化、停用长期项目成员
- 改变成员权限、工作区访问边界或审批边界
- 跨会话、跨工程调用 Agent
- 共享私有记忆或写入项目长期事实
- 将原会话、目标、成员和历史迁入工程
- 可能产生明显成本、外部副作用或不可逆变化的操作

用户可以在设置中预先授权部分自动行为，但授权必须有明确范围、可撤销、可查看，并保留必要的变更记录。

## 八、自然体验的验收标准

每份产品设计都要用以下问题自检：

1. 用户无需先理解 Multi-Agent、角色或编排概念，能否开始工作？
2. 代理内部协作是否默认不要求用户管理成员、依赖和流程？
3. 用户能否在需要时看懂谁在做什么、工作到哪里、有什么风险、结果在哪里？
4. 模式切换是否保留目标、上下文、文件、产物、状态和相关成员？
5. 是否明确告诉用户长期身份、权限、记忆和工程归属发生了什么变化？
6. 只有真实决策、阻塞、权限边界或用户主动要求时，系统才会打断用户吗？
7. 失败、部分完成、停止、等待和取消是否与成功明确区分？
8. 非工程工作是否不会因为复杂、耗时或调用多个 Agent 就被自动收编为工程？
9. 用户是否仍然可以手动选择代理或 CEO，而不必先走系统推荐路径？
10. 这项设计是在减少用户管理负担，还是只是把管理负担换了一个界面？

## 九、专题文档的写作要求

每一份专题文档都应包含以下内容，顺序可按主题调整：

1. **目的与范围**：明确本文解决什么问题，不解决什么问题。
2. **用户价值**：说明用户在什么场景下需要它，以及不用它会遇到什么问题。
3. **核心定义**：给出对象、角色、状态和边界的单一解释。
4. **正常流程**：从用户意图开始，写到执行、协作、交付和后续复用。
5. **异常与回退**：说明失败、取消、暂停、超时、权限不足和迁移失败时怎么办。
6. **与其他模式的关系**：说明嵌入、切换、复用和退出，不把模式写成孤岛。
7. **授权与可见性**：说明什么自动完成、什么提示、什么必须确认，以及用户看到什么。
8. **首版范围与后置范围**：明确哪些先验证，哪些暂不承诺。
9. **待决策问题**：把尚未对齐的内容列出来，不用含糊措辞隐藏争议。
10. **相关文档**：链接到上游方向、基线和下游对象或路线图文档。

专题文档不重复复制上游全文。需要引用共同规则时，链接到上游文档并只保留本专题的差异、流程和例外。若专题方案与当前裁定冲突，先标记冲突并回写裁定，不得通过沉默覆盖形成第二个权威版本。

描述功能时优先使用用户能理解的语言。`delegate`、`worker`、`DAG`、`replan`、`handoff`、`escalate` 等内部术语只有在确有必要时出现，并同时给出产品语义。

## 十、产品审阅方法

审阅结果要优先报告会导致用户行为错误、对象边界错误或后续实现返工的问题，而不是罗列所有个人偏好。推荐使用以下格式：

```text
问题：
严重程度：最高 / 高 / 中 / 低
依据：对应的产品事实、用户表达或文档位置
为什么重要：会造成什么用户误解、冲突或实现风险
建议：最小、明确、可验证的修订方向
```

审阅时重点检查：

- 定位是否让用户知道“我可以直接交代目标”。
- 代理、CEO、工程是否分别位于正确的维度。
- 是否错误地以 Agent 数量、耗时或任务长度判断模式。
- 会话主 Agent、会话成员、PM 和项目成员的生命周期是否混淆。
- 是否把临时行为写成长期关系。
- 用户自由选择与系统建议、自动执行之间是否冲突。
- 文件、产物、共享事实、私有记忆和权限的边界是否明确。
- 当前任务、当前会话、工作区、工程和账户默认值的作用范围是否明确。
- 文档是在规定方向，还是越权冻结了实现细节。
- 是否有失败、暂停、恢复、取消和无法迁移时的诚实收口。
- 是否把首版验证约束误写成永久产品限制。
- 是否把 OpenCode 或 AgentCore 的文档描述误写成当前版本已确认能力。
- 是否区分任务状态、运行状态、当前责任人和底座事件证据。

## 十一、与子 Agent 的协作准则

子 Agent 参与产品讨论时，应当被当作有明确任务边界的产品同事，而不是无上下文的意见生成器。

### 派发顺序

主产品经理应向子 Agent 明确发送：

1. 先阅读 AgentCore 旧文档和索引，先报告旧产品理解与实际状况。
2. 再阅读 Magic 相关产品文档，说明已确认方向和待决策内容。
3. 最后进行新旧对照或专题审阅。

### 派发内容

每次派发至少说明：

- 审阅目标和不在范围内的内容。
- 需要阅读的旧文档路径。
- 需要阅读的 Magic 文档路径。
- 要区分事实、方向和假设。
- 输出格式、问题数量和严重程度标准。
- 是否允许修改文件。未明确允许时，只审阅不修改。

### 结果处理

子 Agent 的意见是审阅输入，不是自动生效的产品决策。主产品经理必须：

- 区分子 Agent 的事实判断和方案偏好。
- 对每条重要意见作出接受、部分接受或不接受的解释。
- 需要时邀请用户确认会改变产品方向的判断。
- 只有完成判断后，才修改正式文档。
- 不让子 Agent 直接覆盖用户已经确认的方向。

## 十二、产品决策与文档变更纪律

- 已确认的《产品方向总纲》是上游方向基线，专题文档不得无提示地推翻它。
- 发现总纲与专题冲突时，先指出冲突，再决定是修订专题还是重新提交总纲判断。
- 新增对象、长期身份、权限边界、默认行为和自动化行为，都必须说明其创建条件、作用范围、生命周期和删除或归档方式。
- 不因为工程模式宏大，就一次性冻结全部工程细节；优先验证 PM、少量成员、任务会话、共享事实和基本汇报闭环。
- 不因为代理模式简单，就削弱其直接执行、工具调用、验证、恢复和真实交付能力。
- 不因为 CEO 模式显式，就把它写成必须经过的升级路径。
- 不因为产品追求自由，就省略风险、授权、责任和信息隔离。
- 修改文档前先确认相关文件中的现有内容，保留用户已有的未提交修改，不做无关重写。
- 临时审阅纪要应与正式产品文档区分；完成吸收后删除或移入明确的会议记录位置。
- 正式技术会议前应先阅读《Magic 最终产品裁定与技术会议输入》和《Magic 产品系统边界与生命周期底图》，不得只凭单篇模式专题冻结实现。

## 十三、Magic 当前的长期判断

以下判断是当前产品设计的共同底座：

> 让用户先交代目标，而不是先管理团队；让 Agent 自主完成合理的内部协作；让 CEO 成为用户可以主动展开的团队治理方式；让工程成为用户确认后建立的长期组织；让所有模式共享可靠的执行、记忆、权限、可见性和真实交付能力。

因此，Magic 的核心竞争力不是拥有最多 Agent、最复杂的组织层级或最多的编排按钮，而是让不同复杂度和持续周期的工作，在同一产品中自然连续地成长，同时不让用户失去选择权、理解力和控制权。
