# CEO 模式

## 一、产品定义

CEO 模式是 Magic 的任务级 Multi-Agent 协作方式。用户将目标交给 CEO，CEO 负责判断如何拆解、组织队员、整合结果并向用户汇报。

CEO 模式解决的是“单个 Agent 直接完成不够可靠或不够高效，但用户又不想自己做项目经理”的问题。

## 二、用户心智

> **我把目标交给 CEO，由 CEO 负责组织团队完成。**

用户是最终决策者。CEO 是受用户委托的主 Agent，负责协作组织和结果整合，不取代用户做最终的高风险或价值判断。

## 三、核心循环

```text
说目标 → CEO 组队 → 队员执行 → 用户看协作 → 必要时拍板 → CEO 汇总 → 交付
```

组队和开始协作默认不要求用户逐项批准。只有真正影响目标、范围、风险或交付的决策，才进入用户检查点。

## 四、CEO 的职责

CEO 负责：

- 理解用户目标和约束
- 判断是否需要多 Agent 协作
- 为队员分配临时职责
- 决定任务依赖和并行关系
- 在必要时让队员继续委派
- 组织交叉验证、辩论或圆桌评审
- 汇总不同队员的结果
- 识别冲突、缺口和未完成事项
- 向用户说明事实、判断和建议
- 对最终交付负责

CEO 不应把每个内部选择都转交给用户，也不应把没有依据的结果包装成完成。

## 五、队员的职责

队员是当前任务中的临时 Agent 参与者，可以根据 CEO 分配承担研究、实现、验证、评审或其他职责。

队员可以拥有适合当前任务的工具和上下文。队员的临时职责不等于永久职业身份，也不自动成为工程模式中的可复用 Agent。

## 六、可见性

CEO 模式需要让用户理解协作正在如何推进，重点展示：

- 当前有哪些队员参与
- 每个队员承担什么任务
- 哪些任务已完成、进行中或受阻
- 结果之间是否存在冲突
- 哪些证据支撑最终判断
- CEO 当前正在等待什么或准备什么
- 哪些内容需要用户拍板

可见性服务于信任和决策，不应退化为用户逐项管理队员。

## 七、用户介入

用户可以：

- 补充目标或约束
- 对当前方向进行插话
- 把后续要求排队
- 停止当前协作
- 对计划进行调整
- 在检查点放行、修改或停止
- 要求查看某个队员的过程或产物

用户不需要：

- 事先设计全部团队结构
- 手动给每个队员命名职业
- 为每个子任务指定模型
- 批准每一个队员的启动

## 八、CEO 模式与工程模式的边界

CEO 模式的团队默认服务当前任务，任务结束后团队关系可以结束。工程模式的 Agent 团队则服务长期工程，可以被反复调用并积累独立记忆。

如果当前任务反复出现相同角色、协作关系和长期上下文，系统可以建议用户进入工程模式，但不能自动完成转换。

## 九、完成标准

CEO 模式的一次协作只有在以下内容清楚后才算完成：

- 目标和范围得到回应
- 团队实际完成的工作可追溯
- 关键结论有依据或明确标注为判断
- 冲突意见和未完成事项被说明
- 交付物真实存在并可访问
- 用户知道哪些事项已经结束、哪些还需决定

## 十、待决策

- CEO 模式的团队是否允许用户在任务中途直接替换队员职责
- 圆桌会议是 CEO 的内置能力，还是独立协作工具
- CEO 模式是否支持从代理模式无缝接管未完成任务
- 临时团队记录保留多久、以什么方式可检索
