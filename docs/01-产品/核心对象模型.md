# 核心对象模型

## 一、目的

本文先用产品语言建立 Magic 的对象地图，避免三种工作模式各自发展出互相冲突的实体。具体字段、存储和接口属于后续技术设计。

## 二、对象关系

```text
用户
  └── 工作空间
       ├── 工程或工作范围
       │    ├── 共享上下文
       │    ├── 共享记忆
       │    ├── 产物与文件
       │    └── 长期 Agent 团队（工程模式）
       └── 对话
            ├── 回合
            │    ├── 代理执行
            │    ├── CEO 临时协作
            │    └── 模式切换记录
            ├── 用户决策
            └── 交付结果
```

## 三、核心对象定义

### 用户

最终目标、范围、关键判断和授权的拥有者。用户可以直接使用代理模式，也可以选择 CEO 模式或工程模式。

### 工作空间

Agent 可以访问、修改和交付文件或产物的范围。工作空间是三种模式共享的基础，不应因为模式切换而产生隐式的多份副本。

### 工程

围绕一个长期目标组织工作、上下文、产物和 Agent 团队的持久范围。工程是工程模式的核心对象；代理模式和 CEO 模式可以在工程范围内工作，但一次普通任务不自动成为工程。

### 对话

用户与 Agent 或 CEO 连续交流的交互单元。对话保存目标、上下文、过程和汇报。对话可以发生在工作空间或工程范围内。

### 回合

一次用户输入触发的完整执行单元。回合可以包含单 Agent 执行、CEO 委派和用户决策，但不应把每一个工具调用都等同于新的用户任务。

### Agent

具备独立推理和执行能力的运行时参与者。代理模式中，Agent 直接服务用户；CEO 模式中，队员是当前任务的临时 Agent；工程模式中，Agent 可以成为具有稳定职责和记忆的长期参与者。

### CEO

负责组织任务级 Multi-Agent 协作的主 Agent。CEO 不是一个必须永久存在的职业角色，而是 CEO 模式中的组织职责。工程模式是否拥有长期 CEO，属于待决策事项。

### 队员

CEO 模式中被临时委派任务的 Agent。队员的临时职责不等于工程模式中的长期 Agent 身份。

### 长期 Agent

工程模式中可被反复调用、具有稳定职责和独立记忆的 Agent。长期 Agent 的创建、修改、停用和复用需要明确的生命周期设计。

### 任务

用户目标或 Agent 为完成目标而承担的一项可执行工作。代理模式中任务通常由单 Agent 自主拆解；CEO 模式中任务可以形成可见的协作结构；工程模式中任务可以进入长期队列。

### 记忆

可跨回合或跨对话使用的上下文信息。至少需要区分用户偏好、工作空间事实、工程共享信息、Agent 独立记忆和临时执行上下文。

### 共享信息

工程或协作范围内，多个 Agent 可以读取的经过定义的信息。共享信息需要有来源、范围和更新责任。

### 产物

Agent 或团队实际生成并可被用户访问、继续编辑、验证或交付的文件、代码、文档或其他结果。

### 模式切换

用户改变后续工作组织方式的动作。模式切换不是新建产品，也不是删除原任务；它应尽可能继承上下文并保留历史事实。

## 四、重要区分

### 执行层派发与组织层团队

Agent 内部为了做完工作而安排步骤，不等于创建用户可管理的 Agent 团队。只有后者才进入 CEO 模式或工程模式的产品语境。

### 临时队员与长期 Agent

一次任务中被 CEO 委派的队员，可以在工程模式中被重新使用，但不能默认自动获得长期身份和独立记忆。

### 对话、回合与任务

对话是连续交流范围，回合是一次完整执行，任务是要完成的工作。三者可以有关联，但不能互相替代。

### 共享信息与记忆

共享信息强调哪些参与者可以使用同一事实；记忆强调信息如何跨时间保留。共享信息可以是短期的，记忆也可以只属于一个 Agent。

## 五、待决策

- 工程是否等同于文件夹，还是建立在工作空间之上的独立对象
- 长期 Agent 的身份是否可以跨工程复用
- CEO 是工程中的长期 Agent、组织职责，还是两者兼容
- 记忆的所有权和删除权如何分配
- 临时团队是否可以一键固化为长期团队
- 产物是否需要独立于文件的统一实体
