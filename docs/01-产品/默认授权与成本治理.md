# 默认授权与成本治理

> 本文定义 Magic 如何处理“默认怎么工作”“这次允许做什么”“最多花多少”和“什么时候必须问人”。它不是技术权限实现方案，而是产品层的行为契约。

## 一、白话原则

Magic 要把四件事分开：

1. **工作偏好**：例如新任务默认使用代理方式还是 CEO 方式。
2. **权限授权**：例如能否读取某个目录、执行命令或发布内容。
3. **成本预算**：例如本次任务最多消耗多少模型和工具资源。
4. **高风险确认**：例如删除、付费、部署或对外发布前是否需要人确认。

一个用户可以偏好 CEO 方式，但这不代表 CEO 自动拥有更高权限；一个 Agent 可以拥有执行工具，也不代表它可以读取所有工程；一次任务被允许执行，也不代表它可以无限花费。

## 二、工作偏好继承

工作偏好采用以下覆盖顺序：

```text
当前任务明确选择
  > 当前会话默认
  > 当前工程或工作区默认
  > 账户默认
  > 系统默认代理方式
```

工作偏好包括代理/CEO 的默认选择、计划展示偏好、通知偏好和其他不直接扩大权限的工作体验设置。

规则如下：

- 当前任务的明确选择只影响当前任务。
- 修改会话默认只影响该会话后续的新任务。
- 修改工程或工作区默认只影响之后创建的新会话或新任务。
- 修改账户默认只影响没有更近明确设置的后续工作。
- 任何默认值变化都不追溯改写已经执行、正在执行、已完成或已归档的任务。
- “本次使用 CEO”和“以后默认使用 CEO”必须是两个不同的产品操作。

## 三、权限模型

每条有效授权至少包含：

```text
主体 + 资源 + 动作 + 范围 + 时效 + 授权来源
     + 成本上限 + 副作用等级
```

例如“可以操作项目代码”还不够，至少要能区分：哪个 Agent、哪个工程、哪些目录、可以读取还是写入、有效多久、谁授予、最多消耗多少、是否允许部署。

权限判断采用三种结果：

| 结果 | 含义 | 产品行为 |
|---|---|---|
| `allow` | 有权主体已经授予，且没有违反上级边界 | 可以在范围内继续执行 |
| `ask` | 动作可能允许，但还需要有权主体批准 | 暂停该动作，说明需要谁决定 |
| `deny` | 明确禁止，或当前主体无权授予 | 不执行，并说明被哪条边界拦住 |

`allow` 不是无条件放行。授权主体只能授予自己拥有且允许转授的范围；任何下级授权都不能突破上级 `deny` 或系统硬边界。下级可以进一步缩小资源范围、动作范围、预算或有效时间。

## 四、角色与授权的关系

角色只说明职责，不自动代表权限：

- CEO 可以决定如何拆解和派发任务，但不是账户管理员。
- PM 可以协调工程任务和成员，但不是所有成员任务的默认执行者。
- 架构专家可以负责方案设计，但不因此获得部署权限。
- 测试 Agent 可以运行测试，但不因此获得修改生产数据的权限。
- 临时 Agent、会话成员和项目成员都使用完整 Agent 核心能力，但有效权限由当前任务和成员关系决定。

## 五、向下派发与权限衰减

Agent 创建下属 Agent 或派发子任务时：

1. 先确认自己是否有权创建该类型的 Agent 和任务。
2. 先预留本次派发可能使用的预算。
3. 只传递自己拥有且明确允许转授的权限。
4. 默认不传递原始凭据、隐藏推理、全部私有记忆或完整父会话。
5. 明确子 Agent 的任务范围、资源范围、期限、预算、汇报对象和结束条件。
6. 子 Agent 的失败不会自动转移上级任务责任或扩大上级权限。

一个“允许读取项目文档”的 Agent，不能仅因为它创建了下属 Agent，就把账户凭据或其他工程目录一起传下去。

## 六、预算和成本

预算治理至少要记录四个数字：

- **预算上限**：这项任务最多允许消耗多少。
- **已预留**：已经承诺给在途 Agent 或工具调用的额度。
- **实际消耗**：模型、工具、网络和其他可计量资源已经产生的费用。
- **剩余额度**：上限减去预留和实际消耗后还能使用的额度。

同时记录成本归属：任务、运行实例、Agent、会话、工程和账户至少要能按需要汇总。

规则如下：

- 子 Agent 派发前应完成预算预留，避免多个下属同时超支。
- 运行失败、取消或重试产生的成本仍然计入实际消耗，不能因为任务失败而伪装成零成本。
- 预算不足时，系统可以停止继续派发或进入等待授权，不得静默突破上限。
- 用户批准增加预算时，记录批准主体、增加额度、原因和生效范围。
- 底座能提供的精确计量作为运行事实；Magic 负责按产品对象归集、展示和执行预算策略。

## 七、撤销、过期与历史

权限或预算设置发生变化时：

- 新的工具调用、新 Agent 创建和新的信息访问按新规则判断。
- 已经开始的底层运行是否能停止，依赖底座的停止能力和产品风险策略，不能假设一定可以立即终止。
- 已完成的工具调用、文件写入、费用和外部副作用继续保留为历史事实。
- 撤销权限不等于撤销已经发生的副作用，也不等于删除历史记录。
- 任务、审批、授权和预算变化都保留来源、时间、操作者、原因和影响范围。

## 八、跨工程边界

首版默认禁止跨工程直接调用、直接读取和隐式借调。项目成员属于其工程，角色模板可以复用，但身份、记忆、权限、责任和成本不自动跨工程流动。

未来开放跨工程借调时，必须同时建立：

- 目标工程的临时成员关系；
- 独立目标任务和唯一当前责任人；
- 隔离的工作会话与最小上下文；
- 单独预算和成本归属；
- 明确的期限、汇报对象和结束条件；
- 来源工程的时间冲突检查；
- 可撤销、可审计的授权记录。

## 九、用户界面原则

用户不需要阅读继承矩阵或逐条管理 Agent 权限。普通情况下界面只需要让用户知道：

- 这次 Agent 能做什么；
- 预计会花多少；
- 哪个动作被拦住；
- 需要谁决定；
- 已经发生了哪些不可自动撤销的副作用。

低风险、可逆且在授权范围内的动作可以自动处理。只有权限边界、目标或范围变化、预算超限、明显外部副作用或无法恢复的冲突真正需要决定时，才向用户、PM 或其他有权主体提示。

首次出现系统主动建议 CEO 或其他治理方式时，可以给出一次非阻塞说明；用户关闭后不重复打扰。明确选择不需要重复确认式提示。

## 十、U-12 三档权限入口

U-12 已由用户确认采用。用户界面提供三档简单选择：

| 用户选择 | 产品含义 |
|---|---|
| 请求批准 | 遇到需要确认的动作时暂停并询问 |
| 当前范围内自动处理 | 在当前任务、会话或工程已授权范围内自动工作，高风险动作仍询问 |
| 完全访问当前工程 | 解除当前工程的文件和网络访问限制，但系统禁止项、高风险确认、预算和账户边界仍有效 |

三档选择只是审批入口，不是完整权限表，也不改变 Agent 的工作模式。内部仍需分别记录：

```text
资源访问边界 + 审批策略 + 动作风险 + 预算范围
              + 环境范围 + 授权有效期 + 授权来源
```

“当前范围内自动处理”默认只作用于当前任务；扩展到当前会话或工程必须明确显示范围。“完全访问当前工程”不能扩大到其他工程、账户、私有记忆或原始凭据。

低风险且可逆的读取、计划、独立修改空间、Git 分支/工作树创建、本地测试和本地提交可以在授权范围内自动执行。合并主版本、远程推送、共享资源修改、超预算动作按策略处理；生产部署、生产数据写入、删除重要资源、付费、对外发布和无法可靠审计的动作必须确认或首版禁止。

权限请求至少记录请求范围、批准主体、批准方式、有效期、实际执行结果和副作用结果。运行中遇到高风险动作时，保存当前结果和运行事实后进入等待确认；批准后继续，拒绝后保留历史，不重复执行已发生的动作。

## 十一、首版范围

首版必须具备：

- 任务、会话、工程、工作区和账户默认值的作用域区分；
- 当前任务明确选择覆盖默认工作偏好；
- `allow / ask / deny` 三种授权结果；
- 上级硬边界和下级权限衰减；
- Agent 创建和派发时的权限、预算和深度限制；
- 预算上限、预留、实际消耗、剩余和成本归属记录；
- 权限撤销、预算调整和审批历史；
- 首版默认禁止跨工程直接调用；
- 用户能看懂当前能力、成本、拦截原因和待决定事项。

首版不要求：

- 复杂多组织权限继承界面；
- 跨工程成员直接调用或自动借调；
- 原始凭据在 Agent 之间自动转发；
- 无限层级预算池和无限委派深度；
- 以角色名称自动授予管理员或部署权限。

## 十二、技术核查项

技术会议需要验证：

- OpenCode 工具审批是否能接收 Magic 的主体、资源、动作和时效信息；
- 工具调用开始前能否可靠拦截、等待审批和拒绝；
- 模型、工具、网络和重试成本能否稳定计量并关联到任务与 Agent；
- 预算预留、并发扣减、重复事件和断连重连后能否最终一致；
- 权限撤销对在途运行、新工具调用和新 Agent 创建分别如何生效；
- 文件、命令、MCP、网络和凭据是否能按工程与成员范围隔离；
- 审批、授权、预算和副作用记录是否可审计、恢复和导出。
