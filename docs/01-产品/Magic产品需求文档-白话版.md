# Magic 产品需求文档（白话版）

**版本**：PRD v0.1
**日期**：2026-08-30
**文档状态**：产品主入口，供产品、技术和后续协作成员统一理解
**阅读对象**：CEO、产品经理、设计师、技术团队以及第一次接触 Magic 的协作 Agent

> 这是一份“先让人看懂”的主 PRD。它不替代技术架构文档，也不把所有未来能力都写成首版承诺。阅读本文件后，读者应该能回答：Magic 是什么、用户怎么使用、Agent 怎样协作、首版先做什么。

---

## 1. Magic 是什么

Magic 是一个建立在 OpenCode 之上的 AI 工作台。

它的目标不是让用户学习如何编排 Agent，而是让用户直接说出目标，AI 根据事情的大小和用户的选择，采用合适的工作方式完成任务。

最简单的一句话是：

> 用户负责提出目标和做关键决定，Magic 负责把工作组织清楚，OpenCode 负责真正执行。

Magic 同时支持三种工作方式：

- **代理模式**：像使用一个能力很强的 AI 助手，直接完成事情。
- **CEO 模式**：让当前会话里的 Agent 临时承担 CEO 的组织责任，安排其他 Agent 帮忙，并对最终结果负责。
- **工程模式**：为一个长期项目建立专属团队，让 PM 和项目成员以独立会话持续工作。

这三种方式不是三个互相割裂的产品，也不是“低级、中级、高级”三个等级。它们可以在同一个工作区里配合使用，用户可以根据当前任务自由选择。

---

## 2. 为什么要做 Magic

现在的 Agent 产品已经能写代码、查资料、改文件和运行工具，但用户经常遇到四个问题：

1. **简单事情也要先做很多管理工作**

   用户本来只想说“帮我修复这个问题”，却要先选择角色、建立团队、配置流程、维护任务列表。

2. **任务一复杂，就不知道是谁在负责**

   多个 Agent 可能都在工作，但用户不清楚谁接到了任务，谁正在处理，结果由谁确认。

3. **Agent 用完就消失，前面的工作难以复用**

   临时 Agent 完成一次分析后，下一次还要重新解释背景。长期项目也缺少真正属于项目的成员和会话。

4. **运行结束不代表事情真的完成**

   底层程序可能已经停止，但文件是否写入、结果是否通过验收、是否还有风险，不能只看“运行结束”四个字。

Magic 要解决的是“工作如何自然地被组织起来”，而不是重新发明一个更复杂的 Agent 管理后台。

---

## 3. Magic 的核心体验

用户在 Magic 里应该有这样的感觉：

1. 我先说我要做什么，不必先填写一张编排表。
2. 简单任务，AI 直接开始做。
3. 复杂任务，AI 会把任务拆开，并说明谁负责哪一部分。
4. 我能看到任务目前做到哪一步、下一步是什么、结果在哪里。
5. 我临时想到新要求，可以直接告诉当前会话或项目 PM，不必自己维护复杂队列。
6. 我可以在代理、CEO 和工程组织之间选择，但不需要重新解释已经说过的目标。
7. 涉及重要文件、外部系统或其他有风险的动作时，我知道 AI 做了什么，并能决定是否批准。
8. 失败就明确告诉我失败；不确定就告诉我需要核对，不把“程序停了”伪装成“任务成功”。

## 4. Magic 和 OpenCode 的关系

### 4.1 OpenCode 负责什么

OpenCode 是 Magic 的首版执行底座。它负责 Agent 真正工作的基础能力，例如：

- 接收消息并进行推理；
- 读取和修改文件；
- 执行命令和开发工具；
- 访问项目资源；
- 产生会话、回合、运行过程和工具调用事实；
- 返回文本、文件变化和运行结果。

### 4.2 Magic 负责什么

Magic 在 OpenCode 上面增加产品层的组织能力：

- 代理、CEO、工程三种工作方式；
- 任务负责人和任务台账；
- 计划、进度和任务验收；
- Agent 之间的派发、汇报和项目归属；
- 受控制的信息共享；
- 资源、分支、修改和合并关系；
- 权限、审批、成本和副作用的可见性；
- 让用户知道现在发生了什么。

简单理解：OpenCode 像“真正干活的执行系统”，Magic 像“把工作组织成团队并向用户解释清楚的产品层”。Magic 不能随意改写 OpenCode 的运行事实，也不能因为界面收到了一个“结束”事件，就直接宣布用户的任务已经成功。

### 4.3 AgentCore 在首版中的位置

AgentCore 对 Magic 的产品设计和机制设计很有帮助，尤其是 Agent 协作、状态收敛和恢复方面的经验。

但是，首版不会把 AgentCore 写成必须经过的生产运行层。首版优先使用 OpenCode 的成熟执行能力，并验证 Magic 自己的任务、责任、信息和结果规则。未来是否让 AgentCore 进入生产链路，需要由技术验证和实际收益共同决定。

## 5. 三种工作方式

## 5.1 代理模式：我说目标，AI 直接做

代理模式是 Magic 的默认入口，也是一种完整、强大的工作方式，不是低级模式。

它适合：

- 修复一个问题；
- 解释一段代码；
- 修改一个页面；
- 查资料并给出结论；
- 运行测试并修复失败；
- 任何用户希望直接交给 AI 处理的事情。

### 例子

用户说：

> “请检查这个登录页面为什么在手机上变形，修好后运行测试。”

主 Agent 会直接开始检查代码、修改文件和运行测试。必要时，它可以在当前会话里找一个临时 Agent 做移动端分析，再把分析结果收回来继续工作。

用户通常只需要关注主 Agent 的进度和最终结果，不需要手动管理临时 Agent。

### 代理模式里的临时 Agent

- 临时 Agent 也是完整 Agent，可以使用正常工具和能力；
- 它的角色由派发任务的人决定，例如“移动端专家”“资料调研员”；
- 它的责任来自这一次派发，不等于永久拥有这个角色；
- 同一个会话内，后续任务仍然可以继续使用它；
- 换到工作区里的另一个新会话时，默认不能直接复用前一个会话的临时成员；
- 如果未来要跨会话或跨工程借调，必须经过明确授权和记录。

---

## 5.2 CEO 模式：让当前 Agent 临时组织一轮工作

CEO 模式适合一次任务里需要多种专业意见、需要统一判断，或者需要有人负责审批、审计和最终确认的情况。

这里的 CEO 不是一个固定的人，也不是另一个底层运行程序。它更像是：

> 用户把这一轮工作交给当前 Agent，由当前 Agent 临时承担 CEO 的组织责任。

CEO 可以根据任务安排不同的完整 Agent，例如：

- 调研专家；
- 产品分析专家；
- 技术架构专家；
- 前端或后端专家；
- 测试专家；
- 结果审计专家。

CEO 要做的事情包括：

1. 理解用户目标和限制条件；
2. 判断需要哪些帮助；
3. 给 Agent 派发清楚的任务；
4. 收集结构化结果；
5. 检查结果是否互相矛盾；
6. 决定是否需要补做、重做或向用户提问；
7. 对最终交付负责。

### 例子

用户说：

> “我想把这个产品改造成面向小团队的 AI 工作台，请先调研竞品，再给出产品方案和技术风险。”

CEO 可能安排：

- 调研专家整理竞品做法；
- 产品专家整理用户流程；
- 技术专家评估 OpenCode 能否支持；
- 审计专家检查结论是否有证据。

最后由 CEO 把各方结果整理成一份用户能读懂的方案，再返回给用户。

### CEO 模式的切换规则

- 用户可以在发起新一轮工作时主动选择 CEO；
- 用户也可以直接在对话中说“这次请用 CEO 方式完成”；
- CEO 可以在同一个会话中继续接收用户的新要求；
- 一旦某一轮运行已经开始，不能把正在运行的底层进程中途改成另一种模式；
- 新模式会从下一轮工作开始生效，不要求用户重新解释已有目标；
- 这一轮结束后，用户可以回到代理方式继续工作；
- CEO 的临时成员可以在当前会话内复用，但不自动变成整个工作区的永久成员。

---

## 5.3 工程模式：为长期项目建立真正的项目团队

工程模式不是把一次任务多派几个 Agent，而是为一个长期项目建立持续存在的组织。

工程模式适合：

- 长期开发一个产品；
- 持续维护一个复杂系统；
- 需要多人分工和多轮交付的项目；
- 需要保存成员记忆、职责和工作历史的工程。

一个工程可以有：

- 一个项目 PM；
- 前端、后端、测试、产品、美术评判等项目成员；
- 每个成员自己的独立会话；
- 每个成员自己的职责、工作历史和记忆；
- 成员继续派发自己的小任务或小团队；
- PM 统一接收结果、调整任务和向用户汇报；
- 圆桌会议，用于让多个成员讨论重要方案。

### 例子

用户创建“电商小程序工程”，PM 负责统筹：

- 产品成员整理需求；
- 前端成员制作页面；
- 后端成员设计接口；
- 测试成员验证功能；
- 视觉成员检查页面效果。

用户通常和 PM 沟通：“先完成下单流程，支付部分放到第二阶段。”PM 再把任务分给项目成员。用户也可以打开某个成员的独立会话，直接询问前端当前卡在哪里。

第一个项目的 PM 派发给的是第一个项目自己的成员。用户同时做第二个项目时，第二个项目会有自己的 PM 和成员，两个项目的团队不能因为角色名称相同就自动混在一起。

### 工程模式的自由度

工程不要求一开始就把团队建满：

- 用户可以只建立一个 PM；
- PM 可以按需要招募成员；
- 用户可以临时创建一个新会话并给它新的角色；
- 新会话可以在得到授权后加入工程；
- 某个成员可以创建自己的小组；
- 用户可以直接进入成员会话处理具体问题；
- 是否建立完整团队，由项目需要决定，不由产品强制决定。

工程模式的长期组织能力会很大，因此首版只先做最小闭环，完整团队画布、圆桌、多层管理和跨工程借调属于后续增量。

## 6. 三种方式如何组合

Magic 的关键不是让用户在三个模式中永久选一个，而是把不同能力组合起来。

可以这样理解：

- **代理、CEO**主要决定“一轮工作由谁来组织”；
- **工程**主要决定“这个项目是否有长期成员和长期关系”；
- **计划**主要决定“任务是否需要分步骤展示和推进”；
- **权限**主要决定“哪些动作可以自动做，哪些动作要问用户”。

所以，一个用户可以：

1. 在普通代理会话中直接完成小任务；
2. 下一轮任务选择 CEO，请临时组织调研；
3. 调研完成后，在同一个会话里要求建立一个长期工程；
4. 工程 PM 接手长期项目，持续派发项目成员；
5. 某个项目成员遇到困难时，再使用 CEO 方式组织一轮专项分析；
6. 项目完成后回到普通代理会话处理其他小事。

这不是产品割裂，而是同一个工作目标在不同阶段采用不同的组织方式。

---

## 7. 用户该如何选择

产品默认优先让用户开始工作，而不是强迫用户先做组织设计。但用户拥有主动选择权。

### 建议选择

| 用户面对的事情 | 建议方式 | 白话理解 |
|---|---|---|
| 一个明确的小问题 | 代理模式 | “你直接帮我做完。” |
| 一次任务需要多种专业判断 | CEO 模式 | “你来组织几个人帮我完成这一轮。” |
| 项目会持续很久，需要成员反复工作 | 工程模式 | “给这个项目建立一支长期团队。” |
| 任务步骤多，希望看到过程 | 计划模式 | “告诉我分几步做，现在做到哪一步。” |
| 涉及重要文件或外部系统 | 审批模式 | “关键动作先问我。” |

### 用户可以随时表达自己的意图

例如：

- “直接帮我改好。”
- “这次请用 CEO 方式，找一个架构专家评估。”
- “把这个项目建立成工程，先创建 PM 和测试成员。”
- “这个任务分步骤做，每一步告诉我进度。”
- “涉及删除文件时先问我。”

如果用户没有明确选择，Magic 可以根据任务复杂度给出建议，但不能擅自把用户带进庞大的工程组织，也不能把模式升级当成强制流程。首次使用时可以告诉用户有哪些选择，用户之后可以关闭重复提示。

## 8. 一个完整使用例子

下面用“做一个产品官网”说明 Magic 如何自然地成长。

### 第一步：代理模式开始

用户说：

> “帮我做一个产品官网，先给我一个能运行的版本。”

代理 Agent 直接开始工作。它读取项目文件，创建页面，运行检查，并向用户返回结果。

### 第二步：用户需要专项判断

用户又说：

> “在继续写之前，请用 CEO 方式找一个产品专家和一个视觉专家，判断这个方向是否合适。”

当前会话开始一轮 CEO 工作。CEO 安排两个临时成员，分别给出建议，再统一整理结论。用户不用自己打开三个会话，也不用重新提供官网背景。

### 第三步：用户决定长期建设

用户说：

> “这个官网后面还要持续迭代，建立一个工程，先安排 PM、前端和测试。”

Magic 建立工程团队。此后的长期需求主要进入项目 PM 会话。PM 为当前工程的成员分派任务，每个成员拥有自己的独立会话和职责。

### 第四步：工程中插入新需求

用户在 PM 会话中说：

> “新增一个多语言需求，但不要影响本周发布。”

PM 收到新需求后，把它放进最新任务清单，重新安排优先级，并告诉用户：本周发布继续进行，多语言作为下一项任务。

“通知 PM”不等于所有工作都必须停下来等待 PM 审批。PM 需要判断哪些任务可以继续，哪些任务确实有依赖关系。

### 第五步：结果交付

任务结束时，Magic 告诉用户：

- 谁负责了任务；
- 做了哪些工作；
- 哪些文件发生了变化；
- 测试是否通过；
- 哪些结果已经验收；
- 哪些风险仍需用户决定。

如果底层 OpenCode 只是运行结束，但文件没有正确写入，或者测试没有通过，Magic 必须显示真实状态，而不是显示“已完成”。

## 9. Agent、会话和团队到底是什么关系

用户不需要记住下面的技术名词，但需要理解它们的区别。

### 9.1 会话

会话就是一段可以持续交流的工作空间。用户创建的对话是会话，Agent 为项目成员创建的对话也是真实会话。

它们都可以拥有自己的上下文、记忆、工具和工作历史。

### 9.2 Agent

Agent 是真正执行工作的 AI。所有 Agent 都是完整 Agent，角色只说明“这次希望它从什么角度工作”，不代表它能力低，也不代表它天然拥有所有权限。

例如“测试专家”仍然可以使用正常工具，但它能不能修改主分支，要看当前授权，而不是看名字。

### 9.3 会话成员和工程成员

- **会话成员**：为了当前会话或当前一轮工作加入，通常是临时关系。当前会话可以继续复用它。
- **工程成员**：属于某个长期工程，有自己的项目职责和独立会话，能够跨多次任务持续工作。

一个临时 Agent 后来可以被正式挂接到工程里，但这必须是明确的产品动作，不能因为它完成过一次任务就自动成为项目成员。

### 9.4 PM 和 CEO

- **CEO**：更像一次任务中的组织负责人，通常是临时的。
- **PM**：属于一个长期工程，负责项目任务安排、成员协调和项目汇报。

同一个 Agent 在不同场景下可以承担不同职责，但它的责任、归属、可见范围和权限必须被清楚记录。

## 10. Magic 如何保证“责任到人”

每个正式任务在任何时候只有一名当前责任人。

责任人可以是用户、主 Agent、CEO、PM 或某个项目成员。

派发任务不等于原责任人自动免责。例如：

- 用户把任务交给主 Agent，主 Agent 是当前责任人；
- 主 Agent 派给调研 Agent，调研 Agent 负责调研子任务；
- 主 Agent 仍然负责把调研结果合并成正确的最终交付；
- CEO 派发给架构专家，CEO 仍负责判断架构建议能否用于最终方案；
- PM 派给前端成员，PM 仍负责向用户说明项目整体状态。

等待、失败、断线、重试或子 Agent 出错，都不会自动把责任转给别人。只有明确记录了新的责任人和交接原因，责任才会改变。

这样用户永远可以追问：

> “这件事现在由谁负责？他正在做什么？结果要交给谁？”

## 11. Agent 如何共享信息

Magic 不会默认把所有会话的完整聊天记录互相开放。

这样做是因为“共享全部内容”看起来方便，实际上会带来三个问题：

- Agent 会读到大量无关内容；
- 不同项目的信息可能混在一起；
- 用户无法判断哪些信息被使用了。

Magic 的协作重点是传递“完成工作所需的信息”，而不是复制整段聊天记录。

### 11.1 默认共享的内容

一个 Agent 把结果交给另一个 Agent 时，应该尽量包含：

- 要解决的问题；
- 已知的背景和限制；
- 已完成的工作；
- 得出的结论和证据；
- 产生的文件或其他产物；
- 未解决的问题和风险；
- 建议的下一步；
- 结果由谁负责、交给谁使用。

这可以理解为一张“工作交接单”。

### 11.2 信息访问的边界

- 每个会话默认只看到自己的内容；
- 派发者可以明确允许它读取某些任务、文件或共享结论；
- Agent 只获得完成当前任务所需的最小信息；
- 访问范围可以过期、撤销和审计；
- 跨会话、跨工程的信息访问不能因为“都是同一个用户”就自动开放。

### 例子

产品 Agent 让技术 Agent 评估“多语言功能是否能在本周完成”。技术 Agent 不需要读取产品 Agent 的全部聊天记录，只需要看到：目标、时间限制、页面范围、当前代码位置和相关设计结论。它完成评估后返回一张交接单，PM 再决定是否调整计划。

---

## 12. 计划、进度和真实状态

计划模式不是只有工程模式才有。只要任务足够长，任何 Agent 都可以使用计划，把工作拆成几个步骤并持续展示进度。

计划的作用是让用户知道：

- 目标是什么；
- 总共有哪几步；
- 当前正在做哪一步；
- 已经完成什么；
- 下一步是什么；
- 有没有被阻塞。

计划模式不等于创建了多个 Agent。一个 Agent 完全可以自己列计划、逐步执行，不需要为了显示进度而人为增加团队成员。

Magic 必须区分下面几件事：

- **运行结束**：底层这一次执行已经停止；
- **任务成功**：结果通过了任务要求和验收；
- **任务失败**：任务没有达到要求，且需要修复或重新尝试；
- **任务等待**：需要用户审批、补充信息或人工核对；
- **任务部分完成**：部分结果已经产生，但整体目标还没有完成。

例如，OpenCode 已经结束运行，但测试失败，Magic 应显示“运行结束，任务未通过测试”，而不是简单显示“成功”。

---

## 13. 权限、审批和副作用

Agent 能力很强，但不是所有动作都应该自动做。

Magic 采用三种基本处理方式：

- **允许**：符合当前授权，可以直接执行；
- **询问**：执行前需要用户或上级 Agent 批准；
- **拒绝**：当前不允许执行。

用户可以选择适合自己的权限入口：

1. **请求批准**：重要动作都先问用户；
2. **当前范围内自动处理**：在当前工程和授权范围内自动做，超出范围再问；
3. **完全访问当前工程**：允许 Agent 在当前工程范围内自主工作，但仍需遵守明确的系统限制。

### 需要特别告知用户的动作

- 修改或删除文件；
- 写入外部系统；
- 发布、部署或发送消息；
- 使用可能产生费用的服务；
- 影响其他工程或其他成员的动作。

用户需要知道的不只是“调用了什么工具”，还包括“实际产生了什么变化”。如果文件已经改了但记录还没有及时保存，系统不能自动重试造成重复副作用，也不能伪造一条成功记录；无法确认时应进入人工核对。

### Git 和重叠修改

工程可以关联多个资源。一个资源被多个 Agent 同时修改时，首版不允许多个责任主体直接写同一工作位置。

需要并行修改时，使用独立分支或 worktree。每次修改形成 ChangeSet，之后再通过 MergeTask 合并到主资源。这样用户能看清：谁改了什么、是否冲突、谁负责合并。

---

## 14. 用户应该看到什么

Magic 的界面首先应该是工作台，而不是管理后台。

用户在主要工作区至少应该能看到：

- 当前正在处理的目标；
- 当前责任人；
- 任务目前的真实状态；
- 当前步骤和下一步；
- 哪些 Agent 在协作；
- 每个 Agent 的任务和进度；
- 结果和文件产物在哪里；
- 哪些动作已经发生；
- 是否需要用户审批或人工核对；
- 失败、风险和阻塞原因。

用户可以深入查看某个成员的独立会话，也可以只看 PM 或主 Agent 的总结。默认呈现应该帮助用户做决定，而不是把所有底层事件全部堆到屏幕上。

未来可以增加团队画布：在画布上看到每个会话的任务、责任、当前工作、上报对象、派发对象和结果去向。但画布是任务台账的可视化，不应成为另一套互相矛盾的状态来源。

---

## 15. 首版先做什么

首版的目标不是一次做完完整的“AI 公司”，而是先证明最小闭环可靠。

首版范围暂定为：

- 单用户；
- 单工程；
- 一个当前 PM；
- 一个项目成员；
- 一个正式成员任务；
- 一个 Git 主资源；
- 一个独立 worktree；
- 主 Agent 或 PM 可以派发一个协作任务；
- Agent 返回结构化结果、文件产物和修改记录；
- 用户能看到责任、进度、结果和真实终态；
- 具备最小的允许、询问、拒绝和审批恢复流程；
- 能验证断线、重连、重启、重复事件、乱序事件和副作用核对。

首版必须先让下面这条链路可靠：

> 用户提出目标 -> Magic 创建任务 -> Agent 执行 -> 必要时派发协作任务 -> 结果和产物回传 -> Magic 汇总 -> 用户验收或继续处理。

---

## 16. 首版暂时不做什么

以下能力是重要方向，但不作为首版自动放行的内容：

- 两个或更多项目成员并发修改同一资源；
- 成员身份在多个会话之间自动复用；
- PM 自动交接和复杂的 PM 故障接管；
- 自动冲突合并；
- 完整的停止、重开和复杂恢复交互；
- 团队画布的全部可视化能力；
- 圆桌会议的完整机制；
- 多层 PM、组长和组员的复杂层级；
- 跨工程成员借调；
- 多用户、多端协作；
- AgentCore 必须参与的生产运行链路。

这不是否定这些方向，而是先把最小可用闭环做稳。首版验证通过后，再按照真实用户需求和技术证据增加复杂组织能力。

## 17. 当前项目阶段和开发门槛

当前阶段不是产品方向讨论期，也不是已经可以无限扩张开发的阶段，而是：

> **开发前技术发现与契约收敛期。**

产品方向已经可以进入开发准备，技术团队还需要完成底座和关键行为的验证。首次正式开发的条件是：

1. 锁定首版使用的 OpenCode runtime、client 和运行环境；
2. 产品和技术共同签署三份 P0 架构文档；
3. F-10 技术验证在锁定环境中可重复通过；
4. 断线、重连、进程重启、审批、停止、取消、重试和副作用不确定等情况都有诚实处理；
5. 五位技术总监共同接受验证证据。

在这些条件完成前，首次正式开发仍然是 **No-Go**。这不代表产品不能继续设计，而是不能在底层行为尚未验证时，把大量产品承诺直接写成代码。

## 18. 产品成功标准

Magic 首版是否成功，不以“创建了多少 Agent”衡量，而以用户能否放心地把工作交出去衡量。

至少要满足：

1. 用户做简单任务时，不需要先管理团队。
2. 用户需要协作时，可以自然地使用 CEO 或临时 Agent。
3. 长期项目可以拥有清晰的 PM、成员和独立会话。
4. 每个正式任务都能找到当前责任人。
5. 用户能区分运行结束、任务成功、失败、等待和部分完成。
6. Agent 的结果可以复用，但不会无边界地读取其他会话。
7. 文件变化、外部动作和风险都能被看见和追溯。
8. 断线、重启和重复消息不会让系统伪造成功或重复执行有副作用的动作。
9. 用户可以在需要时深入管理，但不被迫一直做管理工作。

## 19. 需要所有成员记住的几条原则

- **先让工作开始，再要求组织设计。**
- **代理模式不是低级模式。**
- **CEO 是一轮工作的组织方式，不是正在运行的底层进程类型。**
- **工程模式是长期组织，不是复杂任务的自动升级按钮。**
- **用户可以主动选择模式，系统不能替用户强制升级。**
- **所有 Agent 都是完整 Agent，角色、权限、归属和责任必须分开。**
- **同一正式任务任何时候只有一名当前责任人。**
- **Magic 的任务台账记录产品状态，OpenCode 提供运行事实。**
- **运行结束不等于任务成功。**
- **共享结构化结果和必要事实，不默认共享完整会话。**
- **用户可以给 PM 插入新需求，但插入需求不等于所有工作必须停下来。**
- **发生过的副作用必须诚实记录，无法确认时必须让人核对。**
- **工程团队应该逐步形成，不要求一开始就建满。**

## 20. 名词解释

| 名词 | 白话解释 |
|---|---|
| 工作区 | 用户放置多个工程和会话的总空间。 |
| 工程 | 一个有长期目标、资源、PM 和项目成员的项目。 |
| 会话 | 一段可以持续交流和工作的对话空间。 |
| Agent | 真正思考、调用工具和执行任务的 AI。 |
| 任务 | 用户或 Agent 要完成的一件事情。 |
| 回合 | 用户提出一次要求后，系统围绕这次要求进行的一轮工作。 |
| 运行 | 底层 Agent 实际执行工具和推理的过程。 |
| 计划 | 把一个较长任务拆成步骤并展示进度。 |
| 当前责任人 | 现在必须对任务下一步和结果负责的人或 Agent。 |
| CEO | 当前一轮工作中的临时组织负责人。 |
| PM | 一个长期工程中的项目负责人。 |
| 会话成员 | 当前会话或当前任务临时使用的 Agent。 |
| 工程成员 | 长期属于某个工程、拥有独立会话的 Agent。 |
| 产物 | 任务产生的文件、方案、报告、代码或其他可交付结果。 |
| ChangeSet | 一组可以被查看、审查和合并的修改。 |
| worktree | 给某次独立修改准备的工作目录，避免多人直接改同一位置。 |
| 副作用 | 文件修改、发布、发送消息、外部写入等真实变化。 |
| 结果交接单 | Agent 交给另一个 Agent 的结构化结论、证据、产物和风险。 |

## 22. 本 PRD 的后续维护规则

当产品发生新的重要裁定时：

1. 先在对应的专题文档中记录完整规则和案例；
2. 再把影响用户理解的结论同步到本 PRD；
3. 明确标记它是“已确认”“首版范围”还是“后续方向”；
4. 技术实现细节仍然写入架构文档，不把本 PRD 变成代码设计文档。

这样 Magic 可以继续变得强大，但用户第一次打开主文档时，仍然能读懂它到底是什么。
