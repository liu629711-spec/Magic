# Magic 产品一页纸

> 本文是 Magic 的快速理解入口，不替代方向总纲、产品契约或技术会议结论。读完本文后，按议题进入对应专题，不需要第一次就通读全部产品资料。

## 一、Magic 是什么

Magic 是建立在 OpenCode 之上的统一 AI 工作台：用户可以直接把目标交给 Agent，也可以在需要时让 Agent 组织会话内协作，还可以在确认后围绕长期项目建立自己的 Agent 工程组织。

一句话定位：

> **简单的事，直接做；复杂的事，组织做；长期的事，建成一支持续工作的 Agent 团队。**

Magic 的价值不是让每个任务都调用更多 Agent，而是让工作可以在同一产品内自然成长，同时保持连续、可见、可控和可追责。

## 二、两个组合维度

```text
会话工作方式：代理方式 / CEO 方式
长期组织形态：非工程工作 / 工程组织
```

| 维度 | 解决的问题 | 用户心智 |
|---|---|---|
| 代理方式 | Agent 直接理解、执行、验证和交付 | 我交代目标，你直接帮我完成 |
| CEO 方式 | Agent 显式组织会话成员分工、协调和汇报 | 我把目标交给 CEO，由 CEO 组织完成 |
| 非工程工作 | 用户自行通过会话和文件持续工作 | 我按自己的方式推进 |
| 工程组织 | 项目拥有专属 PM、成员、任务会话和长期治理 | 我建立一支长期建设这个项目的团队 |

代理与 CEO 是平等的会话工作方式；工程是长期组织形态。工程内部仍可使用代理或 CEO，用户也可以永远不建立工程。

## 三、三个必须区分的行为

| 行为 | 会发生什么 | 不会发生什么 |
|---|---|---|
| 代理内部调用协作者 | 主 Agent 为完成任务调用临时 Agent 或复用会话成员 | 不自动进入 CEO，不自动建立工程 |
| 当前任务启用 CEO | 当前任务形成可查看、可协调的显式协作结构 | 不自动改变会话默认，不自动产生项目成员 |
| 建立或进入工程 | 创建长期项目组织、PM、成员和工程任务边界 | 不应由复杂度、耗时或 Agent 数量自动触发 |

## 四、核心生命周期边界

```text
临时执行 Agent：只服务局部工作
会话成员：属于一个会话，可在本会话多个任务中复用
项目成员：属于一个工程，可在本工程多个会话和任务中复用
会话主 Agent：面对用户并负责当前会话收口
项目 PM：负责工程计划、派发、汇报收敛和项目级协调
运行实例：一次真实执行尝试，不等于 Agent 身份或任务最终状态
```

共享文件不等于共享身份、私有记忆、权限或工程关系。不同工程即使使用同一角色模板，也默认拥有不同的成员实例和项目记忆。

## 五、首版先验证什么

首版优先验证一个单用户、单工程的完整闭环：

```text
建立工程 → 确认 PM → 配置少量成员 → PM 创建任务会话
→ 成员执行并汇报 → 回收状态、事实和产物
→ 用户查看进度或直达成员 → PM 获知影响并重新协调
```

首版建议从一名 PM、2 至 4 名项目成员、一个主工作区和一个主目录开始。这些是验证约束，不是永久产品上限。

## 六、不可违反的产品原则

- 代理方式不是低级模式，CEO 方式不是强制升级路径。
- 用户可以直接选择初始工作方式，也可以只为一次任务使用 CEO。
- 系统可以建议，但不能未经确认建立长期工程、长期成员或跨边界记忆关系。
- 任务任一时刻只有一名当前责任人，任务状态与运行状态必须分离。
- 失败、部分完成、等待、停止和取消不能被包装成成功。
- 模式变化尽量保持目标、上下文、产物和责任连续；无法无损时必须说明影响。

## 七、技术会议当前只需回答

1. 锁定 OpenCode 版本，并用实机证据确认哪些能力原生满足、需要适配、需要 Magic 补建或当前不支持。
2. 确认 Magic 任务、会话、Agent 身份、工程和运行实例之间的映射。
3. 确认任务责任、状态真相源、模式作用域、执行中移交、权限和副作用边界。
4. 对 `U-01` 至 `U-12` 给出方案、代价、风险和推荐，再由产品负责人裁定。
5. 用端到端场景验证首版闭环，不以 Agent 数量或页面数量代替产品验收。
