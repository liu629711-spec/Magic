# 任务结果回传与受控信息访问

> 本文是 U-08 的专题产品契约。它规定多个独立 Agent 如何协作，不要求 Agent 共享完整会话，也不要求用户维护一套事实审批后台。字段名、接口、数据库结构和底层实现由技术团队另行设计。

## 一、正式裁定

Magic 的协作核心是：

```text
最小任务上下文
→ 独立 Agent 执行
→ 结构化任务结果回传
→ 文件和证据按需查看
→ 责任人验收并继续派发
```

因此：

- Agent 会话、完整能力、私有记忆和权限默认保持独立；
- 子 Agent 必须把可交付结果交给指定接收者；
- 结果回传不等于共享完整 transcript；
- 文件和产物是独立资源，不因为写入某个工作区就自动对所有 Agent 开放；
- 共享事实和项目决定是沉淀后的可引用材料，不等于原始会话；
- 需要更多资料时，由任务关系和权限策略决定是否允许，不让用户逐条管理普通信息。

一句话：

> Agent 不互相偷看完整工作现场，但会把该交的结果交回来；需要查证时，只打开对应的文件、测试记录或任务证据。

## 二、四层协作信息

### 2.1 任务上下文

任务上下文是 Agent 开工时获得的必要材料，通常包括：

- 任务目标和验收标准；
- 当前角色、责任关系和结果接收者；
- 相关文件、资源和项目规则；
- 已确认的项目决定和适用的技术事实；
- 可使用的工具、目录、外部资源和预算边界；
- 已交付且与当前任务相关的结果。

任务上下文不是父会话全文复制。用户和 PM 的完整讨论、无关任务、私有记忆、其他项目资料和隐藏推理不自动进入其中。

### 2.2 任务结果

任务结果是子 Agent 向父 Agent、当前责任人或指定接收者提交的正式汇报。产品上必须能表达：

```text
为哪个任务工作
当前状态
完成了什么
结论或主要发现
产物在哪里
依据什么验证
未完成事项
风险、阻塞或待决定问题
建议下一步
```

结果状态至少要能区分：

```text
已完成 / 部分完成 / 失败 / 阻塞 / 已取消 / 待审查
```

状态不能只由 Agent 的一句“完成了”决定。比如运行已经结束但测试失败，结果可以是“部分完成”或“待审查”，不能直接包装成成功。

### 2.3 文件与产物

文件、diff、截图、测试报告、构建结果和外部资源属于产物或证据，不属于会话上下文。

父 Agent 默认收到产物的引用和说明，例如：

```text
修改文件：src/auth/token.ts
变化：调整测试环境 Token 过期时间
验证：登录单测通过，退出码为 0
状态：待主 Agent 完整回归
```

父 Agent 可以按需查看 diff、打开文件或重新运行测试。文件存在不等于交付完成，交付完成也不等于父任务完成。

### 2.4 项目知识与决定

只有经过整理、引用和适用范围确认的信息，才进入项目级知识或决定层，例如：

- 当前项目采用的接口约定；
- 用户确认的业务目标；
- 已采纳的技术方案；
- 当前项目的验收规则；
- 已验证的技术事实；
- 已知风险和限制。

Agent 判断、用户陈述、项目决定和客观执行事实必须分开。一个 Agent 的建议可以作为项目决定的依据，但不会自动变成客观事实。

## 三、结果如何回到主会话

标准流程是：

```text
1. 主 Agent 或 PM 建立正式任务
2. 系统确定责任人、结果接收者、工作范围和权限
3. 系统提供最小任务上下文
4. 子 Agent 在独立会话中执行
5. OpenCode/AgentCore 记录运行、工具、文件和测试事实
6. 子 Agent 提交任务结果
7. 系统将结果通知指定接收者
8. 接收者按需读取产物和验证证据
9. 当前责任人判断采纳、复核、补充派发或结束任务
10. Magic 任务账本更新产品任务状态
```

结果回传是定向的：

```text
子 Agent → 指定接收者
```

不是：

```text
子 Agent → 所有 Agent 自动获得全部上下文
```

工程模式下，PM 可以收到成员结果并重新规划；CEO 模式下，CEO 可以比较多个专家结果；代理模式下，主 Agent 可以直接吸收结果并向用户交付。底层都遵守同一套回传规则。

## 四、信息访问规则

### 4.1 默认可见内容

在任务关系和权限允许的前提下，Agent 默认可以获得：

- 自己的任务上下文；
- 自己负责或被授权查看的任务状态；
- 指定接收者收到的任务结果；
- 已发布且适用于当前项目的决定和事实；
- 相关产物引用、文件 diff 和测试报告；
- 当前工作所需的项目规则。

### 4.2 默认不可见内容

以下内容不因“可能相关”就自动开放：

- 父会话、兄弟会话或下属会话的完整 transcript；
- 其他 Agent 的私有记忆和隐藏思考；
- 其他项目的会话、文件、商业资料和权限；
- 与当前任务无关的凭据、个人信息和敏感资源；
- 没有被发布或授权的内部讨论。

### 4.3 超范围信息请求

Agent 需要更多信息时，应提出明确请求：

```text
需要什么：部署配置摘要
为什么需要：确认线上数据库类型
访问方式：仅读取
影响：不提供则无法完成环境判断
```

处理规则：

- 同项目、低风险、与任务直接相关的文件或结果，可以自动允许；
- 任务结果、已发布决定和相关证据优先由父 Agent 或 PM 处理；
- 私有会话、跨项目内容、凭据和高风险资源默认拒绝或升级给用户；
- 允许读取某项结果，不等于允许继续向下派发或读取该 Agent 的完整会话；
- 访问必须保留主体、资源、目的、范围、时间和授权来源。

### 4.4 文件可见性不能只靠会话隔离

如果多个 Agent 使用同一个工作区，仅隔离聊天记录是不够的。Magic 必须在产品和技术上分别表达文件范围，例如：

```text
私有：仅当前会话
任务：当前任务相关主体
项目：项目授权成员
工作区：工作区授权主体
```

底层必须通过工具网关、路径权限、隔离工作树或其他真实机制执行限制。界面上显示“不可见”，但工具仍可读取，不算实现了隔离。

## 五、三种模式中的表现

### 5.1 代理模式

```text
用户提出目标
→ 主 Agent 判断需要帮助
→ 派发完整 Agent
→ 收到结果、产物和验证依据
→ 主 Agent 复核并向用户交付
```

用户通常只看到主 Agent 的进展和最终结果，必要时可以展开子任务。

### 5.2 CEO 模式

```text
CEO Agent
→ 派发调研、架构、性能等完整 Agent
→ 分别收到结果包
→ 比较证据和方案分歧
→ 形成决定或向用户提出取舍
→ 继续派发执行任务
```

三个专家分别推荐 Redis、消息队列和数据库方案时，这是方案判断和取舍，不应直接包装成三个互相冲突的客观事实。

### 5.3 工程模式

```text
PM
→ 给后端成员派发接口任务
→ 收到接口变更结果和测试证据
→ 将必要的接口约定发布给前端和测试成员
→ 成员按需读取产物
→ PM 根据验收结果重新规划
```

前端不需要读取后端完整开发过程，只需要收到接口交付、相关文件和测试结果。PM 也不需要把每个成员的所有思考转发给用户。

## 六、完整案例

用户说：

> 请修复登录页测试失败，并确保相关测试通过。

主 Agent 建立任务，并派发后端 Agent 检查 Token 配置。后端 Agent 获得认证模块相关文件、验收标准、测试命令和编辑权限，但没有获得主会话全文。

它修改配置并运行测试。底层记录运行开始、文件修改、测试命令、退出码和运行结束。它向主 Agent 返回：

```text
状态：待审查
结论：已修复测试环境 Token 配置问题
产物：认证配置文件 diff
验证：登录单测通过，退出码为 0
未完成：完整回归测试尚未执行
风险：生产环境配置尚未验证
下一步：主 Agent 执行完整登录回归测试
```

主 Agent 自动收到这份结果，按需打开 diff 并执行回归测试。如果回归通过，主任务才能完成；如果回归失败，子任务可以部分完成，主任务进入待继续处理。

用户最终看到的是：

```text
登录测试问题已修复。
已修改：认证配置文件
验证：登录测试和完整回归测试通过
责任：主 Agent 已完成最终验收
```

用户默认不需要看到子 Agent 的完整会话、无关工具日志和私有记忆。

## 七、首版范围与明确不做

首版必须具备：

- 子 Agent 结果能回到指定父 Agent 或责任人；
- 结果至少包含状态、完成内容、产物、验证依据、未完成事项和下一步；
- 文件和证据可以引用到来源任务和运行记录；
- 结果回传与完整会话读取分开；
- 同项目相关信息可以按策略自动允许；
- 超范围信息可以请求、拒绝或升级；
- 任务状态不因 Agent 的口头完成或底层运行结束而自动成功；
- 事实、判断、决定、用户陈述和执行事实分开；
- 事实或决定变化时保留历史，并能发现受影响任务。

首版明确不做：

- 全量 transcript 自动广播；
- 全自动事实真伪裁判；
- 每条信息都需要用户点击确认；
- 自动把所有聊天内容沉淀为永久记忆；
- 跨项目无限共享；
- 因事实变化自动回滚全部文件；
- 复杂知识图谱编辑器；
- 仅靠 UI 标记实现文件和权限隔离。

## 八、验收场景

1. 代理模式派发调研 Agent，主 Agent 收到摘要、证据引用和无文件说明，不读取完整子会话也能继续工作。
2. 子 Agent 修改文件后返回 diff、测试结果和未完成事项；文件存在但测试失败时，任务显示部分完成或待审查。
3. CEO 同时收到三个专家结果，能够比较方案和证据，但不会把三个建议自动变成三个事实。
4. 工程模式后端发布接口交付，前端读取接口结果和相关产物，不获得后端完整会话。
5. Agent 请求同项目相关低风险文件时可以自动处理；请求跨项目私有资料或凭据时被拒绝或升级。
6. 用户提出与当前工作区状态冲突的描述时，系统同时展示用户陈述和可复现证据，并询问范围，不静默覆盖任一方。
7. 共享决定被替代后，原运行和产物保留，只有依赖旧决定的任务被标记为需要复核。
8. 多个 Agent 使用共享工作区时，未授权文件读取会在工具层被拦截，而不是只在界面隐藏。

## 九、待技术核查

技术团队需要围绕以下事实提交版本、复现方式、限制和证据：

- OpenCode 子会话创建、结果回收和父子关联；
- 结果回传是否支持前台等待、后台通知和断连恢复；
- 文件、diff、测试报告和运行记录的来源绑定方式；
- 同一工作区下的路径权限、隔离工作树和并发修改冲突；
- 超范围信息请求的拦截点、审计记录和升级流程；
- 任务结果、底层运行事实和 Magic 任务状态的最终收敛。

产品结论不预设 OpenCode 已经原生满足以上全部能力。每项技术结论必须标记为：原生满足、适配后满足、Magic 需补建、当前不支持或仍未知。
