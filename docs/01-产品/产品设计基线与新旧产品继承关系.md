# 产品设计基线与新旧产品继承关系

> 本文是 Magic 重构阶段的产品设计工作基线。它先回答“旧产品带来了什么事实、Magic 要重新设计什么”，不替代各模式专题，也不把工程模式的未验证设想写成实现契约。

本文是证据与继承依据，不是当前首版功能清单。它解释 AgentCore 和 OpenCode 的职责边界；具体产品裁定以《Magic 最终产品裁定与技术会议输入》为准，历史讨论以三方会议纪要为准。

## 一、设计前提

Magic 建立在 OpenCode 之上，同时继承 AgentCore 已经完成过产品设计和试运行的经验。

这里有两个不能混淆的事实：

1. AgentCore 已经实现了 Multi-Agent 协作和相当完整的 CEO 编排能力，并在既有试运行范围内验证了这类协作的可用性。这是实现与有限试运行证据，不等同于大规模市场验证。
2. AgentCore 的主要痛点不是“没有协作能力”，而是用户容易先感受到协作组织和编排管理，难以把它当成一个可以直接交代目标、持续完成工作的自然 Agent 工作台。

因此，Magic 不是从单 Agent 重新起步，也不是把 AgentCore 的 CEO 产品原样迁移。Magic 要做的是重新安排能力出现的层级和时机：先让用户自然地把工作交给 Agent，再在确有需要时展开 CEO 协作，最后为长期项目提供工程组织。

## 二、旧 AgentCore 的产品事实

### 2.1 核心定位与主循环

旧产品将自己定位为 Multi-Agent AI 工作台，核心心智是用户作为老板，掌管由 AI CEO 带队的 Agent 团队。它已经形成了清晰的主循环：

```text
说目标 → 自动判断轻重并组队 → 看见协作过程 → 在决策点拍板 → 收到真实产物 → 记住可复用信息
```

这一主循环仍然是 Magic 最重要的产品资产。其中“看见协作过程”“只在真决策点询问”“交付诚实”和“记住可复用信息”尤其值得继承。

### 2.2 已形成的 CEO 与协作资产

从旧产品文档和实际试运行经验看，以下能力已经形成成熟的产品或运行时设计资产：

- 一个面向用户的 CEO 主 Agent 和统一收尾声音
- CEO 根据任务轻重决定直答或委派，而不是所有请求都机械组队
- 基于依赖关系的并行、串行和混合执行
- 子 Agent 的独立上下文、任务结果和向上汇报
- 多轮编排、追加任务、重新规划和同一队员带现场继续工作
- Agent 之间通过产物、简报、共享便签和升级通道协作
- 用户在关键决策、阻塞和权限边界处介入
- 协作过程时间线、内嵌协作图、队员详情和统一状态呈现
- 停止、排队、插话、挂起、恢复和断连后的事实收敛
- 失败、部分完成、取消、等待和真实交付的区分
- 工作区文件、产物、修改记录、验证结果和交付状态的关联
- 用户偏好、文件夹事实、导航和可复用记忆的沉淀

这些能力构成 Magic 的协作底座。它们不应因为增加代理方式就被削弱，也不应全部暴露成用户必须管理的编排工具。这里的“成熟”指已有实现或运行时设计资产，不表示每项能力都可以从 AgentCore 直接迁移到 Magic。

### 2.3 旧文档中的状态分层

旧资料同时包含三种内容，重构时必须分别处理：

| 内容类型 | 处理方式 |
|---|---|
| 文档明确标记已落地、且用户在试运行中验证过的能力 | 作为可继承资产，重新设计入口和产品呈现 |
| 文档明确标记已确认但尚未落地的蓝图 | 作为候选能力重新评估，不默认进入 Magic 首版 |
| 提案、实验项目和被否决设计 | 记录其原因，除非新证据出现，不直接迁入 Magic |

旧文档中大量运行时参数、内部工具名、事件和前端收敛规则是实现经验，不是 Magic 必须沿用的用户概念。Magic 应继承背后的产品原则和可靠性要求，而不是继承所有内部名词。

## 三、旧产品最重要的启示

### 3.1 协作能力强，不等于默认心智自然

旧产品把 CEO 作为主要对话入口，并围绕 CEO、delegate、worker、协作图和检查点组织产品。这个模型有一个很强的优点：用户不需要亲自拆解复杂工作。

但它也会带来一个风险：用户每次表达目标时，都可能感觉自己是在启动一次团队编排，而不是在使用一个能够直接完成工作的 Agent。即使系统内部已经支持轻量直答，用户对产品的第一印象仍可能是“我要管理这支团队”。

这解释了为什么“代理模式”不是把 CEO 降级，而是必须新增一个平等的默认工作方式：让 OpenCode 的直接执行能力成为用户最自然的入口，让 CEO 协作在需要时展开。

### 3.2 子 Agent 的一次性生命周期限制了连续性

旧产品已经具备同一队员续派、上下文交接和多轮编排资产，但普通用户感知到的子 Agent 仍容易是一次任务中的执行节点。任务完成后，用户不知道这个 Agent 是否还存在、能否继续工作、能否在下一条需求中被复用。

Magic 必须把生命周期明确分开：临时执行 Agent、当前会话成员和工程项目成员是三个不同层次。不能通过模糊的“Agent”统称掩盖复用范围。

### 3.3 可见性应服务信任，不应转化为管理负担

旧产品在协作图、时间线、详情面板、检查点和交付对账上积累了很强的经验。Magic 应继续让用户能够看懂“谁在做什么、做到哪里、有什么风险、最终交付了什么”。

但默认界面不应要求用户处理每个任务节点、每次工具调用或每个成员的编制。过程可见和过程必须由用户管理是两件不同的事。

### 3.4 旧产品的“诚实性”必须成为全模式共性

旧产品对部分完成、失败、停止、等待和真实落盘的区分，是不能丢失的底线。代理方式看起来更简单，但不能为了自然而隐藏事实。

无论是 OpenCode 直接执行、代理模式内部调用协作者、CEO 协作，还是工程 PM 汇总，都必须对同一套事实负责：做了什么、没有做什么、结果在哪里、还需要谁介入。

## 四、Magic 的产品设计模型

Magic 采用两个可组合的维度，而不是三个互斥的等级模式。

### 4.1 会话工作方式

| 工作方式 | 主 Agent 的主要责任 | 用户心智 |
|---|---|---|
| 代理方式 | 直接理解、执行、验证和交付；必要时自主调用协作者 | 我交代目标，你直接帮我完成 |
| CEO 方式 | 组织分工、协调依赖、追踪进度、综合结果和统一交付 | 我把目标交给 CEO，由 CEO 组织完成 |

两种方式共享同一个会话主 Agent。代理方式可以调用子 Agent，CEO 方式也可以直接执行；区别在于当前工作的主要责任是否已经转为团队治理，而不是参与 Agent 的数量。

### 4.2 长期组织形态

| 组织形态 | 解决的问题 | 长期对象 |
|---|---|---|
| 非工程工作 | 处理一次或连续但由用户自行组织的工作 | 会话、会话主 Agent、会话成员、任务记录 |
| 工程 | 管理需要持续建设、跨会话复用和明确汇报关系的项目 | 项目 PM、项目成员、成员任务会话、计划、共享事实和治理记录 |

工程内部可以采用代理方式或 CEO 方式。用户也可以不启用工程，只通过多个非工程会话和文件自行组织长期工作。工程提供组织连续性和降低管理成本的能力，不是长期工作的唯一合法路径。

### 4.3 身份生命周期

```text
临时执行 Agent
└── 只服务当前局部工作，完成后不保留持续身份

会话成员
└── 属于一个会话，可跨该会话多个任务复用

项目成员
└── 属于一个工程，可跨该工程多个会话和任务复用

角色模板
└── 可跨工程复用职责和配置，但不复制成员身份与私有记忆
```

在此基础上还需要区分两个长期责任主体：会话主 Agent 对当前会话的用户交互和任务收尾负责；项目 PM 对工程范围内的计划、派发、汇报收敛和项目级协调负责。Agent 身份结束不等于删除历史、产物和交付记录。

默认隔离边界是会话和工程。共享工作区文件不等于共享 Agent 身份、私有上下文、记忆、权限或汇报关系。

### 4.4 工程与工作区的关系

当前设计基线采用以下对象关系，具体字段和权限留给后续专题冻结：

- 工作区是文件、代码、会话和权限等资源的基础边界。
- 工程是建立在工作区之上的长期组织对象，不等同于工作区，也不等同于文件夹。
- 工程可以关联一个或多个文件夹、代码资源和共享事实；关联资源不自动改变其原有路径或所有权。
- 工程的 PM、项目成员、任务会话和治理记录属于工程；普通会话不因使用了某个文件夹就自动成为工程会话。
- 一个工作区可以存在多个相互隔离的工程；跨工程调用、共享私有记忆或继承权限必须经过明确授权。

这套关系是后续工程设计的起点，而不是在本基线中提前冻结全部数据模型。

## 五、能力继承与重新包装

### 5.1 直接继承为底座

以下能力应作为底座能力重新审计和设计：

- Agent 的连续执行、工具调用、文件和代码工作流
- 任务执行状态、停止、恢复、断连收敛和真实结果记录
- 子任务委派、依赖调度、结果回收和多轮续派
- 上下文传递、会话历史、记忆和工作区访问边界
- 权限、审批、沙箱、修改记录和验证结果
- 协作过程的可见性、交付对账和错误收口

来源边界如下：

| 能力来源 | 在 Magic 中的职责 | 处理原则 |
|---|---|---|
| OpenCode | Agent 直接执行、工具调用、代码和文件工作流，以及其已有的会话与权限能力 | 以实际版本能力为准，先完成接口、状态和限制审计，不假定全部能力可直接嵌入 |
| AgentCore | Multi-Agent 协作、CEO 编排、连续调度、上下文交接、可见性和交付诚实性的产品经验 | 优先继承已实现并在试运行中可用的原则与机制；迁移前重新映射对象、事件和权限 |
| Magic | 代理方式、CEO 方式、工程组织以及三者的组合关系 | 负责统一用户心智、生命周期和确认语义，不把两个旧系统的内部名词直接暴露给用户 |

“直接继承”因此表示优先复用和验证已有能力，不表示复制旧系统的界面、数据模型或内部实现。

### 5.2 在代理方式内部自然化

以下旧产品能力不应消失，但默认应收进代理方式的自主执行层：

- 小范围任务拆解
- 临时协作者调用
- 清晰边界的会话成员复用
- 局部验证和交叉检查
- 内部依赖调度
- 轻量结果汇总

用户默认只需要看到工作状态、重要变化、风险和交付。只有用户主动展开，或协作确实成为主要工作结构时，才呈现完整团队视图。

### 5.3 作为 CEO 方式显式呈现

以下情况可以成为系统建议启用 CEO 协作的信号：

- 多条工作线需要持续并行和协调
- 成员之间存在明显依赖、交叉评审或反复协商
- 主 Agent 的主要工作变成分派、追踪、调整和验收
- 用户需要从团队视角观察、干预或在关键决策点拍板

这些信号只用于生成建议，不代表系统自动升级。CEO 体验应复用旧产品的协作图、队员详情、辩论、检查点、升级和统一收尾能力，但将其定位为用户主动选择、预先授权或接受建议后的显式协作方式。

### 5.4 重新设计为工程组织

以下能力不能简单理解为 CEO 团队的“规模放大”，而应作为工程专题分阶段重新设计：

- 项目专属 PM 和 PM 主会话
- 项目成员的长期身份、职责和独立记忆
- 一个成员拥有多个独立任务会话
- PM 自动派发、接收汇报、维护计划和同步依赖
- 成员自行组织局部 CEO 团队
- 用户直达成员但不破坏 PM 的全局知情
- 工程共享事实、权限、圆桌会议和组织治理
- 工程完成、归档、恢复、成员停用和资源回收

首版工程组织优先验证：项目 PM、少量项目成员、成员任务会话、基本派发与汇报、项目共享事实，以及用户直达成员后的 PM 知情边界。多层级派发、复杂圆桌、跨工程协作、复杂权限和规模治理属于后续增强，不应在首版被默认承诺。

这些能力需要用户确认长期关系，不能由一次普通委派或一次模式建议静默创建。

## 六、统一产品原则

### 6.1 先交代目标，再决定组织

用户可以直接向 Agent 提出目标，不需要先填写团队编制、角色名单或流程表单。用户也可以在新会话开始时直接选择代理方式或 CEO 方式。

### 6.2 用户自由选择，系统适度建议

系统可以根据持续周期、协作依赖和用户表达提出 CEO 或工程建议，但建议不能打断当前工作，不能把代理方式说成低级能力，也不能未经确认建立长期组织。

### 6.3 模式可以互相嵌入

代理方式可以在当前任务中启用显式 CEO 协作；CEO 方式可以在局部直接执行；工程中的 PM 或项目成员可以采用代理方式或 CEO 方式；工程不必从一开始建立完整团队。

### 6.4 切换保持连续，边界保持可见

需要严格区分三种行为：

1. **代理内部调用协作者**：主 Agent 为完成当前工作临时拆解、调用或复用会话成员，不改变当前工作方式，也不因为 Agent 数量增加就自动进入 CEO。
2. **当前任务启用 CEO 协作**：当前目标形成用户可理解、可查看、可干预的正式协作结构；它可以是临时的，完成后回到原工作方式。
3. **切换会话默认工作方式**：影响当前会话后续任务的默认入口；是否同时影响执行中的任务、是否作为新会话默认，需要在专题中明确。

代理与 CEO 之间发生上述切换时，默认保留当前会话主 Agent、目标、文件、产物、执行状态和会话成员。普通工作进入工程时，必须明确哪些内容成为工程共享信息，哪些成员转为项目成员，哪些权限和记忆发生变化。

连续性不意味着抹平所有边界。用户不应重新解释已经说过的目标，但也必须知道长期身份和共享范围何时发生变化。

### 6.5 自主调度不等于无限组织

Agent 可以自主拆解和调用辅助 Agent，但长期成员、项目 PM、跨工程调用、扩大权限和持久化项目记忆必须受到明确边界约束。组织层级、成员数量和圆桌会议都不是越多越好。

授权分级的方向是：内部拆解和临时 Agent 可以在当前授权内自主完成；任务级 CEO 协作默认通过建议或用户选择进入；创建工程、创建长期成员、改变权限、跨边界共享记忆和写入项目长期事实必须获得用户明确确认。用户可以在设置中预先授权部分自动行为，但授权范围、可撤销性和审计记录必须可见。

## 七、产品设计顺序

Magic 的设计与验证按以下顺序推进：

1. 先把 OpenCode 的直接执行能力变成自然可靠的代理方式。
2. 复用旧 AgentCore 的协作底座，定义会话成员如何在当前会话内保留和复用。
3. 完成 CEO 方式的主动进入、上下文连续、协作可见和统一交付闭环。
4. 冻结代理与 CEO 的切换范围、默认值、临时覆盖和失败回退。
5. 以真实项目为样本，先验证 PM、少量项目成员、成员任务会话、共享信息和基本汇报闭环。
6. 再验证成员直达、成员局部 CEO、工程内圆桌和更复杂的自治关系。
7. 最后处理角色模板、团队演化、跨工程协作和规模治理。

不应因为工程模式可以做得宏大，就在没有验证 PM 和项目成员价值之前一次性实现完整组织系统。

## 八、首轮产品设计待冻结决策

以下五项是下一轮专题最优先的产品决策：

1. **工程与资源的对象关系**：工程如何建立在工作区之上，如何关联文件夹、代码和共享事实，以及多个工程如何保持隔离。
2. **三层协作与切换语义**：代理内部协作者、任务级 CEO 协作和会话默认切换的定义、范围、提示和执行中任务的处理。
3. **Agent 身份与记忆生命周期**：会话主 Agent、临时 Agent、会话成员、项目 PM、项目成员、运行实例、历史和记忆如何关联与结束。
4. **用户、主 Agent、PM 和成员的权责**：用户直达成员、PM 知情、任务归属、交付责任和跨边界调用如何保持一致。
5. **自治与确认分级**：哪些行为可以自主完成，哪些只生成建议，哪些涉及长期组织、权限或持久化事实而必须确认；同时冻结工程首版验证范围。

## 九、设计判断

旧 AgentCore 对 Magic 最大的帮助，不是提供一套需要照搬的旧界面，而是提供了三类宝贵证据：

- 复杂 Multi-Agent 协作确实可以被组织成可执行、可观察和可交付的产品能力；
- 用户真正需要的是减少拆解和管理负担，而不是更多编排按钮；
- 可靠的暂停、恢复、上下文、记忆、权限和交付语义，是自然 Agent 体验的底层条件，不是只有 CEO 模式才需要的附属能力。

Magic 的方向因此可以概括为：

> **继承旧产品已经证明的协作能力，改变用户进入协作的方式；让代理成为自然入口，让 CEO 成为可主动展开的工作方式，让工程成为经确认后建立的长期组织。**

## 十一、方向性验收标准

后续专题、交互和实现评审至少应能回答以下问题：

- 用户无需先理解 Multi-Agent、角色或编排概念，就能在代理方式中开始工作。
- 代理内部协作默认不要求用户管理成员、依赖或流程；用户展开时仍能看懂关键状态。
- 模式切换不要求用户重复目标、文件和已经产生的结果。
- 只有真实决策、阻塞、权限边界或用户主动要求时，系统才打断用户。
- 用户始终能知道当前谁对任务负责、工作做到哪里、是否需要介入、真实结果在哪里。
- 进入 CEO 协作或建立工程不会静默改变长期身份、权限、记忆共享范围或项目归属。
- 非工程工作不会因为任务复杂、调用了多个 Agent 或出现模式建议，就被自动收编为工程。
- 失败、部分完成、停止、等待和取消不会被统一包装成成功。
