# Magic 产品设计第一阶段三方对齐会议纪要

> **历史记录说明：**本文保留主产品经理、Nash、Tesla 第一阶段会议的原始结论，用于追溯产品方向如何形成。随后第四位“OpenCode 底座、产品系统边界与运行时契约审阅员”加入终审，Nash 与 Tesla 又完成了交叉复核。本文中的“共同冻结”仅代表第一阶段产品共识，不代表数据模型、接口、状态机、权限或 OpenCode 能力已经冻结。当前正式结论以《Magic 最终产品裁定与技术会议输入》为准。

本文只用于历史追溯和审阅过程复盘，不是新的决策入口。当前未决事项和技术会议状态统一查看《技术会议议题与裁定表》。

## 一、会议目的

本次会议用于让两位独立产品审阅助手在完整阅读 AgentCore 旧项目资料和 Magic 当前产品资料后，对 Magic 的产品方向、设计基线和下一步设计顺序进行交叉复核。

会议遵循的顺序是：

1. 先理解 AgentCore 旧产品的事实、试运行经验和未落地蓝图。
2. 再理解 Magic 已确认的产品方向、待决策设计和工程蓝图。
3. Nash 先完成第一轮审阅。
4. Tesla 独立复核后提出方案建议。
5. Nash 对 Tesla 的观点逐条回应。
6. 主产品经理整合三方意见，形成最终产品设计结论。

## 二、三方共同确认的产品事实

### 2.1 AgentCore 的真实价值

AgentCore 已经形成了以 CEO 主 Agent 为入口的 Multi-Agent 工作系统，并在既有试运行范围内证明了复杂协作的可行性和可用性。它的价值不只是调用多个 Agent，而是已经探索出以下工作闭环：

```text
目标理解 → 任务拆解 → 多 Agent 执行 → 中途干预 → 结果汇总 → 产物交付与状态对账
```

具有较强实现或运行时证据的能力包括：

- CEO 主 Agent、按需直答和复杂任务委派
- 串行、并行、混合执行和依赖调度
- 多轮编排、追加任务、同人续派和上下文连续
- 用户澄清、审批、插话、暂停、恢复和停止
- 协作图、时间线、成员详情和过程可见性
- 真实产物交付，以及失败、部分完成、等待和停止的区分
- 文件、工作区、修改记录、验证结果和交付状态关联
- 记忆、用户偏好、文件夹事实和可复用信息沉淀

这些是 Magic 的重要产品资产，但不代表可以把 AgentCore 的用户入口、内部对象、界面结构和全部蓝图原样迁移。

### 2.2 AgentCore 证据的边界

三方共同确认：

> AgentCore 的实现证据和有限范围试运行证据，不等于大规模市场验证，也不等于用户已经愿意长期使用这种组织化工作体验。

因此，Magic 不仅要验证“系统能不能完成复杂协作”，还要验证：

- 用户能否理解系统正在做什么；
- 用户是否信任系统的决策和交付；
- 用户是否愿意复用会话成员或项目 PM；
- 用户是否因为协作自动化而减少了管理工作；
- 用户是否愿意把更多长期目标交给 Magic。

### 2.3 Magic 的两层产品模型

Magic 不是三个互斥的等级模式，而是两个可以组合的维度：

```text
会话工作方式：代理方式 / CEO 方式
长期组织形态：非工程工作 / 工程组织
```

第一阶段共同确认、并在四方终审中保留为产品不变量的判断：

- 代理方式是完整、平等的强能力工作方式，不是低级模式。
- CEO 方式是显式的团队治理工作方式，不是代理方式的替代品。
- 工程是跨会话、跨任务的长期组织形态，不是 CEO 的简单放大版。
- 代理方式可以调用多个 Agent，但 Agent 数量不决定产品模式。
- 工程不是复杂工作的必经入口。
- 工程内部仍可以使用代理方式或 CEO 方式。
- 用户可以直接选择代理或 CEO，不必先经过系统推荐路径。

## 三、三方共同确认的方向边界

> 本节同时包含长期产品原则和当时提出的首版方案。经四方终审后，长期产品原则继续有效；“一个 PM”“2 到 4 名成员”“三级共享事实”等具体结构仅作为首版建议或待裁定方案，不应被技术团队解释为永久产品规则。

### 3.1 三种协作行为必须分开

| 行为 | 产品含义 | 是否改变默认工作方式 | 是否建立长期组织 |
|---|---|---:|---:|
| 代理内部调用协作者 | 主 Agent 为完成当前目标内部拆解、调用临时 Agent 或复用会话成员 | 否 | 否 |
| 当前任务启用 CEO 协作 | 当前目标形成可查看、可理解、可干预的正式临时协作结构 | 默认不改变 | 否 |
| 切换会话默认工作方式 | 改变当前会话后续任务的默认入口 | 是 | 否 |

禁止以以下信号自动切换模式或建立工程：

- 调用了多个 Agent；
- 任务耗时较长；
- 文件数量较多；
- 任务文本较长；
- 内部出现了依赖、拆解或重试。

### 3.2 长期身份必须有明确边界

以下对象不能混为同一个“Agent”：

- 临时 Agent：服务当前局部任务，完成后不保留持续身份。
- 会话成员：属于一个会话，可在当前会话的多个任务中复用。
- 项目成员：属于一个工程，可跨本工程多个会话和任务复用。
- 会话主 Agent：面对当前会话用户，对会话任务理解、执行和收尾负责。
- 项目 PM：工程级长期协调身份，对项目计划、汇总、依赖和治理负责。
- Agent 运行实例：一次具体执行，不等于 Agent 长期身份。

默认隔离边界为会话和工程。共享文件不等于共享身份、完整上下文、私有记忆、权限或汇报关系。

### 3.3 责任闭环必须成立

三方同意，工程和复杂协作至少必须明确：

- 一个任务有一个最终收口责任人；
- 一个任务有一个统一的最终交付状态；
- 任务可以追溯到所属会话、任务记录和运行实例；
- 一个任务可以产生多个产物，但不能存在多个互不一致的最终结论。

责任分工的当前基线是：

```text
用户：决定目标、范围和关键取舍
PM：负责工程级优先级、计划和冲突协调
任务责任人：负责具体任务的最终结果和验收收口
执行成员：负责被分派的具体工作
运行实例：记录实际执行过程、状态和产物来源
```

首版工程由一个 PM 负责项目级协调，但这不冻结未来所有工程都只能有一个协调主体，也不意味着所有任务都必须经过 PM 亲自派发。

### 3.4 共享事实是独立对象

共享事实不能等同于文件、完整记忆或全部会话上下文。它至少需要能够表达：

- 来源和关联任务或产物；
- 写入者、创建时间和更新时间；
- 当前确认状态；
- 可见范围和使用范围；
- 冲突关系；
- 撤销、废弃或过期状态。

第一阶段推荐采用风险分级，而不是要求所有事实都人工确认。该三级结构是待产品契约继续裁定的建议，不是已冻结的数据模型：

1. 候选事实：Agent 自动提取，带来源，尚未作为项目共识使用。
2. 项目事实：经 PM 或用户确认，可以被成员默认引用。
3. 受争议事实：存在冲突、影响范围较大或需要用户取舍，必须显式处理。

### 3.5 工程与工作区的关系

当前共同基线是：

- 工作区是文件、代码、会话和权限等资源的基础边界。
- 工程是建立在工作区之上的长期组织对象。
- 工程不等同于工作区，也不等同于文件夹。
- 工程可以关联一个或多个文件夹、代码资源和共享事实。
- 使用某个文件夹的普通会话，不自动成为工程会话。
- 多个工程可以存在于同一工作区，默认相互隔离。

工程与文件夹的一对一关系、完整资源模型和最终导航结构暂不冻结，应通过真实工程场景验证。

## 四、三方共同确认的工程首版最小闭环

工程首版不以成员数量、组织层级或圆桌复杂度作为成功标准，而验证下面的最小闭环：

```text
建立一个工程
→ 确认一个 PM
→ 配置少量项目成员
→ PM 创建成员任务会话
→ 成员执行并汇报
→ 共享事实沉淀
→ 用户追踪进度和真实交付
→ 用户直达成员后，PM 能知情并处理项目影响
```

“少量成员”用于验证关系，不是最终人数限制。建议首轮以 2 到 4 名项目成员进行验证。

首版优先观察：

- 任务是否有明确归属和最终责任人；
- PM 是否能理解项目整体状态；
- 成员是否能跨任务会话延续职责；
- 结果是否能回到 PM 和用户；
- 文件、产物、共享事实和交付状态是否可追踪；
- 用户是否减少手动派发、重复沟通和重复说明。

以下内容不在首版默认承诺内：

- 多层级组织和无限嵌套派发；
- 完整圆桌和多团队治理；
- 跨工程成员调用；
- 复杂权限和自动权限扩大；
- 永久职业身份和成员市场；
- 自动完整建队；
- 所有记忆自动共享。

## 五、三方共同确认的产品验证维度

“减少管理负担”不能只是一句方向口号，需要与可靠性和可控性一起观察：

### 自然性

- 用户手动拆解和派发次数；
- 用户重复说明目标次数；
- 无意义的中途确认次数；
- 从提出目标到开始执行的时间；
- 用户是否能在不查看完整协作图的情况下理解关键状态。

### 可靠性

- 任务完成率和交付质量；
- 失败、部分完成、停止和等待是否被及时发现；
- 产物位置、修改记录和验证结果是否真实；
- 状态是否出现过早成功或多个冲突结论。

### 可控性与信任

- 用户是否能快速回答“谁负责、结果在哪里、还需要我做什么”；
- 用户是否知道长期身份、权限和记忆共享范围何时变化；
- 用户是否能在关键决策、阻塞和风险处介入；
- 用户是否愿意再次复用同一个会话成员或 PM；
- 用户是否信任系统的自动协作结果。

不能简单追求用户操作越少越好。必要的确认、风险提示和责任说明是可控性的一部分。

## 六、下一步设计方案

三方最终对下一步形成以下顺序：

### 第一步：对象、责任与生命周期底图

先共同定义最小关系：

- 工作区、文件夹、工程、会话、任务、回合和运行实例的关系；
- 会话主 Agent、临时 Agent、会话成员、项目 PM、项目成员的关系；
- 文件、产物、私有记忆、共享事实、任务状态和权限的边界；
- 用户、PM、任务责任人、执行成员和运行实例的责任关系；
- 创建、复用、暂停、恢复、归档、停用和结束的生命周期。

这一步不是冻结完整工程实现，而是先画出产品对象和责任底图，防止后续反复重构。

### 第二步：三种协作行为的最小契约

在底图基础上，定义：

- 作用范围；
- 持续时间；
- 是否影响正在执行的任务；
- 是否产生长期身份；
- 是否改变记忆或权限；
- 用户如何进入、取消和回退；
- 完成后如何回到原工作方式。

首版至少要让用户清楚区分：

- “这次用 CEO 完成”；
- “以后默认使用 CEO”；
- “把当前工作建立为工程”；
- “将会话成员转为项目成员”。

### 第三步：工程最小闭环专题

完成工程与资源关系、PM、少量成员、任务会话、共享事实、派发汇报、用户直达成员和可追踪交付的专题设计。

### 第四步：会话成员生命周期专题

在代理模式和 CEO 方式的真实使用场景中验证成员何时创建、何时复用、何时空闲、何时归档。成员应是可复用的持续身份，而不是每次都必须调用的固定团队成员。

### 第五步：复杂治理增强

在最小闭环成立后，再考虑多层派发、局部 CEO 团队、圆桌、跨工程专家协作、复杂权限、团队演化和规模治理。

## 七、尚不能提前冻结的事项

以下内容必须继续保持待决策或待验证状态：

- 工程是否与文件夹一一对应；
- 工程完整资源模型、导航结构和权限模型；
- 会话成员自动保留期限、数量上限和归档策略；
- PM 是否永远是工程唯一协调中心；
- 用户直达成员后的全部冲突、抢占和优先级细节；
- 共享事实自动写入的完整规则；
- 记忆迁移和复杂冲突处理；
- 跨工程调用、永久职业身份、成员市场和自动完整建队；
- 圆桌、多团队自治和无限层级组织。

任何涉及长期身份、工程归属、权限、跨边界记忆、默认工作方式或明显外部副作用的变化，都必须提交用户确认。

## 八、第一阶段三方结论

Nash 与 Tesla 没有发现会推翻 Magic 当前方向的根本性分歧。两位审阅助手的结论可以合并为：

> **Magic 的方向和产品设计基线已经成立。下一步不应继续扩大组织想象，而应先冻结对象关系、责任归属、生命周期、共享事实和三种协作行为的最小契约，再用真实用户行为验证它是否真的减少了管理负担。**

主产品经理的整合判断是：

> **先让 Magic 变得自然可靠，再让它变得组织强大；先保证谁负责、结果在哪里、还需要用户做什么，再扩展更多 Agent、层级和治理能力。**

本纪要是后续产品专题的共同输入，不替代《产品方向总纲》和具体专题文档。若未来用户对产品方向作出正式调整，应先更新上游方向基线，再同步审阅本纪要和《产品经理工作准则》。

## 九、四方终审补充

第四位系统边界审阅员加入后，四方没有发现需要推翻本纪要方向的根本分歧，但共同补充了以下约束：

- OpenCode 的版本、接口、状态、恢复、权限、事件和持久化能力尚未经过本轮实机核查；“由 OpenCode 负责”只表示能力来源设想，不表示底座已经确认满足要求。
- AgentCore 的 `Run`、`RunSession`、transcript、DAG、Journal 和事件机制可以提供经验或实现参考，但不能直接等同于 Magic 的任务、Agent 身份、项目成员、工程或产品权威状态。
- 任务必须有唯一的当前责任人；责任可以显式转移，但任一时刻只能有一个。任务状态与运行实例状态必须分离。
- 首版“一个 PM、2 到 4 名成员、一个主工作区和主目录”均为验证约束，不是永久限制。
- 不承诺执行中的任意无损模式重编排。产品承诺应是尽量保持目标、上下文、产物和责任连续；无法无损时明确告知，并提供继续、暂停、重新规划或回退。
- 正式实现前必须分别通过产品契约门槛和 OpenCode 实机能力门槛；首版完成后还要通过真实用户价值验证。

四方终审后的完整分级、待裁定事项和技术会议议程，见《Magic 最终产品裁定与技术会议输入》。
